---
title: セルフヒーリングテスト
description: UI が変わったときに、リプレイされたエージェントステップがどのように回復し、記録がどのように自己修復するかを説明します。
---

セルフヒーリングテストは、記録された `agent.act()` ステップの下で UI が変わっても
成功し続けます。ランナーは、記録が画面と一致しなくなるまでリプレイします。
その後、ステップの残りをエージェントに引き継ぎ、エージェントは現在の画面からゴールを完了させます。
`read-write` モードでは、後続のチェックが成功すれば、同じ実行で新しいフローを保存できます。

実行サマリーでは、このように回復した各ステップを `handed off` として数えます。

```text
        Cache  4 replayed · 1 handed off · 1 missed
```

## UI が変わったときに起こること

2 つのアクションで記録されたステップと、記録後に名前が変わったボタンを例にします。

```ts title="tests/checkout.e2e.ts"
import { expect, test } from 'e2e';

test('applies a discount code', async ({ app, agent, screen }) => {
  await app.open('/checkout');
  await agent.act('apply the discount code SUMMER');
  await expect(screen.getByRole('status')).toHaveText('10% off');
});
```

1. リプレイは、モデルを呼び出さずに `Discount code` フィールドに `SUMMER` を入力します。
2. リプレイは、記録されたボタン `Apply` を探します。ボタンは現在 `Redeem` になっているため、
   15 秒以内に一致するコントロールが見つかりません。リプレイは `target-not-found` で停止します。
3. エージェントは、リプレイが行ったことの記録とともにステップを受け取ります。
   エージェントは画面を読み取り、`Redeem` を見つけてタップします。
4. `expect` が成功します。試行の終了時に、ランナーは `Apply` の代わりに `Redeem` を使った
   新しい記録を保存します。
5. 次の実行では、モデルを呼び出さずにステップ全体をリプレイします。

リプレイは決して推測しません。記録されたコントロールが一致しなくなった場合は引き継ぎになり、
最も近いコントロールをタップすることはありません。コントロールの照合方法については
[リプレイの仕組み](/cache#how-a-replay-works) を参照してください。

## エージェントに伝えられる内容

エージェントへの最初のプロンプトには、リプレイがすでに実行したアクションと、
リプレイが停止した理由が列挙されます。上のステップでは次のようになります。

```text
Cached replay already performed these recorded actions for this step:
1. type "SUMMER" into textbox "Discount code"
Replay stopped (target-not-found) after 1 of 2 recorded actions.
Continue the step from the CURRENT screen state shown below — do NOT redo the actions above.
```

プロンプトは、すでに処理された送信など、それらのアクションを繰り返さないようエージェントに指示します。
2 つの停止理由では警告が追加されます。

- `end-mismatch`: すべてのアクションが実行されましたが、リプレイはそれが記録された結果を
  生んだことを示せません。結果が表示されなかったか、リプレイが操作する前からすでに画面に
  表示されていました。エージェントは、操作する前にステップが反映されたかどうかを確認するよう
  指示されます。
- `action-uncertain`: アクションが失敗しましたが、それがアプリに届いた可能性があります。
  エージェントは、同様の操作を再度試す前に現在の状態を確認するよう指示されます。

リプレイされたアクションと待機は、ステップの [予算](/reference/agent#budgets) と期限に
加算されます。[キャッシュのページ](/cache#why-a-step-was-not-replayed) にすべての停止理由が
記載されています。リプレイが最初のアクションの前に停止した場合、そのステップは引き継ぎではなく
ミスになります。エージェントは通知なしに最初からステップを実行します。

## 記録が自己修復する仕組み

回復したステップは、新しいステップと同様に再記録されます。条件は `read-write` モードであり、
かつロケーターのアサーションや `agent.assert` など、ステップ後のチェックが成功した場合だけです。
その場合、ストアが書き込みを拒否しない限り（`not-written`）、記録は新しいコントロールと
終了状態で保存されます。それ以外の場合、古いエントリーは削除されます。

- ステップが失敗した場合。次の実行では、壊れたフローをリプレイしません。
- ステップの後に成功したチェックがない場合。
- ステップがリプレイで確認できる変化を何も起こさなかったため、保存する新しいフローがない場合。
- エージェントが `end-mismatch` を修正するために操作する必要があった場合。次の検証済みの実行で、
  失敗したフローと修正を合わせたものではなく、クリーンなフローを記録します。

どのモデルも応答しなかった場合や実行がキャンセルされた場合、エントリーはそのまま残ります。
レポートの `step.cache.write` に何が起こったかが記載されます。すべての値と、何がチェックとして
数えられるかについては [記録が書き込まれるタイミング](/cache#when-a-recording-is-written) を
参照してください。

## UI の変更だけでなくリグレッションも検出する

エージェントは、記録されたクリックではなく、指示のゴールに向かって回復します。
割引ボタンが移動していれば、エージェントはそれを見つけます。割引が機能しなくなっていれば、
ステップかその後のチェックが失敗します。

それでも、意図しない形でゴールが達成されることがあります。たとえば、別の割引が適用される場合です。
上の `toHaveText('10% off')` のように、テストの最後に結果の決定論的なチェックを置いてください。
このチェックは、リプレイされた場合も回復した場合も、毎回の実行で行われます。

## どのステップが回復したかを確認する

回復した各ステップは、停止理由とともに `step.cache.mode: 'agent-concluded'` を報告し、
`step.cache.detail` にはリプレイがどこでなぜ停止したかが記載されます。
[トレースのページ](/debugging#traces) では、ステップの下に次のように表示されます。

```text
cache: replayed 1 of 2 recorded actions, then the agent took over: a recorded target is not on the screen; recorded with `openai/gpt-6-luna-fast`; at action 2 of 2, tap button "Apply"; recording saved (`.e2e/cache/<entry>.json`)
```

`agent.act()` は、`write` を除いた同じ記録を `result.cache` として返します。
[カスタムエグゼキューター](/executors#replay-cache) は `ctx.replayedPrefix` で引き継ぎを受け取り、
同様に現在の画面から続行する必要があります。

## CI で回復にモデル呼び出しのコストがかからないようにする

`CI` が設定されていて `cache` が未設定の場合、キャッシュは `read-only` になるため、
回復したステップは保存されません。そのステップは CI の実行のたびに再び引き継ぎになり、
毎回モデル呼び出しのコストがかかります。ローカルの `read-write` の実行で再記録してから、
[リプレイキャッシュをコミット](/cache#commit-the-replay-cache) してください。

回復させずに失敗させるには、CI を `--strict-cache` 付きで実行します。記録がリプレイできなくなった
ステップは `REPLAY_STALE` で失敗し、モデルは呼び出されません。
[古い記録で失敗させる](/cache#fail-on-a-stale-recording) を参照してください。
