`@e2e-dev/mobile` は、iOS シミュレーター、Android エミュレーター、およびマシンに接続したスマートフォンでテストを実行します。[agent-device](https://github.com/callstack/agent-device) をベースに構築されています。テストはブラウザのテストと同じ `agent`、`screen`、`expect` の API を使います。

## セットアップ

iOS シミュレーターのランタイムを含む Xcode、またはエミュレーターを含む Android SDK をインストールします。次に [クイックスタート](/quickstart)に従い、**Mobile
(iOS/Android)** を選択します。ウィザードは macOS では iOS を、それ以外では Android を選択し、ワーカー 1 つで設定アプリをターゲットにするため、アプリを指定する前にテストを実行できます。デバイスの起動はテストの計時が始まる前に行われ、`launchTimeout` には含まれません。完成したセットアップについては[サンプルプロジェクト](/example-projects)を参照してください。

セットアップを確認します。

<CodeGroup>
```bash npm
npx e2e doctor
```

```bash pnpm
pnpm exec e2e doctor
```

```bash bun
bunx e2e doctor
```
</CodeGroup>

agent-device、Xcode または Android SDK、ターゲットが指定する各デバイス、`appPath` のビルドをチェックします。`appPath` がない場合は、1 台のデバイスが起動しているときに `bundleId` がインストールされているかをチェックします。[`e2e doctor`](/reference/cli#e2e-doctor) を参照してください。

## アプリを指定する

ターゲットの `app.bundleId` に、アプリの bundle id またはパッケージ名を設定します。`app.open()`、`app.restart()`、`app.clearState()` はそのアプリを起動します。ビルドを指定するには `appPath` を追加します。iOS では `.app` バンドル、Android では `.apk` です。

```ts
{
  name: 'ios',
  engine: mobile({ platform: 'ios' }),
  app: {
    bundleId: 'com.example.app',
    appPath: './build/MyApp.app', // the iOS .app bundle
  },
}
```

デバイスのターゲットには `bundleId`、`appPath`、またはその両方が必要です。エンジンは自分では何もインストールしません。デバイスごとに 1 回 `device.installApp()` を呼び出してください。たとえば、すべてのテストが受け取るフィクスチャ内で呼び出します。パスを指定しない場合は `app.appPath` をインストールします。`bundleId` がない場合、`app.open()` はビルドがインストールしたアプリを起動します。

CI でテストスイートを実行するには、[モバイルのジョブ](/ci#mobile-jobs)を参照してください。

### 起動引数と権限

`app.launchArguments` と `app.permissions` は、新規の起動のたびに適用されます。

```ts
app: {
  bundleId: 'com.example.app',
  launchArguments: ['-e2e', 'YES'],
  permissions: { camera: 'grant', notifications: 'deny', location: 'reset' },
},
```

- 起動引数は、iOS ではプロセスの引数、Android では `am start` の引数です。
- 権限は起動前に設定されるため、システムのプロンプトは表示されません。`app.clearState()` はデータとともに権限をリセットし、その後再度設定します。
- iOS の `deny` は、プロンプトなしでアプリに拒否を伝えます。Android では権限を取り消すため、OS が再度尋ねます。
- 実行前のウォームアップではどちらも渡されないため、各テストは `app.open()` で開始してください。
- ビルドモードを選択する引数は、アプリの中身を変えます。各モードに独自の `app.identity` を与えて、記録を分けてください。

1 つのテストを独自の値で起動するには、`device.openApp` を使います。渡した各オプションはターゲットの値全体を置き換えます。`permissions: { camera: 'deny' }` はターゲットのその他の権限を破棄します。ターゲットのアプリを再起動する場合、渡さなかったオプションはターゲットの値を保持します。

```ts
await device.openApp('com.example.app', { relaunch: true, permissions: { camera: 'deny' } });
```

### アプリを別の言語で実行する

iOS では、起動引数でその起動時のアプリの言語と地域を設定します。デバイスは自身の言語を保ちます。言語ごとに 1 つのターゲットを追加してください。

```ts
{
  name: 'ios-fr',
  engine: mobile({ platform: 'ios' }),
  app: {
    bundleId: 'com.example.app',
    launchArguments: ['-AppleLanguages', '(fr)', '-AppleLocale', 'fr_FR'],
  },
}
```

- アプリがその言語を含んでいる必要があります。含んでいない場合、iOS は開発言語を表示します。
- Android には言語用の起動引数がありません。ホスト型のデバイスでは、`browserstack()` または `testmu()` で `language` と `locale` を設定してください。ローカルのデバイスでは、実行前にデバイスの言語を設定してください。

### Expo の開発ビルド

開発ビルド (`expo-dev-client`) は dev launcher で開き、JavaScript を dev サーバーから読み込みます。iOS シミュレーターでは、次の起動引数でサーバーを直接開き、dev メニュー、そのオンボーディングシート、フローティングボタンをオフにします。`app.command` がサーバーを起動します。

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { mobile } from '@e2e-dev/mobile';

export default {
  targets: [
    {
      engine: mobile({ platform: 'ios' }),
      app: {
        bundleId: 'com.example.app',
        launchArguments: [
          '--initialUrl', 'http://localhost:8081',
          '-EXDevMenuShowsAtLaunch', 'NO',
          '-EXDevMenuIsOnboardingFinished', 'YES',
          '-EXDevMenuShowFloatingActionButton', 'NO',
        ],
        command: { executable: 'npx', args: ['expo', 'start', '--port', '8081'] },
        readyUrl: 'http://localhost:8081/status',
      },
    },
  ],
} satisfies E2EConfig;
```

- ウォームアップではアプリが dev launcher に残ります。各テストは `app.open()` で開始してください。
- 最初の起動では、dev サーバーがアプリをバンドルするのを待ちます。テストの最初のチェックには長めのタイムアウトを指定してください。
- Android では、expo-dev-launcher は `--initialUrl` を読み取りません。`device.openLink` とビルドの `exp+<slug>://expo-development-client/?url=<encoded server URL>` リンクでサーバーを開いてください。

## デバイスのテストを書く

`screen` は、ネイティブのコントロールを `button`、`textbox`、`listitem`、`switch` などの共通のロールに対応付けます。ネイティブの要素識別子には `getByTestId` を使ってください。

```ts
import { test } from '@e2e-dev/mobile';
import { expect } from 'e2e';

test('shows the version in dark mode', async ({ agent, app, device, screen }) => {
  await device.setAppearance('dark');
  await app.open();
  await agent.act('go to General, then About');
  await expect(screen.getByRole('button', /^iOS Version/)).toBeVisible();
  await expect(device.locator('role=navigation-bar id=About')).toBeVisible();
});
```

テスト間では、アプリは前のテストが残した状態のままです。デバイスは `selectOption`、`setInputFiles`、`scrollIntoView`、`secondaryTap`、および `tap` と `doubleTap` の `modifiers` をサポートしていません。ネイティブのコントロールにはタップとスワイプを使ってください。

### フレームワーク別のテスト ID

`getByTestId` は、iOS ではアクセシビリティ識別子を、Android ではリソース ID を読み取ります。UI フレームワークごとに設定方法が異なります。

| フレームワーク | ID の設定方法 | 例 |
| --- | --- | --- |
| React Native | `testID` | [with-expo](https://github.com/e2e-inc/e2e/tree/main/examples/with-expo) |
| SwiftUI | `.accessibilityIdentifier()` | [with-swiftui](https://github.com/e2e-inc/e2e/tree/main/examples/with-swiftui) |
| UIKit | `view.accessibilityIdentifier`、または Interface Builder の Identity inspector の Identifier | - |
| Jetpack Compose | `Modifier.testTag()` | [with-compose](https://github.com/e2e-inc/e2e/tree/main/examples/with-compose) |
| Compose Multiplatform | `Modifier.testTag()` | [with-kotlin-multiplatform](https://github.com/e2e-inc/e2e/tree/main/examples/with-kotlin-multiplatform) |
| Flutter | `Semantics(identifier:)` | [with-flutter](https://github.com/e2e-inc/e2e/tree/main/examples/with-flutter) |
| .NET MAUI | `AutomationId` | [with-maui](https://github.com/e2e-inc/e2e/tree/main/examples/with-maui) |
| NativeScript | `testID` | [Norrix のガイド](https://docs.norrix.net/guides/e2e-testing/#3-write-a-first-test) |

- Android では、ネイティブの `android:id` と .NET MAUI の `AutomationId` は `<package>:id/<id>` として読み取られます。`getByTestId('greet')` は、iOS と同様に、アプリのパッケージなしでそれらを見つけます。`android:id/content` のようなフレームワークの ID は、完全な形でのみ一致します。
- Android では、ルートの composable が `Modifier.semantics { testTagsAsResourceId = true }` を設定するまで、Compose はテストタグを隠します。これがないと、`getByTestId` は何も見つけません。iOS は Compose Multiplatform のタグをそのまま読み取るため、共有画面では Android の activity でこのフラグを設定します。
- SwiftUI では、`VStack` などのコンテナに付けた `.accessibilityIdentifier()` は、その中のすべての要素の ID を置き換えます。すると `getByTestId` はコンテナの ID では `LOCATOR_AMBIGUOUS` で失敗し、子の ID では何も見つけません。両方を保つには、識別子の前に `.accessibilityElement(children: .contain)` を置いてください。
- Flutter では、ボタンの `Semantics` を `MergeSemantics` で包んで、ID とボタンのロールが 1 つのノードに載るようにしてください。
- NativeScript では、`testID` と `accessibilityIdentifier` は同じ ID を設定します。`getByTestId('login-button')` は両方のプラットフォームで `<Button text="Login" testID="login-button" />` を見つけます。`accessibilityLabel` は ID ではなく名前を設定します。Android では NativeScript がそれをテキストの前に置くため、`<Button text="Help" accessibilityLabel="Open help" />` の名前は `Open help. Help` になります。`getByRole('button', /^Open help/)` で一致させてください。

## device フィクスチャ

`device` は、モデル呼び出しなしでデバイスの設定を変更します。ネットワーク、権限、外観、アプリのインストールなどです。各呼び出しはレポート内で `device.<method>` ステップになります。[モバイルエンジンのリファレンス](/reference/mobile#device)にすべてのメソッドが記載されています。

`device.locator` は、上のテストのように agent-device のセレクターを受け取り、`screen` のクエリでは名前を指定できないコントロールに使います。

`device.installApp` は、アップグレードや新規インストールのテストにも使えます。

```ts
const { app } = await device.installApp('./build/MyApp.app', { reinstall: true });
await device.openApp(app);
```

`device.openApp` は bundle id、パッケージ、または表示名を受け取り、リンクは受け取りません。`device.openLink` は、ディープリンクや Web リンクを、固定されたアプリ (またはオプションの `app`) で開きます。マジックリンクでのサインインやディープリンクのルートに使います。

```ts
await device.openLink('myapp://orders/42');
await expect(screen.getByText('Order #42')).toBeVisible();
```

`device.setNetwork('offline')` と `device.setAirplaneMode(true)` は Android でのみ動作します。iOS シミュレーターは Mac のネットワークを共有し、simctl はステータスバーしか変更できないため、iOS ではどちらも `UNSUPPORTED_CAPABILITY` で失敗します。`setNetwork('online')` と `setAirplaneMode(false)` は iOS では何もしないため、両方のプラットフォームで実行されるクリーンアップフックは合格します。

Android では、`setNetwork('offline')` は Wi-Fi だけをオフにするため、アプリはモバイル通信でオンラインのままになることがあります。アプリをオフラインにするには `setAirplaneMode(true)` を使ってください。Android 11 以降が必要です。エンジンはテスト後にネットワークを復元しないため、テストが失敗したときにも実行される `afterEach` で再度オンにしてください。

```ts
import { afterEach, test } from '@e2e-dev/mobile';
import { expect } from 'e2e';

afterEach(async ({ device }) => {
  await device.setAirplaneMode(false);
});

test('shows the offline banner', { platforms: ['android'] }, async ({ app, device, screen }) => {
  await app.open();
  await device.setAirplaneMode(true);
  await expect(screen.getByText('You are offline')).toBeVisible();
});
```

`device.clearKeychain()` はシミュレーターのキーチェーンをリセットします。キーチェーンは `app.clearState()` では変更されないため、これにより保存されたセッショントークンは次の起動時には消えています。iOS 専用です。

`device` でカバーされないものについては、`device.unstable_raw` が、テストのセッションにバインドされた [agent-device](https://github.com/callstack/agent-device) クライアントに加えて、セッション名、デバイスの ID と名前、クライアントの呼び出しに展開するための `selection` を提供します。これは不安定な API であり、どのリリースでも変更または削除される可能性があります。

```ts
const { client, deviceId } = device.unstable_raw;
const { nodes } = await client.capture.snapshot({});
```

クライアントの呼び出しはステップではありません。レポートやトレースには含まれず、エージェントのキャッシュはそれらをリプレイせず、渡したシークレットは秘匿処理されず、呼び出し後に画面が落ち着くのを待つこともありません。

<Accordion title="テキストサイズとアニメーション">
`device` にはシステムのテキストサイズやアニメーション用のメソッドがないため、`unstable_raw` を通じて設定してください。テキストサイズは `app.open()` の前に変更します。実行中のアプリは再度起動するまで古いサイズを保持することがあるため、テストの途中で変更した場合は `app.restart()` を呼び出してください。

```ts
import { afterEach, test } from '@e2e-dev/mobile';
import { expect } from 'e2e';

afterEach(async ({ app, device }) => {
  const { client, selection } = device.unstable_raw;
  await client.settings.update({ ...selection, setting: 'text-size', state: 'large' });
});

test('the checkout button shows at the largest text size', async ({ app, device, screen }) => {
  const { client, selection } = device.unstable_raw;
  await client.settings.update({ ...selection, setting: 'text-size', state: 'accessibility-extra-extra-extra-large' });
  await app.open();
  await expect(screen.getByRole('button', 'Checkout')).toBeVisible();
});
```

`text-size` は iOS シミュレーターと Android で動作し、どちらも `large` がデフォルトです。`state: 'off'` または `'on'` を指定した `setting: 'animations'` は Android 専用で、iOS では失敗します。Android では、ウィンドウ、トランジション、アニメーターのスケールを 0 または 1 に設定します。どちらの設定もテストの終了後も残るため、`afterEach` で元に戻してください。次のテストの `app.open()` がアプリを再起動するため、設定を戻すだけで十分です。
</Accordion>

<Accordion title="ピッカーのテスト用の写真">
`device` はライブラリに写真を追加できないため、`app.open()` の前にホストから追加してください。iOS シミュレーターでは `xcrun simctl addmedia` で追加でき、`deviceId` はシミュレーターの UDID です。`addmedia` は呼び出すたびにコピーを追加し、エージェントのステップは同一の写真を区別できないため、このサンプルはシミュレーター自身のデータディレクトリにマーカーファイルを残し、写真を 1 回だけ追加します。シミュレーターを消去すると、マーカーはライブラリとともに消えます。

```ts
import { execFileSync } from 'node:child_process';
import { existsSync, writeFileSync } from 'node:fs';
import { resolve } from 'node:path';
import { test, type Device } from '@e2e-dev/mobile';
import { expect } from 'e2e';

// Put a JPEG named receipt.jpg beside this test.
const receipt = resolve(import.meta.dirname, 'receipt.jpg');

function addPhotoOnce(device: Device, file: string): void {
  const { deviceId } = device.unstable_raw;
  const listing = execFileSync('xcrun', ['simctl', 'list', 'devices', '-j'], { encoding: 'utf8' });
  const { devices } = JSON.parse(listing) as {
    devices: Record<string, { udid: string; dataPath: string }[]>;
  };
  const simulator = Object.values(devices).flat().find((d) => d.udid === deviceId);
  if (!simulator) throw new Error(`No simulator ${deviceId}`);
  const marker = resolve(simulator.dataPath, 'tmp', 'receipt-photo-added');
  if (existsSync(marker)) return;
  execFileSync('xcrun', ['simctl', 'addmedia', deviceId, file]);
  writeFileSync(marker, file);
}

test('attaches the receipt from the photo library', { platforms: ['ios'] }, async ({ app, device, screen }) => {
  addPhotoOnce(device, receipt);
  await app.open();
  await screen.getByLabel('Choose photo').tap();
  await screen.getByRole('image', /^Photo, /).first().tap();
  await expect(screen.getByText(/^Receipt attached/)).toBeVisible();
});
```

システムのピッカーはアプリの外で動作しますが、その写真は画面のツリーにあり、それぞれ `Photo, ` と撮影日を名前に持つ `image` です。ピッカーはその日付で新しい順に並べます。これは写真の EXIF データにある日付で、追加した日ではありません。

Android エミュレーターでは、`adb` でファイルをプッシュしてメディアスキャンを行う必要があり、そのピッカーは独自の名前を持つ別のアプリです。このページは Android では検証されていないため、そのロケーターを書く前にトレースでピッカーのツリーを読んでください。
</Accordion>

<Accordion title="折りたたみ式のシミュレーターとエミュレーター">
`device.fold(pose)` は、iPhone Duo シミュレーターまたは折りたたみ式の Android エミュレーター (Pixel Fold のプロファイル、または汎用の "7.6in Foldable") をヒンジの姿勢にします。`closed` は外側のディスプレイを点灯させます。`half-open` と `open` は内側のディスプレイを点灯させます。Duo では、ヒンジがその姿勢に達した時点で呼び出しが戻り、通常 10〜16 秒かかるため、`actionTimeout` は 20 秒以上にしてください。Duo での `half-open` は 130° のブック型です。Android エミュレーターでは、Android が対応するデバイスの状態を確定したあと、数秒以内に戻ります。`half-open` はプロファイル固有の角度 (Pixel の折りたたみ式では 90°) で、カバーディスプレイへの折りたたみは、エミュレーターが表示する "Swipe up to continue" のロック画面を閉じます。次の観測では、もう一方のディスプレイ上のアプリが読み取られます。

エンジンは姿勢をリセットしないため、リトライと次のテストは前のテストが残した姿勢から始まります。テストが失敗したときにも実行される `afterEach` で元に戻してください。

```ts
import { afterEach, test } from '@e2e-dev/mobile';

afterEach(async ({ device }) => {
  await device.fold('closed');
});

test('the list and the detail split across the fold', async ({ agent, app, device }) => {
  await app.open();
  await device.fold('half-open');
  await agent.assert('the list and the detail sit on either side of the fold', { vision: true });
});
```
</Accordion>

### 画面遷移を録画する

[`app.startRecording()` と `app.stopRecording()`](/reference/app#startrecording) は、画面の 1 つの区間を `.mp4` として録画します。ロケーターの `boundingBox()` は、要素のフレームをポイント単位 (Android では物理ピクセル) で返します。

```ts
test('the sheet slides up', { video: 'off' }, async ({ app, screen }) => {
  await app.open();
  await app.startRecording({ name: 'sheet' });
  await screen.getByRole('button', 'Open sheet').tap();
  await expect(screen.getByText('Sheet title')).toBeVisible();
  const [video] = await app.stopRecording();
});
```

録画は `app.open()` のあとに開始してください。`device.closeApp()` のあとに開始した録画は、停止時にデバイスのセッションを終了するため、そのあとでアプリを再度開いてください。[`videoTouches`](/reference/mobile#videotouches) が `false` でない限り、タップが表示されます。

## 複数のデバイス

プラットフォームごとにターゲットを追加します。

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { mobile } from '@e2e-dev/mobile';

const app = { bundleId: 'com.example.app' };

export default {
  targets: [
    { name: 'iphone', engine: mobile({ platform: 'ios' }), app },
    { name: 'pixel', engine: mobile({ platform: 'android' }), app },
  ],
  workers: 1,
} satisfies E2EConfig;
```

テストは両方のターゲットで実行されます。プラットフォーム固有のラベルや動作を持つテストには、`platforms: ['ios']` または `platforms: ['android']` を設定してください。

ファイルを並列に実行するには、デバイスのプールを指定し、`workers` を少なくともそのサイズに設定します。各デバイスには 1 つのワーカーが割り当てられます。

```ts
mobile({ platform: 'ios', device: ['iPhone 17', 'iPhone 17 Pro'] })
```

`device` がない場合、エンジンはワーカーの上限まで、起動済みのデバイスを使います。接続可能な (USB またはネットワーク経由の) ペアリング済みの iPhone や iPad は、起動済みとみなされます。起動済みのデバイスがない場合は、シャットダウンしているデバイスを 1 台起動します。iOS では iPhone、iPad、Apple TV の順に、Android ではスマートフォンまたはタブレットを TV より優先し、次に新しい OS、次に名前順で選びます。2 つのワーカーが同じデバイスを操作することはありません。

## エージェントのツール

エージェントにはすでに `tap`、`type`、`scroll` などの基本的なアクションがあります。アプリの切り替え、自由形式のスワイプ、システムのアラートには `mobileTools` を追加してください。設定内のすべてのデバイスエンジンを 1 回の呼び出しに渡します。

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { mobile } from '@e2e-dev/mobile';
import { mobileTools } from '@e2e-dev/mobile/tools';
import { gateway } from 'ai';

const app = { bundleId: 'com.example.app' };
const iphone = mobile({ platform: 'ios' });
const pixel = mobile({ platform: 'android' });

export default {
  targets: [
    { name: 'iphone', engine: iphone, app },
    { name: 'pixel', engine: pixel, app },
  ],
  agents: { default: { model: gateway('openai/gpt-6-luna-fast'), tools: mobileTools(iphone, pixel) } },
} satisfies E2EConfig;
```

呼び出しは、現在の試行を実行しているエンジンに送られます。`open_app`、`swipe`、`alert` はデバイスの状態を変更するため、キャッシュのリプレイ中もエージェントがライブで実行します。各ツールについては[モバイルエンジンのリファレンス](/reference/mobile#agent-tools)で説明しています。これらと並べて独自のツールを追加するには、[プロジェクトツール](/tools)を参照してください。

## 実機

agent-device は、マシンに接続したスマートフォンを、シミュレーターと同じように、ほかのエンジンやオプションなしで操作します。認識されているデバイスを一覧表示します。

<CodeGroup>
```bash npm
npx agent-device devices --platform ios
```

```bash pnpm
pnpm exec agent-device devices --platform ios
```

```bash bun
bunx agent-device devices --platform ios
```
</CodeGroup>

次に、一覧に表示されたとおりの名前で `device` にスマートフォンを指定します。

```ts
mobile({ platform: 'ios', device: 'QA iPhone' })
```

ID ではなく名前を使ってください。エンジンが `device` の文字列を ID として読むのは、シミュレーターの UDID または `emulator-<port>` のシリアルの場合だけです。名前が一致する最初のデバイスが選ばれるため、各スマートフォンには一意の名前を付けてください。`device` がない場合、接続可能な (USB またはネットワーク経由の) ペアリング済みの iPhone や iPad、または接続された Android スマートフォンは起動済みとみなされ、起動済みのシミュレーターと並んでプールに加わります。

スマートフォンを一度だけセットアップします。

<Tabs>
  <Tab title="iOS">
  - スマートフォンをペアリングして信頼し、ロックを解除して、デベロッパモードをオンにします。
  - agent-device は XCTest ランナーをビルドして署名し、スマートフォンに配置します。`AGENT_DEVICE_IOS_TEAM_ID` にチーム ID を、`AGENT_DEVICE_IOS_BUNDLE_ID` に `com.example.agentdevice.runner` のような一意の逆 DNS 形式の ID を設定してください。署名プロファイルは、その ID と `<id>.uitests` を許可している必要があります。最初の実行ではランナーをビルドするため、時間がかかります。
  - これらの変数を変更したら、`npx agent-device daemon stop` を実行してください。実行中のデーモンは、起動時の環境を保持します。
  - `app.appPath` は、シミュレーター用の `.app` ではなく、署名済みのデバイス用ビルドである必要があります。

  iOS の署名については `npx agent-device help physical-device` で詳しく説明しています。
  </Tab>
  <Tab title="Android">
  - USB デバッグをオンにし、スマートフォンを承認します。`adb devices` に `device` として表示されます。
  - `app.appPath` はエミュレーターと同じ `.apk` です。
  </Tab>
</Tabs>

スマートフォンでは、アプリ内の `localhost` はスマートフォン自身を指します。アプリをマシンのネットワークアドレスに向けるか、Android では `adb reverse tcp:<port> tcp:<port>` でポートを転送してください。

<Accordion title="スマートフォンで動作しないもの">
一部のデバイス操作には、シミュレーターまたはエミュレーターが必要です。スマートフォンでは、agent-device のメッセージとともに失敗します。

- iPhone では、すべてのデバイス設定がシミュレーター専用です。`app.permissions`、`device.setPermission`、`app.clearState()`、`device.setLocation`、`device.clearLocation`、`device.setAppearance`、生体認証のメソッド、`device.clearKeychain` です。`device.clipboard`、`device.setClipboard`、`device.fold` も同様です。
- iPhone でクリーンな状態から始めるには、`device.installApp(path, { reinstall: true })` で再インストールしてください。agent-device が削除するアプリを判断できるよう、`app.bundleId` または `app` オプションを設定してください。
- `xcrun devicectl list devices` に表示されない古い iPhone は、agent-device が CoreDevice なしで操作します。タップ、入力、画面は動作します。インストール、`--video`、`device.openLink`、`app.launchArguments` は失敗します。ビルドは Xcode からインストールし、`app.bundleId` を固定してください。
- Android スマートフォンでは、`device.setLocation` はエミュレーター専用です。`device.setBiometrics('fingerprint', ...)` は、スマートフォンが `cmd fingerprint` を公開している場合にのみ動作します。
- iPhone での `--video` は、約 15 フレーム毎秒のスクリーンショットから作成され、フレームが欠落します。
</Accordion>

## ホスト型デバイス

アプリの自動インストールとデバイスのクリーンアップを備えた、ホスト型の iOS シミュレーターと Android エミュレーターには [Limrun](/integrations/limrun) を使ってください。

サービスがホストするデバイスで実行するには、`device` に `DeviceProvider` を設定します。シミュレーター、エミュレーター、またはスマートフォンの隣で agent-device デーモンを実行するサービスであれば、どれでも動作します。プロバイダーは、実行の開始時にワーカースロットごとに 1 台のデバイスをリースし、実行の終了時に解放します。

[Expo Simulators](/integrations/eas) には `@e2e-dev/eas` の `expoSimulators()` を使います。[TestMu AI](/integrations/testmu) には `@e2e-dev/testmu` の `testmu()` を使います。[BrowserStack](/integrations/browserstack) には `@e2e-dev/browserstack` の `browserstack()` を使います。[E2B](/integrations/e2b) 上の Android には `@e2e-dev/e2b` の `e2b()` を使います。その他のサービスについては、以下の例の `hostedDevices` のような数十行のプロバイダーを書いてください。

```ts
mobile({
  platform: 'ios',
  device: hostedDevices({ serviceUrl: 'https://devices.example.com', image: 'ios-18-iphone-17' }),
})
```

- 各ワーカーは独自のセッションをリースし、サービスはセッションの実行中に課金します。`workers` はテストスイートが使い切れる数にしてください。
- リプレイキャッシュは `app.bundleId` をキーにするため、ローカルで作成した記録はホスト型デバイスでリプレイされます。
- リースされたデバイスは、ローカルのデバイスと同様に、テストの計時が始まる前にウォームアップされます。

<Accordion title="DeviceProvider の契約">
```ts
export interface DeviceProvider {
  /** Label in progress lines and error messages. */
  readonly name: string;
  acquire(request: DeviceRequest): Promise<DeviceLease>;
  release(lease: DeviceLease, context: DeviceReleaseContext): Promise<void>;
  record?(lease: DeviceLease, context: ProviderRecordContext): Promise<ProviderRecording>;
}

export interface DeviceLease {
  /** The provider's handle (a session id), handed back to `release`. */
  readonly id: string;
  /** The agent-device daemon the worker connects to; a lease names this, `client`, or both. */
  readonly daemon?: { readonly baseUrl: string; readonly authToken?: string };
  /** agent-device client configuration the worker's client is created with: a lease scope, a `stateDir`. */
  readonly client?: DeviceClientConfig;
  /** Device to select inside that daemon, when it hosts more than one. */
  readonly device?: string;
  /** Device to select inside that daemon by the id agent-device lists it under: a simulator UDID or an Android serial. */
  readonly deviceId?: string;
  /** Bundle id or package the provider installed itself; skips the target's `app.appPath`. */
  readonly installedApp?: string;
}
```

**`acquire`** は、ランナーのプロセス内で、すべてのワーカースロットに対して同時に実行されます。リクエストには、`platform`、`runId`、`targetName`、`slot`、`slots`、`app` (ターゲットの `app.bundleId`)、解決済みの `appPath`、`agentDeviceVersion` (特定のバージョンのデーモンを起動するサービス向け)、`projectRoot`、`env`、中断用の `signal`、レポーターに届く `log` が含まれます。

- トークンは `process.env` ではなく `request.env` から読み取ってください。プロジェクトのファイルは `process.cwd()` ではなく `request.projectRoot` 以下から読み取ってください。
- 実行するものがないターゲットは何もリースしません。
- `installedApp` は、リクエストに `appPath` がある場合にのみ設定してください。そうでない場合、実行は失敗します。

**`release`** は、最後のワーカーが終了したあと、`cleanupTimeout` 以内に、失敗、中断、`prepare` の例外など、あらゆる終了経路で実行されます。`acquire` が返したオブジェクトを受け取るため、プロバイダーは独自のフィールドをそこに保持できます。ワーカーに届くのは `DeviceLease` のフィールドだけです。1 つのスロットのリースに失敗した場合、実行はテストの前に終了し、エンジンは取得したすべてのリースを引き続き解放します。

**`client`** は agent-device クライアントの設定で、JSON データとして、セッション名と `daemon` のアドレスの上に適用されます。`session`、`daemonBaseUrl`、`daemonAuthToken`、`daemonTransport` を設定したリースは拒否されます。agent-device 自身のデバイスクラウドのランタイムの場合、`client` は `leases.allocate` が返したリースのスコープ (`tenant`、`runId`、`leaseId`、`leaseBackend`、`leaseProvider`) を持ちます。スコープのないコマンドはローカルのデバイスにフォールバックします。`client` 内の `stateDir` はワーカーをプロバイダーが起動したデーモンに向けるため、`daemon` のアドレスは不要です。

**`record`** は省略可能です。試行が動画を録画するとき、ワーカーは agent-device の画面録画の代わりにこれを呼び出します。ワーカーは別のプロセスである場合があるため、`record` が受け取るのはリースのフィールドだけで、`acquire` が保持した状態は受け取りません。`ProviderRecording` (`e2e/engine` の型) を返し、その `stop` は、受け取ったディレクトリにファイルを書き込んで `{ file }` を返す (`video/<file>` として保持されます) か、サービスが保持する録画について `{ url, mediaType }` を返します (レポートからリンクされます)。失敗した `record` は試行の起動を失敗させます。失敗した `stop` は、試行の終了時にもう一度試行されます。
</Accordion>

<Accordion title="例: セッション API 用のプロバイダー">
一般的なセッション API には 3 つのリクエストが必要です。セッションを作成し、デーモンに到達できるまでポーリングし、停止します。

```ts title="device-provider.ts" expandable
import type { DeviceProvider } from '@e2e-dev/mobile';

/**
 * Leases devices from a service that starts an agent-device daemon per
 * session. Replace the three requests with your service's API.
 */
export function hostedDevices(options: { serviceUrl: string; image: string }): DeviceProvider {
  return {
    name: 'hosted-devices',
    async acquire(request) {
      const token = request.env['DEVICE_SERVICE_TOKEN'];
      if (token === undefined || token === '') throw new Error('DEVICE_SERVICE_TOKEN is not set');
      const headers = { Authorization: `Bearer ${token}`, 'Content-Type': 'application/json' };
      // 1. Ask for a device; name the session after the run so it can be found later.
      const created = await fetch(`${options.serviceUrl}/sessions`, {
        method: 'POST',
        headers,
        body: JSON.stringify({
          platform: request.platform,
          image: options.image,
          name: `e2e ${request.runId} ${request.targetName} ${request.slot + 1}/${request.slots}`,
        }),
        signal: request.signal,
      });
      if (!created.ok) throw new Error(`device service: HTTP ${created.status}`);
      const { id } = (await created.json()) as { id: string };
      // 2. Wait until the session exposes its agent-device daemon.
      for (;;) {
        const response = await fetch(`${options.serviceUrl}/sessions/${id}`, { headers, signal: request.signal });
        const session = (await response.json()) as { status: string; daemonUrl?: string; daemonToken?: string; viewerUrl?: string };
        if (session.status === 'ready' && session.daemonUrl !== undefined) {
          if (session.viewerUrl !== undefined) request.log(`watch at ${session.viewerUrl}`);
          return { id, daemon: { baseUrl: session.daemonUrl, authToken: session.daemonToken } };
        }
        if (session.status !== 'starting') throw new Error(`device service: session ${id} is ${session.status}`);
        await new Promise((resolve) => setTimeout(resolve, 5_000));
      }
    },
    async release(lease, context) {
      // 3. Stop the session; the run waits for this within cleanupTimeout.
      const token = context.env['DEVICE_SERVICE_TOKEN'] ?? '';
      await fetch(`${options.serviceUrl}/sessions/${lease.id}/stop`, {
        method: 'POST',
        headers: { Authorization: `Bearer ${token}` },
        signal: context.signal,
      });
    },
  };
}
```
</Accordion>

<Accordion title="例: agent-device がサポートするデバイスクラウド">
agent-device 自身が通信するデバイスクラウドでは、独自のセッション API は不要です。`@e2e-dev/mobile/lease` の `agentDeviceLeases()` は、`env` の認証情報でワーカースロットごとに agent-device デーモンを起動し、`selectors` でリースを割り当て、実行がリースを保持している間はそれを維持し、解放時には agent-device がセッションの終了を確認しない限り失敗します。`@e2e-dev/testmu` の `testmu()` は [TestMu AI](/integrations/testmu) 向けに、`@e2e-dev/browserstack` の `browserstack()` は [BrowserStack](/integrations/browserstack) 向けに、この方法で動作します。

```ts title="device-cloud-provider.ts" expandable
import type { DeviceProvider } from '@e2e-dev/mobile';
import { agentDeviceLeases } from '@e2e-dev/mobile/lease';

/**
 * Leases devices from a device cloud agent-device itself speaks to. Each
 * worker slot gets its own agent-device daemon, whose runtime for the cloud
 * starts the session when the lease is allocated and ends it on release.
 * `provider` is agent-device's name for the cloud.
 */
export function cloudDevices(options: { provider: string; device: string; osVersion: string; app: string }): DeviceProvider {
  const leases = agentDeviceLeases({ provider: options.provider, label: options.provider });
  return {
    name: options.provider,
    async acquire(request) {
      const token = request.env['CLOUD_TOKEN'];
      if (token === undefined || token === '') throw new Error('CLOUD_TOKEN is not set');
      return leases.acquire(request, {
        // The daemon's runtime reads the credentials from its environment.
        env: { CLOUD_TOKEN: token },
        selectors: { device: options.device, providerOsVersion: options.osVersion, providerApp: options.app },
        summary: `${options.device}, ${request.platform} ${options.osVersion}`,
      });
    },
    release: (lease, context) => leases.release(lease, context),
  };
}
```
</Accordion>

## Web との違い

| Web の場合 | デバイスの場合 |
| --- | --- |
| `app.open('/path')` とエージェントの `navigate` 動詞 | アプリの URL も `navigate` もありません。`app.open()` は `app.bundleId` を新規に起動し、`device.openLink(url)` はそこでリンクを開きます。[`app.linkBase`](/reference/config#linkbase) を指定すると、`app.open('/path')` はパスをリンクとして開きます |
| `test.setup` がセッションを保存し、`session:` が復元する | 利用できません。シミュレーターには移植可能なセッションのスナップショットがないため、テストごとにサインインするか、アプリにデータを投入してください |
| シークレットの入力 | `type_secret` と `screen.getByLabel(...).fill(secret)` が、宣言されたシークレットをセキュアなフィールドに入力します |
| `--video` は WebM のスクリーンキャストを書き出す | `--video` は、タップを表示したデバイス画面の MP4 を書き出す (`videoTouches: false` で非表示) か、デバイスプロバイダー独自の録画を保持します |
| キャッシュはページのパスを基準にする | キャッシュは `<bundle id> / <screen title>` という場所を基準にします。タイトルは iOS ではナビゲーションバー、Android ではツールバーから読み取ります |

### デバイスの既知の制限

- デバイスのノードが持つ属性は `placeholder` だけです。
- iOS の React Native のタブ (`accessibilityRole="tab"`) のロールは `other` です。テスト ID またはラベルでクエリし、`toBeSelected` でアサートしてください。チェックボックス、ラジオボタン、`toBeChecked` は両方のプラットフォームで動作します。
- iOS では、通常の React Native の `View` はツリー内に子を持たないため、それに対する `filter({ has })` やそれにスコープしたクエリは何にも一致しません。一方、`filter({ hasNot })` は、除外するつもりだった行も含め、そのような行をすべて残します。画面の `ScrollView` (`device.locator('role=scroll-area')`) にスコープするか、子にテスト ID を付けてください。
- 48dp より小さく描画された Jetpack Compose のクリック可能な要素は、ツリー内で 2 つのボタンとして表示され、タップは `has no parent-owned touch point` で失敗します。コントロールを Android の最小タッチターゲットである 48dp 以上にしてください。
- `display: none` で非表示にした要素はツリーにないため、`toBeAttached` は失敗します。`toHaveCount(0)` または `toBeHidden` でアサートしてください。
- ソフトウェアキーボードが中心を覆っているノードは、画面外にスクロールされたノードと同様に非表示になります。キーボードのキー、候補バー、ドックは表示されたままで、フォーカスされたフィールドも同様です。コンテナは、その子の 1 つがキーボードの上に表示されている間は表示されたままです。その他の覆われたノードでは `toBeVisible()` が失敗し、それらへのタップは `ACTION_FAILED` で失敗します。先に `device.dismissKeyboard()` を呼び出すか、ノードが見えるようスクロールしてください。[可視性](/reference/mobile#visibility)を参照してください。
- iOS での `doubleTap()` と `screen.doubleTapAt()` は、約 285〜335 ms 間隔の 2 回のタップです。ダブルタップの検出には 350 ms 以上の猶予を与えてください。
- iOS では、`device.home()` のあとも `device.foregroundApp()` はセッションのアプリを返します。代わりに画面をチェックしてください。
- クリップボードサービス用のシェルコマンドがない Android ビルド (Android 16 エミュレーターもその 1 つ) では、`device.clipboard()` と `device.setClipboard()` は `UNSUPPORTED_CAPABILITY` をスローします。コピーを確認するには、フィールドに貼り付けてフィールドを読み取ってください。
- iPhone Duo では、`--video` は録画開始時に点灯していたディスプレイを録画します。`device.fold` がアプリをもう一方のディスプレイに移すと、動画の残りは黒くなります。

## トラブルシューティング

デバイスの失敗では、agent-device 自身のメッセージが表示されます。エージェントの下では、より具体的なコードのないエンジンの障害は `APP_UNREACHABLE` として報告されるため、コードより先にメッセージを読んでください。多くの場合、失敗したのはアプリではありません。

**iOS のオートメーションランナーがビジー状態、停止状態、またはスナップショットを提示できない。** 負荷の高い画面やアニメーション中の画面はランナーの処理能力を超えることがあり、Ctrl-C で停止した実行はランナーをビジー状態のまま残すことがあります。メッセージはランナーと最初の対処 (通常は再実行) を示します。次の実行でも同じ状態になる場合は、以下のコマンドでデーモンを停止し、シミュレーターを再起動してください。

**Android で `device.installApp()` が bundle id やパッケージがないと報告する。** agent-device がビルドのパッケージを判別できなかったため、`app.open()` が起動するものがありません。APK のマニフェストを読み取れない場合、`ANDROID_SDK_ROOT`、`ANDROID_HOME`、macOS では `~/Library/Android/sdk`、または `~/Android/Sdk` 以下にある Android SDK の `aapt` にフォールバックします。ターゲットの `app.bundleId` を設定してください。または `ANDROID_HOME` をエクスポートしてから agent-device デーモンを停止し、次の実行でその変数とともに起動されるようにしてください。

**Android がフォアグラウンドアプリのコンテンツ不足を報告する、または iOS がアプリが実行されていないと報告する。** agent-device がまだ画面を読み取れませんでした。多くの場合、コールドスタート後にまだ読み込み中のアプリです。iOS では、これが数えられるのは `app.open()`、`app.restart()`、`device.openLink()` のあと最初に読み取れる画面までです。たとえば、まだアプリを起動中の実機の iPhone などです。あとから終了したアプリは即座に失敗します。待機するロケーターのアクションや `expect` は、まだ存在しない要素の場合と同様に、この状態を待ちます。待機時間が尽きても画面が読み取れない場合、ステップはこのメッセージで失敗します。`count()` や `isVisible()` のような即時の読み取りは代わりに一致なしとみなすため、画面が読み取れない間は `not.toBeVisible()` が合格することがあります。描画前にクラッシュしたアプリの場合も同様です。エージェントの次のターンのような観測は、この状態で即座に失敗します。

**デバイスでのタイムアウト。** デバイスでタイムアウトしたシミュレーターの起動、ランナーへの接続、アプリの起動は、agent-device のメッセージとヒントを伴う `ENGINE_FAILURE` になり、`LAUNCH_TIMEOUT`、`ACTION_FAILED`、`STEP_TIMEOUT` になることはありません。

**タイムアウトを超えて続くアクション。** タップ、入力、キー、スワイプ、`back` は、それぞれの `timeout` (デフォルトは `actionTimeout`) を受け取ります。デバイスが時間内に応答しない場合、ステップは `ACTION_FAILED` で失敗し、リトライされません。入力が届いている可能性があるためです。保留中のタップ、ダブルタップ、フォーカス、チェックまたはチェック解除は、ステップがその待機をやめたとき、または実行が中断されたときにキャンセルされます。すでにデバイスに送信された入力は完了する場合があります。残り時間以上の長さ押し続ける `longPress` は、送信前に拒否されます。その `timeout` を引き上げてください。スナップショットとスクリーンショットは、それを取得する呼び出しのタイムアウト内で実行されるため、応答しなくなったデバイスは、テストのタイムアウトまで待たせるのではなく、`ACTION_FAILED` でステップを失敗させます。`locator.waitFor`、`expect`、`toHaveScreenshot` は、最後のスナップショットに、それまでで最も遅かったスナップショットまでの追加時間をテストのタイムアウト内で与えるため、その間に表示された画面でも合格します。一度も表示されない要素は `LOCATOR_NOT_FOUND`、`expect` の場合は `ASSERTION_FAILED` で失敗します。
