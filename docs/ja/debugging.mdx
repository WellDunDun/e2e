失敗したテストは、そのエラーと[トレースページ](#traces)へのパスを出力します。実行全体の要約が必要な場合は、`markdown` レポーターを追加してください。`.e2e/summary.md` が書き出されます。

## 失敗を読む

`list` レポーターの `Failed Tests` セクションには、エラー、失敗した行、失敗したロケーターに近い一致、アプリが記録したログ、トレースページが表示されます。アプリの最初の 3 件のエラー (コンソールエラー、捕捉されなかった例外、失敗したリクエスト、5xx レスポンス) を、トレースページと同様に秘匿処理したうえで引用します。`.e2e/summary.md` にも引用されます。

```text
 FAIL  |web| tests/todos.e2e.ts > shows the remaining count
LOCATOR_NOT_FOUND: locator did not become visible: getByRole("heading", name: "Todos")
 ❯ tests/todos.e2e.ts:31:3
 ❯ at http://127.0.0.1:4271/nope
 ❯ app 2 errors, 2 warnings logged
   × console error: Error occurred prerendering page "/todos"
   × network error: GET /api/todos 500 Internal Server Error
 ❯ trace .e2e/results/todos-shows-the-remaining-count-796fac5f12ab34cd/trace.md
```

終了コードは失敗の種類を示します。

| 終了コード | 意味 | ジョブをリトライするか |
| ---: | --- | --- |
| 1 | テストが失敗した | テストが flaky な場合のみ |
| 2 | 設定、収集、またはポリシー | まず報告された問題を修正する |
| 3 | エンジン、アプリのプロセス、モデルプロバイダー、アーティファクト、またはクリーンアップのインフラの失敗 | 原因が一時的な場合 |
| 4 | ランナーの内部エラー | 報告する |
| 130 | 実行が中断された | |

## トレース

デフォルトでは、失敗、タイムアウト、中断、または flaky になった各テストは、その[結果ディレクトリ](#artifacts)にトレースページ `trace.md` を持ちます。リンクが機能するよう、エディターの Markdown プレビューで開いてください。テストが実行されたブラウザまたはデバイスに続いて、次の内容が表示されます。

- **ステップ。** アクションが作用したノード、アサーションが待機中に読み取った値、リプレイキャッシュの判断、アプリが記録したログ、ページの遷移先、前のステップからの画面の変化。
- **アプリのログ。** コンソール出力、捕捉されなかった例外、失敗したリクエスト、4xx および 5xx レスポンスを、それぞれのステップとともに表示します。最大 50 行で、エラーと警告が先に表示されます。1 回の試行で保持されるのは、エラーと警告が最大 200 件、その他の行が最大 100 件です。
- **エージェントの最後のターン。**
- **失敗時の画面。** スクリーンショットとセマンティックツリーで、最大 5 秒以内に取得されます。時間内に応答しないアプリには画面のセクションがありません。

アサーションが終始 1 つの値を読み取っていた場合は、期待値が間違っているか、アプリがその状態に到達しなかったかのどちらかです。アプリのログで失敗したリクエストを探してください。読み取った値が変化したアサーション (`"2 remaining" x3 -> at 410ms "1
remaining"`) は、アプリと競合しています。アクションのあとの `screen: unchanged` は、そのアクションが目に見える効果を持たなかったことを意味します。Web では、ステップの画面はアクションが残した画面です。デバイスでは、ステップが操作した画面です。

[`trace`](/reference/config#trace) モードは、どのテストがページを保持するかを設定します。`--trace` は、合格したテストも含め、実行のすべてのテストでページを保持します。`--trace off` は何も書き出しません。テスト自体の `trace` オプションは両方より優先されます。

## アーティファクト

各テストは `.e2e/results/` (または [`<output>`](/reference/config#output)`/results/`) 以下に 1 つのディレクトリを持ち、トレースページと試行ごとの `attempt-<n>` が含まれます。シリアルグループのテストは 1 つのディレクトリを共有します。

```text
.e2e/results/todos-adds-a-todo-1a2b3c4d5e6f7a8b/trace.md
.e2e/results/todos-adds-a-todo-1a2b3c4d5e6f7a8b/attempt-1/screen-at-failure.txt
.e2e/results/todos-adds-a-todo-1a2b3c4d5e6f7a8b/attempt-1/screenshots/001-failure.png
```

テストの実行に到達した各実行は、まず `results/` を空にします。`--last-failed` による再実行は、再実行元のレポートが挙げるファイルを保持し、自身の試行を各テストの `rerun-<n>/` 以下に書き出します。

| アーティファクト | タイミング |
| --- | --- |
| スクリーンショット | 失敗した試行で、エンジンが可能な場合に 1 枚取得します。組み込みの `agent.assert` は、`screenshot: false` でない限り、どちらの判定のあとでも 1 枚取得します。`app.screenshot('label')` は要求に応じて 1 枚取得します。マスクされるのはセキュアなフィールドだけです。[シークレット入力後のスクリーンショット](/reference/security#screenshots-after-a-secret-fill)を参照してください。 |
| ダウンロード | `browser.waitForDownload` で保存されたファイルで、種類は `download`、アプリが提供したままの内容です。ランナーがその中のシークレットをマスクする条件は[ダウンロード](/reference/security#downloads)に記載されています。 |
| 動画 | [録画した](#watch-it-happen)場合。動画は何もマスクしません。[秘匿処理が及ばない範囲](/reference/security#where-redaction-stops)を参照してください。 |
| エージェントのトランスクリプト | [`--debug`](#agent-steps) を指定した場合。 |

## スクリプト向け: report.json

テストの実行に到達したすべての実行は、[出力ディレクトリ](/reference/config#output) (デフォルトは `.e2e`) に `report.json` も書き出します。これは実行のすべての結果をバージョン付きのスキーマで保持します。`--reporter json` はこれを stdout に出力します。

```bash
jq '.run | {status, exitCode, errors}' .e2e/report.json
jq '.run.results[] | select(.status != "passed") | .attempts[-1]
    | {status, error, failure, steps: [.steps[] | select(.status != "passed") | {api, label, source, status, error}], artifacts}' .e2e/report.json
```

`run.errors` は実行レベルの失敗を保持します。失敗した各結果の最後の試行は次を保持します。

| フィールド | 内容 |
| --- | --- |
| `error` | コード、メッセージ、ソース行、アサーションの詳細 |
| `failure` | 画面とスクリーンショットのアーティファクト、およびロケーターの候補 |
| `steps` | 失敗に至った呼び出し。各ステップの `events` は、そのステップが行ったこと (`engine`)、ポーリングしたもの (`poll`)、アプリの遷移先 (`navigation`) を保持します。エージェントのステップには `cache` と直近のモデルのターンが加わります。`observationTruncated: true` は、少なくとも 1 つのセマンティックな観測が不完全だったことを意味します。 |
| `appLog` | アプリが記録したログ。各行の `step` はそのステップの `index` で、最初のステップより前には存在しません。 |
| `artifacts` | 取得されたファイル |

シリアルグループのテストは独自の `attempts` を持ちません。結果は `run.serialGroups` にあり、各試行の各テストに 1 つのメンバーがあります。実行が中断した、またはメンバーに到達しなかったリトライは `cutRetry: true` を持ち、判定を保持しないため、スキップしてください。

```bash
jq '.run.serialGroups[] | (.attempts | map(select(.cutRetry != true)) | last).members[]? | select(.status != "passed")
    | {testId, status, error, failure}' .e2e/report.json
```

## 動作を見る

<CodeGroup>
```bash npm
npx e2e run --headed                      # a visible browser
npx e2e run --video                       # record every attempt
npx e2e run --video=retain-on-failure     # record every attempt, keep the failures
```

```bash pnpm
pnpm exec e2e run --headed                      # a visible browser
pnpm exec e2e run --video                       # record every attempt
pnpm exec e2e run --video=retain-on-failure     # record every attempt, keep the failures
```

```bash bun
bunx e2e run --headed                      # a visible browser
bunx e2e run --video                       # record every attempt
bunx e2e run --video=retain-on-failure     # record every attempt, keep the failures
```
</CodeGroup>

`--video` は省略可能なモードを取ります。テストファイルはその前に置くか、`--video=<mode>` と書いてください。

各録画は試行のディレクトリに保存されます。Web ではページごとの WebM、デバイスでは MP4 です。失敗の要約には、パス、またはホスト型ブラウザが録画を保持する場合は URL が出力されます。ステップの `startedAt` から録画の `startedAt` を引くと、動画内でのそのステップの位置がわかります。

CI では、設定で `video: 'on-first-retry'` を指定してください。最初に合格したテストは何も録画せず、flaky なテストはリトライの録画を残します。

ターゲットの `video` は設定の `video` より優先され、`--video` は両方より優先されます。`test('checkout', { video: 'on' }, ...)` のようなテスト自体のオプションは、それらすべてより優先されます。

設定の `video` と `--video` は、エンジンが録画できるターゲットにのみ適用され、それ以外のターゲットは 1 つの通知で示されます。ターゲットやテストが、エンジンで作成できない録画を要求した場合、実行はテストの開始前に `UNSUPPORTED_ARTIFACT` で失敗します。

すべてのモードとファイルは[録画](/reference/config#recording)に記載されています。

## テストをステップ実行する

`--step` は最初のステップを実行し、その後の各ステップはキーを押すまで保留します。`--headed` を追加すると、ステップ間のブラウザを見ることができます。

<CodeGroup>
```bash npm
npx e2e run tests/checkout.e2e.ts --step --headed
```

```bash pnpm
pnpm exec e2e run tests/checkout.e2e.ts --step --headed
```

```bash bun
bunx e2e run tests/checkout.e2e.ts --step --headed
```
</CodeGroup>

保留中のステップは、そのテストの下、すでに実行されたステップの下に表示されます。

```text
 ❯ |web| tests/checkout.e2e.ts 0/1
   └── pays with a card paused
       ✓ app.open "/checkout" 412ms
       ▶ step 2  locator.fill "getByLabel("Email")"  tests/checkout.e2e.ts:9
         press enter to run this step, press h to show help, press q to quit
```

キーは [`--watch`](/reference/cli#watch-mode) に準じます。プロンプトでは次のキーが使えます。

| キー | 動作 |
| --- | --- |
| Enter | 保留中のステップを実行し、次のステップを保留する |
| `n` | リトライを含めこのテストの残りを実行し、次のテストで保留する |
| `a` | 停止せずに実行の残りを実行する |
| `h` | プロンプトの下にすべてのキーを表示する、または非表示にする |
| `q`、Esc | Ctrl-C と同様に実行を停止する。テストは `interrupted` で終了し、残りはスキップされ、終了コードは 130 |

- プロンプトから 150 ms 以内に押されたキーは無視されるため、前のステップ向けに押したキーがこのステップを実行することはありません。Ctrl-C はステップの実行中も含め、いつでも機能します。
- ステップが保留されている時間はどこにも数えられません。ステップの所要時間にも、テストの `timeout` にも、`maxDuration` にも含まれません。ステップのあとでハングしたテストは、残っていた時間でタイムアウトします。レポート上のテスト自体の所要時間には保留時間が含まれます。
- セットアップテスト、リトライ、`afterEach` フック、フィクスチャのティアダウン、`expect.poll` の読み取り内のステップは、停止せずに実行されます。`agent.act` は 1 つのステップです。
- `Promise.all` などで同時に開始されたステップは 1 つのプロンプトを共有し、1 回の Enter で実行されるため、それを引き起こすクリックと並べた `waitForResponse` がキーを待つことはありません。別のステップが保留されたときにすでに実行中のステップは、自身のタイムアウトで実行を続けます。
- ステップが保留されている間に、ホスト型ブラウザやデバイスがアイドル状態が長すぎるセッションを終了することがあります。

`--step` は一度に 1 つのテストを実行します。CI、`--watch` との併用、`--workers` が 1 を超える場合、json レポーターとの併用では拒否されます。

## ターミナルなしでテストをステップ実行する

コーディングエージェントのシェルのように stdin または stdout がターミナルでない場合、`--step` はテストをバックグラウンドで実行します。コマンドは最初に保留されたステップで、そのステップが待機している画面とともに戻ります。以降の各コマンドは同じディレクトリから実行してください。コマンドにターミナルを与えるシェルでは、代わりにキーのプロンプトが表示されます。stdin を null デバイスからリダイレクトしてください (`< /dev/null`、Windows の `cmd` では `< NUL`)。

<CodeGroup>
```bash npm
npx e2e run tests/checkout.e2e.ts --step
npx e2e run --step next
```

```bash pnpm
pnpm exec e2e run tests/checkout.e2e.ts --step
pnpm exec e2e run --step next
```

```bash bun
bunx e2e run tests/checkout.e2e.ts --step
bunx e2e run --step next
```
</CodeGroup>

```text
✓ app.open "/checkout" 124ms
Paused before step 2 of pays with a card [web]:
  locator.fill "getByLabel("Email")" (tests/checkout.e2e.ts:9)
Screen:
  http://localhost:3000/checkout
  heading "Checkout"
  textbox "Email"
  button "Pay"
Next: e2e run --step next runs it, e2e run --step rest runs the rest, e2e run --step stop ends the run.
```

| コマンド | 動作 |
| --- | --- |
| `e2e run --step next` | 保留中のステップを実行し、次のステップで戻る |
| `e2e run --step rest` | 停止せずに実行の残りを実行する |
| `e2e run --step stop` | `q` と同様に実行を停止する。終了コードは 130 で、別のコマンドが待機中でも停止する |

- 各応答は、前回のコマンド以降に実行が出力した内容から始まります。上の最初の行のように実行されたステップごとに 1 行で、失敗したステップの下にはエラーが表示されます。最後の応答は実行の要約と `The stepped run has ended.` で終わり、コマンドは実行の終了コードで終了します。
- 画面には、トレースページと同様にアプリのノードが、シークレットを秘匿処理した状態で一覧表示されます。
- 1 つのディレクトリにつきステップ実行は 1 つです。そこで 2 つ目の `--step` を実行すると、1 つ目が終わるまで終了コード 2 で終了します。
- `next` と `rest` は、コマンドが出力したステップに対してのみ作用します。待機中にコマンドが強制終了された場合、次のコマンドは見逃した内容 (実行せずにそのステップ、または実行の終了) を出力します。ステップの実行中に送られた `next` や `rest` は、何もせずに次の一時停止を待ちます。いずれの場合も、応答はアクションが適用されなかったことを示す行で始まります。
- コマンドがないまま 30 分間保留されたステップは、実行を停止します。
- `--step` を使う場合、`next`、`rest`、`stop` という名前のファイルやディレクトリには、`./next` のようにパスが必要です。

## コンソール出力

テスト内の `console.log` と `console.error` は、テストの実行中に、ストリーム、ターゲット、ファイル、テストを示す見出しの下に出力されます。

```text
stdout | |web| tests/todos.e2e.ts > adds a todo
hello from the test
```

ファイルのトップレベルやレポーターなど、テストの外からの出力は `stdout | runner` または `stderr | runner` の下に出力されます。どちらのストリームも stdout に出力されます。`list` レポーターがない場合、出力は書き込まれたとおりそれぞれのストリームに送られます。ただし `json` レポーター (`--reporter json` または `reporters` 内) の場合は例外で、stdout をレポート用に確保し、出力を stderr に出力します。設定の読み込み時の出力は実行のヘッダーより前に出力され、読み込みが失敗した場合は警告がヘッダーに置き換わります。

ランナーはシークレットの値を[秘匿処理](/reference/security#redaction)します。レポートにはコンソール出力が含まれないため、後で読む人が必要とするものには `expect` かアーティファクトを使ってください。

## エージェントのステップ

次のフラグで、エージェントが何をしたかを確認できます。

<CodeGroup>
```bash npm
npx e2e run --debug     # timings and a step table on stderr
npx e2e run --ai-trace  # every model call, for a trace viewer
npx e2e run --no-cache  # run the agent live instead of replaying
```

```bash pnpm
pnpm exec e2e run --debug     # timings and a step table on stderr
pnpm exec e2e run --ai-trace  # every model call, for a trace viewer
pnpm exec e2e run --no-cache  # run the agent live instead of replaying
```

```bash bun
bunx e2e run --debug     # timings and a step table on stderr
bunx e2e run --ai-trace  # every model call, for a trace viewer
bunx e2e run --no-cache  # run the agent live instead of replaying
```
</CodeGroup>

`--debug` は、実行の各フェーズの所要時間と、エージェントのステップごとに 1 行の表を追加します。表には、所要時間、モデル呼び出し、トークン、プロンプトキャッシュの割合、そしてプロバイダーが報告する場合はコストが含まれます。計画された各ステップは、モデルのトランスクリプトもアーティファクトとして保存します。

```console
[e2e debug] agent steps (execution order, model openai/gpt-6-luna-fast, total $0.0312)
  step                                   total   model  observe  action  calls  tokens in/out  cached       cost
  act "add a todo named groceries"       3.9s    2.8s    410ms   620ms      3  9412/388       61% (5740)   $0.0198
  assert "the list shows groceries"      1.2s    1.1s     88ms     0ms      1  3120/41        0% (0)       $0.0114
```

`--ai-trace` は `.e2e/ai-trace.json` を書き出します。エージェントのステップごとに 1 つの実行、モデル呼び出しごとに 1 つのエントリーがあり、入力は秘匿処理され、画像のバイトは数に置き換えられます。[unbox-ai](https://github.com/e2e-inc/unbox-ai) で読むと、プロンプト、ツール呼び出し、トークン使用量を確認できます。

<CodeGroup>
```bash npm
npx unbox-ai runs .e2e/ai-trace.json
npx unbox-ai summary .e2e/ai-trace.json --run 0
```

```bash pnpm
pnpm dlx unbox-ai runs .e2e/ai-trace.json
pnpm dlx unbox-ai summary .e2e/ai-trace.json --run 0
```

```bash bun
bunx unbox-ai runs .e2e/ai-trace.json
bunx unbox-ai summary .e2e/ai-trace.json --run 0
```
</CodeGroup>

リプレイされたステップはモデル呼び出しを行わず、AI トレースも残しません。フロー全体をトレースしたり、古い[記録](/cache)を原因から除外したりするには、`--no-cache` を追加してください。

## よくあるエラー

| コード | よくある原因 | 対処 |
| --- | --- | --- |
| `APP_UNREACHABLE` | `app.url` で何も応答しないか、`app.command` が準備完了にならなかった。iOS では、メッセージが代わりにオートメーションランナーを示す場合がある | `app.command.log` を設定して読む。ポートを確認する。`app.command.startupTimeout` を引き上げる。iOS のランナーの場合はメッセージに従う ([モバイル](/mobile#troubleshooting)を参照) |
| `APP_ALREADY_RUNNING` | ランナーが `app.command` を開始しようとしたとき、すでに何かが `app.url` を提供している | それを停止するか、ローカルの実行では `reuseExisting: true` を設定する |
| `LOCATOR_NOT_FOUND` | ロールや名前が誤っている、テキストが完全一致していない、要素が iframe 内にある、ページが開いていない | マークアップでアクセシブルな名前を確認する。`exact: false` を試す。iframe には `browser.frameLocator` を使う。`--headed` で確認する |
| `LOCATOR_AMBIGUOUS` | 2 つ一致した: 非表示の重複、繰り返されるラベル | `{ name }` を追加する、コンテナ内にスコープする、`filter`、`first()`、または `{ visible: true }` を使う |
| `ASSERTION_FAILED` | 期待値が誤っているか、状態が落ち着くのが 5 秒より後。`agent.assert` の場合は判定が false だった | スクリーンショットと比較する。マッチャーに `{ timeout }` を指定する。質問を書き直す |
| `ASSERTION_INCONCLUSIVE` | `agent.assert` または `agent.extract` が、画面に表示されていないものについて尋ねた: 別のページにある、まだ読み込み中、またはピクセルにしかない | 先に正しい画面を開くか待機する。答えがピクセルにある場合は `vision: true` を追加する (メッセージにそう表示される) |
| `ACTION_FAILED` | 要素が覆われている、無効化されている、切り離されている、または操作がタイムアウトした | 先に `expect` で正しい条件を待機する。オーバーレイを閉じる |
| `STEP_BUDGET_EXHAUSTED`、`STEP_TIMEOUT` | エージェントがアクション、モデル呼び出し、または時間を使い切った | ゴールを 1 つのステップに絞る。予算についてはエージェントのエントリーの `maxSteps` または `maxModelCalls` を、`act` ステップについては設定の `timeout` を、`assert`、`waitFor`、`extract` についてはエージェントの `judgmentTimeout` を引き上げる |
| `MODEL_UNAVAILABLE` | 設定でモデルが構築されていないか、GitHub Copilot が設定されたモデルをあなたのアカウントに提供していない | [モデル](/models)を参照。Copilot の場合は[モデルを選ぶ](/subscriptions#pick-a-model)を参照 |
| `MODEL_PROVIDER_FAILED` | 不正なキー、レート制限、クレジット不足、または 1 つのリクエストのすべての試行が 120 秒間応答を得られなかった | プロバイダーが読み取るキーとクォータを確認する。低速なローカルモデルの場合は、より小さな画面 (`agents.<name>.maxObservationBytes`) またはより高速なモデルを使う |
| `MODEL_REFUSED` | モデルがプロンプトを拒否した (終了理由 `content-filter`)。終了コード 1 | 指示を言い換えるか、別のモデルに切り替える |

[エラーリファレンス](/reference/errors)には、すべてのコード、そのクラス、終了コードが記載されています。
