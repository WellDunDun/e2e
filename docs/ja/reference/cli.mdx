`e2e` コマンドは、プロジェクトのスキャフォールド、テストの実行・一覧表示・探索、リプレイキャッシュ、サブスクリプションのログイン、テレメトリの管理、そして自身のアップグレードを行います。すべてのコマンドは `--help` を受け付けます。

<CodeGroup>
```bash npm
npx e2e init                              # scaffold a project
npx e2e run                               # run every test
npx e2e run tests/signup.e2e.ts --headed  # one file, with a visible browser
```

```bash pnpm
pnpm dlx e2e init                              # scaffold a project
pnpm exec e2e run                              # run every test
pnpm exec e2e run tests/signup.e2e.ts --headed # one file, with a visible browser
```

```bash bun
bunx e2e init                              # scaffold a project
bunx e2e run                               # run every test
bunx e2e run tests/signup.e2e.ts --headed  # one file, with a visible browser
```
</CodeGroup>

<Note>
CLI には Node.js 24.8 以降（Node.js 22 では 22.22.3 以降）、または [Bun](#bun) 1.4.3 以降が必要です。npm、pnpm、Plug'n'Play の有無を問わない Yarn、Bun のどのパッケージマネージャーでもインストールできます。Node.js 24.8 から 24.11.0 の Yarn Plug'n'Play では、`.cts` ファイルの読み込みに失敗します。Yarn のローダーが渡すソースを Node.js が拒否するためです。24.11.1 以降では読み込めます。
</Note>

## リファレンス

### ヘルプとバージョン

| オプション | 説明 |
| --- | --- |
| `-h`, `--help` | 直前のコマンドのヘルプを表示し、0 で終了します。`e2e help run` は `e2e run --help` と同じです。 |
| `-v`, `--version` | インストールされている `e2e` のバージョンを表示し、0 で終了します。 |

```console
$ npx e2e --version
0.14.0
```

- 出力はターミナルや CI では色付きになり、パイプ時や `NO_COLOR` が設定されているときはプレーンになります。`FORCE_COLOR` を設定すると色が維持されます。
- コマンドなしの `e2e` は stderr にヘルプを表示し、2 で終了します。
- 幅が 52 列以上のターミナルでは、`e2e --help` はブロック文字で描かれた e2e のロゴから始まります。パイプされた出力やそれより狭いターミナルでは、テキストのみが表示されます。
- npm に新しい `e2e` がある場合、ターミナルで実行したコマンドの最後に、そのバージョン、プロジェクトのパッケージマネージャー向けの [`e2e upgrade`](#e2e-upgrade) コマンド、GitHub で e2e にスターを付けるためのリンクが表示されます。レジストリの確認は 1 日 1 回です。CI、stderr がターミナルでない場合、`e2e mcp` と `e2e upgrade`、または `E2E_UPDATE_CHECK_DISABLED=1`、`NO_UPDATE_NOTIFIER=1`、`E2E_TELEMETRY_DISABLED=1`、`DO_NOT_TRACK=1` のいずれかが設定されている場合は何も表示されません。

#### `e2e init`

プロジェクトをスキャフォールドし、`devDependencies` に `e2e` を追加します。既存の設定ファイルとテストファイルはスキップします。

<CodeGroup>
```bash npm
npx e2e init --yes
npx e2e init --yes --gateway openrouter --skills .agents/skills --mcp .mcp.json --install
```

```bash pnpm
pnpm dlx e2e init --yes
pnpm dlx e2e init --yes --gateway openrouter --skills .agents/skills --mcp .mcp.json --install
```

```bash bun
bunx e2e init --yes
bunx e2e init --yes --gateway openrouter --skills .agents/skills --mcp .mcp.json --install
```
</CodeGroup>

| オプション | 説明 |
| --- | --- |
| `[directory]` | スキャフォールド先です。存在しない場合は作成されます。デフォルト: 作業ディレクトリ。 |
| `-y`, `--yes` | プロンプトをスキップします。フラグで指定されていない回答はそれぞれデフォルトになります: Web エンジン、Vercel AI Gateway、両方の場所へのスキルと MCP 設定、CI パイプラインなし、インストールなし。 |
| `--example <name>` | サンプルアプリから始めます: `with-vite`、`with-next`、`with-astro`、`with-angular`、`with-expo`、`with-swiftui`、`with-compose`、`with-kotlin-multiplatform`、`with-flutter`、`with-maui` のいずれかです。`with-` プレフィックスは省略できます。[サンプルから始める](#starting-from-an-example)を参照してください。 |
| `--engine <ids>` | 新しい設定のエンジン: `web`、`mobile`、または `none`。カンマ区切りまたは繰り返し指定します。`web,mobile` はそれぞれのターゲットを書き込みます。デフォルト: 質問されます。 |
| `--gateway <id>` | 新しい設定でエージェントステップに使うモデルゲートウェイ: `vercel`、`openrouter`、`openai-compatible`、`chatgpt`、`copilot`、`opencode-console`、`grok`、または `none`。デフォルト: 質問されます。 |
| `--endpoint <url>` | `--gateway openai-compatible` のベース URL で、指定するとそれも暗黙に指定されます。HTTPS、またはループバックホストでの HTTP です。デフォルト: 質問されます。`--yes` では `http://127.0.0.1:11434/v1`。 |
| `--skills <dirs>` | エージェントスキルのインストール先: `.agents/skills`、`.claude/skills`、または `none`。カンマ区切りまたは繰り返し指定します。デフォルト: 質問されます。 |
| `--mcp <files>` | MCP サーバーの登録先: `.mcp.json`、`.cursor/mcp.json`、`.codex/config.toml`、または `none`。カンマ区切りまたは繰り返し指定します。デフォルト: 質問されます。 |
| `--ci <id>` | テスト用の CI パイプラインで、プラットフォームごとに 1 つのジョブを持ちます: `github-actions`、`gitlab`、または `none`。[CI パイプライン](#ci-pipeline)を参照してください。デフォルト: 質問されます。`--yes` では `none`。 |
| `--install`, `--no-install` | 依存関係をインストールするかどうか。デフォルト: 質問されます。`--yes` では `--no-install`。 |

- フラグはその質問に答え、そのプロンプトをスキップします。
- `--engine`、`--gateway`、`--endpoint` は新しい設定にのみ適用されます。`--example` と併用すると使用法エラーになります。

| 終了コード | 条件 |
| --- | --- |
| 0 | スキャフォールドが完了したか、ウィザードがキャンセルされました。キャンセルするとファイルは変更されず、コピーされたサンプルは削除されます。 |
| 2 | 不明なフラグ値。書き込み前に終了し、有効な値を一覧表示します。 |
| 2 | 不正な `package.json`。書き込み前に終了します。 |
| 2 | stdin と stdout にターミナルがなく、`--yes` もありません。メッセージにはそのフラグが示されます。 |
| 2 | ファイルのあるディレクトリに `--example` を指定したか、サンプルのダウンロードに失敗しました。何も残りません。 |
| 2 | 依存関係のインストールに失敗しました。 |
| 130 | ロゴの描画中やサンプルのダウンロード中の Ctrl-C または SIGTERM、あるいは依存関係のインストール中の SIGINT。部分的なサンプルは削除されます。 |

##### プロンプト

幅が 52 列以上のターミナルでは、ウィザードは e2e のロゴから始まります。ロゴは上の行から順に ░ から █ へと約 0.5 秒で濃くなっていきます。`--yes` 指定時、CI、dumb ターミナル、または 7 行未満のターミナルでは、一度に表示されます。パイプされた出力やそれより狭いターミナルでは表示されません。

CI の外のターミナルでは、スキャフォールドの完了後に GitHub で e2e にスターを付けるためのリンクが表示されます。ただし、init が起動元のコマンドにそのまま進む場合は表示されません。

新しいプロジェクトでは、ウィザードは次の項目を尋ねます。

- **エンジン。** 1 つ、両方、またはなしを選択します。**Web**（Playwright、デフォルト）は `@e2e-dev/web` を追加します。**Mobile (iOS/Android)** は `@e2e-dev/mobile` を追加し、デフォルトで macOS では iOS、それ以外では Android を使い、設定アプリを開きます。なしを選ぶとエンジンは追加されず、HTTP テストや独自のエンジン向けになります。
- **エージェントステップ用のモデルプロバイダーまたはサブスクリプション:** Vercel AI Gateway、OpenRouter、OpenAI 互換エンドポイント、ChatGPT、GitHub Copilot、OpenCode Console、SuperGrok のいずれかです。なしはロケーターのみを使うテスト向けです。ウィザードは必要なパッケージとモデル設定を追加します。サブスクリプションのユーザーはその後 [`e2e login`](#e2e-login) でサインインします。[モデル](/models)と[サブスクリプション](/subscriptions)を参照してください。
- **エージェントスキルのインストール先**（[e2e guide](#e2e-guide) を参照）。`.agents/skills/` は Codex、Cursor、Copilot、Gemini CLI、OpenCode、Zed に対応し、`.claude/skills/` は Claude Code に対応します。どちらも事前に選択されています。
- **[MCP サーバー](/reference/mcp)の登録先。** Claude Code には `.mcp.json`、Cursor には `.cursor/mcp.json`、Codex には `.codex/config.toml` です。すべて事前に選択されています。Codex は信頼済みプロジェクトで設定を読み込みます。依存関係をインストールした後に新しいセッションを開始してください。
- Web または mobile エンジンを持つプロジェクト向けの **CI パイプライン**: GitHub Actions または GitLab CI/CD で、プラットフォームごとにジョブを持ちます。ウィザードは、リポジトリのリモート、`.github/` フォルダー、または `.gitlab-ci.yml` が示すサービスを事前に選択します。[CI パイプライン](#ci-pipeline)を参照してください。

ファイルの変更を確認すると、ウィザードは選択した依存関係をインストールするかどうかを尋ねます。インストーラーはプロジェクトの `packageManager` フィールドまたはロックファイル、次に呼び出し元のパッケージマネージャー、最後に npm の順に従います。

##### ファイル

| 作成されるファイル | 内容 |
| --- | --- |
| `package.json` | 存在しない場合はプライベートな ESM パッケージとして作成されます。存在する場合は、不足している依存関係とスクリプトのみが追加されます。兄弟パッケージ（`@e2e-dev/web`、`@e2e-dev/mobile`）には、CLI と同時にリリースされたバージョンのキャレット範囲が、CLI がプレリリースの場合はそのバージョンそのものが指定されます。`e2e run` を実行する `test:e2e` スクリプトを、存在しなければ追加します |
| `e2e.config.ts` | 選択したエンジンごとに 1 つのターゲットがあり、その `app` にアプリが設定されます。Playwright は `APP_URL`（デフォルト `http://localhost:3000`）を `app.url` に読み込み、`app.command` をコメントで示します。Mobile は iOS では `app: { bundleId: 'Settings' }`、Android では `com.android.settings` を設定し、`workers: 1` を設定します。ゲートウェイがある場合、`agents.default` は `{ model, system }` です |
| `tests/example.e2e.ts` | どのページに対しても成功するアプリ起動テストと、コメントアウトされたエージェントテストです。デバイスのセットアップでは代わりに設定アプリのチェックになります。両方のエンジンを選んだ場合は代わりに `tests/web.e2e.ts` と `tests/mobile.e2e.ts` が作られ、各テストに `requires: ['browser']` または `requires: ['device']` が付くので、もう一方のターゲットではスキップされます |
| `.gitignore` | `node_modules/`、`.e2e/results/`、`.e2e/cache/`、`.e2e/sessions/`、`.e2e/report.json`、`.e2e/ai-trace.json`、`.e2e/timings.json`、`.e2e/junit.xml`、`.e2e/summary.md`、`.e2e/logs/`、`.e2e/videos/` を追記します。キャッシュのコミットはオプトインです。[リプレイキャッシュをコミットする](/cache#commit-the-replay-cache)を参照してください |
| `.agents/skills/e2e/`, `.claude/skills/e2e/` | `SKILL.md` と、`e2e guide` のトピックごとに 1 つの `references/<topic>.md` です。両方を選んだ場合、Claude Code のディレクトリはコピーへの相対シンボリックリンク（`../../.agents/skills/e2e`）になります。これは `npx skills add` が作る構成と同じです |
| `.mcp.json`, `.cursor/mcp.json`, `.codex/config.toml` | 他のサーバーを変更せずに `e2e mcp` を登録します |
| `.github/workflows/e2e.yml`, `.gitlab-ci.yml` | `--ci` 指定時: ターゲットが実行される各プラットフォームのジョブです。サブフォルダー内のプロジェクトでも、リポジトリのルートに作成されます。[CI パイプライン](#ci-pipeline)を参照してください |

<a id="ci-pipeline" />
##### CI パイプライン

`--ci github-actions` または `--ci gitlab` は、設定のターゲットが実行される各プラットフォーム（Web、iOS、Android）につき 1 つのジョブを持つパイプラインを書き込みます。Web と mobile の両方のターゲットを持つ設定では、すべてのジョブが 1 つのファイルにまとめられます。各ジョブは依存関係をインストールし、`e2e run --target <its targets> --reporter
list,junit` を実行して、`.e2e/report.json`、`.e2e/junit.xml`、`.e2e/results/` を保存します。

<CodeGroup>
```bash npm
npx e2e init --yes --ci gitlab
```

```bash pnpm
pnpm dlx e2e init --yes --ci gitlab
```

```bash bun
bunx e2e init --yes --ci gitlab
```
</CodeGroup>

| ジョブ | GitHub Actions | GitLab CI/CD |
| --- | --- | --- |
| Web | `ubuntu-latest`、Chromium 付き | GitLab のランナー上の `node` イメージ、Chromium 付き |
| iOS | `macos-26`: アプリをビルドし、固定された iOS ランタイムでイメージの iPhone 17 Pro を起動して、アプリをインストールします | セルフマネージドの Mac: 固定されたランタイムで独自のシミュレーターを作成します |
| Android | KVM 付きの `ubuntu-latest`: リリース APK をビルドし、API 36 のエミュレーターで実行します | KVM 付きのセルフマネージド Linux ランナー: `e2e` という名前の AVD を起動します |

| サービス | ファイル | 実行タイミング | モデルキー |
| --- | --- | --- | --- |
| GitHub Actions | `.github/workflows/e2e.yml` | プルリクエストと `main` への push 時 | リポジトリのシークレット。実行ステップの `env` で渡されます |
| GitLab CI/CD | `.gitlab-ci.yml` | マージリクエストのパイプラインとデフォルトブランチ。JUnit レポートはマージリクエストに表示されます | CI/CD 変数。GitLab がジョブに渡します |

- `init` は、変更を確認しインストールが終わった後に、自身が書き込んだ新しい設定から、または `e2e run` と同じ方法で既存の設定を読み込んでターゲットを読み取ります。既存の設定がそれでも読み込めない場合、`init` はその理由を示し、`package.json` にフォールバックします。Web エンジンのみの場合は 1 つの Web ジョブがすべてのターゲットを実行し、mobile エンジンがある場合はパイプラインは作られません。
- Web ジョブは iOS でも Android でもないすべてのターゲット（HTTP テストを含む）を実行し、設定に mobile ターゲットがない場合はすべてのターゲットを実行します。
- mobile のジョブはアプリをビルドします。Expo アプリは `expo run:ios`、および `expo prebuild` と Gradle でビルドします。素の React Native アプリは `ios/*.xcworkspace` を `xcodebuild` で（`Gemfile` があれば Bundler 経由で）ビルドし、`android/gradlew` を実行します。それ以外のアプリには、置き換えるまで失敗するビルドステップが入り、`init` が編集すべきファイルを示します。
- mobile のジョブは、起動したデバイスの名前を `E2E_DEVICE` に設定します。デバイスを指定するターゲットは `mobile()` 内で `device: process.env.E2E_DEVICE` としてそれを読み取るので、そのデバイスで実行されます。デバイスを指定しないターゲットは起動中のデバイスを操作します。
- GitLab のホスト型ランナーではシミュレーターやエミュレーターを実行できないため、mobile のジョブにはセルフマネージドのランナーが必要です。その `tags` を設定してください。[GitLab CI/CD](/ci/gitlab#ios-and-android) を参照してください。
- ファイルは、パッケージが `templates/ci/` に同梱しているテンプレートから作られます。テンプレートは、リポジトリのルートで npm と Expo アプリを使う完全なパイプラインです。`init` はそれをプロジェクトに合わせて埋め、コメントは残します。
- ジョブはプロジェクトのパッケージマネージャーと、`.nvmrc` または `.node-version` の Node バージョン（ない場合は 24）を使います。GitHub はファイルを読むので、正確なバージョンが使われます。GitLab は、ファイルのメジャーバージョンの `node` イメージで Web ジョブを実行します。`22.22.3` なら `node:22` です。GitHub Actions のアクションはコミットで固定されます。
- `init` は追加すべきシークレットまたは変数（`AI_GATEWAY_API_KEY` など）を、それを追加する `gh` または `glab` コマンドとともに示します。
- サブフォルダー内のプロジェクトでは、ファイルはリポジトリのルートに置かれ、ジョブはサブフォルダー内で実行されます。
- 設定に `app.command` がない場合、ランナー上でアプリを起動するものが他にないため、`init` は警告します。また、サインインがあなたのマシンに残るサブスクリプションのゲートウェイや、あなたのマシン上を指す OpenAI 互換の `baseURL` についても警告します。どちらの場合も CI ではエージェントステップが失敗します。
- 既存のパイプラインファイルは変更されません。既存の `.gitlab-ci.yml` がある場合、`init` は `.gitlab/e2e.gitlab-ci.yml` を書き込み、追加すべき `include:` の行を表示します。ジョブは `test` ステージで実行され、`stages:` にそれが含まれていない場合は `init` がそう伝えます。同じ名前のジョブ（`e2e-web`、`e2e-ios`、`e2e-android`）がある場合、すべてのジョブ名に `-run` が付きます。
- `init` はシンボリックリンクになっている `.github` や `.gitlab` フォルダーを通して書き込むことはありません。警告を出し、何も書き込みません。
- すでに `e2e run` を実行しているワークフローや `.gitlab-ci.yml` には何も追加されません。Web や mobile エンジンを持たないプロジェクトも同様です。

<a id="starting-from-an-example" />
##### サンプルから始める

`--example` は[サンプルアプリ](https://github.com/e2e-inc/e2e/tree/main/examples)の 1 つを新規または空のディレクトリにコピーし、その e2e プロジェクトでウィザードを実行します。e2e プロジェクトは、Web アプリや Expo アプリではディレクトリそのもの、ネイティブアプリではその `e2e/` フォルダーです。

<CodeGroup>

- CLI は GitHub から、実行中の CLI の `e2e@<version>` タグのサンプルをダウンロードします。そのタグが存在しない場合は `main` を使い、警告します。
- `.git`、`.DS_Store`、`Thumbs.db` のみを含むディレクトリは空とみなされます。
- サンプルの設定、テスト、スクリプトはそのまま残ります。ウィザードはスキル、MCP サーバー、インストールについてのみ尋ね、不足している `.gitignore` のエントリーを追加します。ネイティブアプリではこれらのファイルは `e2e/` に置かれるので、コーディングエージェントはそこで開いてください。
- e2e プロジェクトの `package.json` はディレクトリの名前を取ります（ネイティブアプリの横では `-e2e` が付きます）。`e2e`、`@e2e-dev/web`、`@e2e-dev/mobile` には、`init` が新しいプロジェクトに書き込むのと同じ範囲が指定されます。
- 最後の `Next:` 行にはサンプルのテストスクリプトが示されます。ネイティブアプリでは先にビルドが必要です。その方法は `README.md` に書かれています。

##### init の再実行

- 既存の設定と既存のテストファイルは 1 バイトも変更されません。エンジンとゲートウェイの回答は新しい設定にのみ適用されるため、それらのパッケージは追加されません。不足しているサンプルテストは、エンジンごとのサンプルが存在しない限り作成されます。
- `package.json` と `.gitignore` には、不足しているもの（`e2e` の dev 依存関係、`test:e2e` スクリプト、ignore エントリー）が引き続き追加されます。既存の依存関係、スクリプト、エントリーはそのまま残ります。
- MCP の登録では、起動コマンドを修復する場合でも、e2e サーバーの追加設定（環境変数やクライアントのタイムアウトなど）が維持されます。最新の登録は 1 バイトも変更されません。
- スキルディレクトリが存在すると、以降の実行ではインストール済みのバージョンと異なるコピーが更新されます。プロジェクトが選択しなかったディレクトリが追加されることはありません。`--skills` と `--mcp` は代わりに正確な場所を指定し、それ以外はそのままにします。
- 以前のバージョンの `.claude/skills/e2e/` のコピーは、同梱ファイルのみを含む場合はシンボリックリンクになります。他のファイルを含むコピーはコピーのまま更新されます。
- `init` は、別の場所へのシンボリックリンクになっているスキルディレクトリや、その配下を通して書き込むことはありません。`--yes` では、リンクとそのターゲットを示す警告を出してスキップします。対話的な実行では、コピーで置き換えるか、リンク先にリンクで置き換えるかを提案します。
- ファイルがあるべき場所にディレクトリがある、またはディレクトリがあるべき場所にファイルがあるコピーは、そのエントリーを示す警告とともにスキップされます。`init` は修復のために何かを削除することはありません。
- シンボリックリンク経由、またはリンクされたディレクトリ配下にある MCP 設定ファイルは、同じ警告とともにスキップされ変更されないため、そこにはサーバーが登録されません。通常の設定ファイルはいつもどおりマージされます。

#### `e2e login`

サブスクリプションにサインインし、認証情報を `$XDG_CONFIG_HOME/e2e/oauth.json`（デフォルトでは `~/.config/e2e/oauth.json`）に保存します。モデルの設定については[サブスクリプション](/subscriptions)を参照してください。

<CodeGroup>
```bash npm
npx e2e login openai              # ChatGPT, browser sign-in
npx e2e login openai --device     # sign in with a device code
npx e2e login github-copilot --from-gh  # use your GitHub CLI login
npx e2e login github-copilot --client-id <id> [--enterprise-url <host>]
npx e2e login opencode-console    # OpenCode Console, device code
npx e2e login spacexai            # SuperGrok, device code
npx e2e login                     # choose a provider
```

```bash pnpm
pnpm exec e2e login openai              # ChatGPT, browser sign-in
pnpm exec e2e login openai --device     # sign in with a device code
pnpm exec e2e login github-copilot --from-gh  # use your GitHub CLI login
pnpm exec e2e login github-copilot --client-id <id> [--enterprise-url <host>]
pnpm exec e2e login opencode-console    # OpenCode Console, device code
pnpm exec e2e login spacexai            # SuperGrok, device code
pnpm exec e2e login                     # choose a provider
```

```bash bun
bunx e2e login openai              # ChatGPT, browser sign-in
bunx e2e login openai --device     # sign in with a device code
bunx e2e login github-copilot --from-gh  # use your GitHub CLI login
bunx e2e login github-copilot --client-id <id> [--enterprise-url <host>]
bunx e2e login opencode-console    # OpenCode Console, device code
bunx e2e login spacexai            # SuperGrok, device code
bunx e2e login                     # choose a provider
```
</CodeGroup>

| オプション | 説明 |
| --- | --- |
| `[provider]` | サブスクリプション: `openai`、`github-copilot`、`opencode-console`、または `spacexai`。デフォルト: 選択画面。 |
| `--device` | ChatGPT: ブラウザを開く代わりに、別のデバイスで入力するコードを表示します。 |
| `--from-gh` | GitHub Copilot: サインイン済みの GitHub CLI のトークンを再利用します。 |
| `--client-id <id>` | GitHub Copilot: デバイスフローを有効にした GitHub OAuth App のクライアント ID。 |
| `--enterprise-url <host>` | GitHub Copilot: GitHub Enterprise のホスト。 |

| 終了コード | 条件 |
| --- | --- |
| 1 | サインインに失敗しました。 |
| 2 | 不明なプロバイダー。 |
| 130 | サインインがキャンセルされました。 |

保存されたログインで利用できるモデルをベンダーに問い合わせ、モデルごとに 1 行を表示します。OpenCode Console では、`OPENCODE_API_KEY` が設定されていればそれを使って問い合わせます。


```bash pnpm

pnpm exec e2e models openai    # one provider
```

```bash bun
bunx e2e models           # every stored login
bunx e2e models openai    # one provider
```
</CodeGroup>

| オプション | 説明 |
| --- | --- |
| `[provider]` | `openai`、`github-copilot`、`opencode-console`、または `spacexai`。デフォルト: 保存されたすべてのログインと、`OPENCODE_API_KEY` のみが設定されている場合は OpenCode Console。 |

各行には次の内容が含まれます。

- `chatgpt()`、`copilot()`、`opencodeConsole()`、または `grok()` が受け取る ID
- ベンダーによるモデル名
- 注記: 推論レベル、ビジョン、プレビュー、非表示。Copilot では `copilot()` が呼び出せない場合に `not enabled` または `no chat or responses`。OpenCode Console では、そのモデルを提供するプラン（Zen または Go）

Copilot アカウントが一覧のモデルを使えるかどうかは、実際に呼び出すまでわかりません。

| 終了コード | 条件 |
| --- | --- |
| 1 | 認証情報がない、または指定したプロバイダーの認証情報がありません。メッセージにはサインインコマンドが示されます。 |
| 1 | 複数のログインのうち 1 つの一覧取得に失敗しました。他のログインは引き続き表示されます。 |
| 2 | 不明なプロバイダー。 |

[モデルを選ぶ](/subscriptions#pick-a-model)を参照してください。

<a id="positional-arguments" />

##### 位置引数

```bash
e2e run [files...]
```

プロジェクトルートからの相対パスで指定するテストファイル、ディレクトリ、または glob です。

| 位置引数 | 選択されるもの |
| --- | --- |
| ファイルパス（`tests/signup.e2e.ts`） | そのファイル。 |
| ディレクトリ（`tests/agent`、`.`） | その配下で検出されたすべてのテストファイル。 |
| 単純な名前（`signup.e2e.ts`、`agent/signup.e2e.ts`、`signup`） | パスがセグメント境界でその名前で終わる、検出されたすべてのファイル。最初の 2 つはどちらも `tests/agent/signup.e2e.ts` を選択します。`/` も `.` も含まない場合は拡張子を除いたファイル名と照合されるため、`signup` でも同じファイルが選択されます。 |
| これらのいずれかに `:line` を付けたもの（`tests/signup.e2e.ts:12`、`signup:12`） | 指定した各ファイルのその行で宣言されたテストのみ。その行とは、エディターやレポートの `source` に表示される、`test(` 呼び出しが始まる行です。 |
| 引用符で囲んだ glob（`'tests/**/*.smoke.e2e.ts'`） | 一致する、検出されたすべてのファイル。文法は設定の `tests` の glob と同じで、`*`、`?`、および `**` のセグメント全体が使えます。 |

- **行。** serial グループの 1 つのメンバーを指す行を指定すると、グループ全体が実行されます。1 つのファイルに複数の行を指定すると合算されます。行を付けずにファイルを指定すると、ファイル全体が選択されます。指定した行でテストが宣言されていない場合、`NO_TESTS` はその位置引数と、そのファイルでテストが宣言されている行を示します。ディスク上に書かれたとおりに存在する位置引数は、`:12` で終わっていてもパスとして扱われます。
- **glob。** 波括弧、文字クラス、extglob は、何にも一致しないパターンではなく、ヒント付きの `INVALID_GLOB` になります。展開は行われないので、候補ごとに 1 つの glob を指定してください。`./`、`..`、末尾の `/`、プロジェクト内の絶対パスは、他の位置引数のパスと同様に解決されます。既存のファイルやディレクトリは、名前にどんな文字が含まれていてもそのパスで選択されます。
- 位置引数は設定の glob と、タグ、プラットフォーム、ケイパビリティのフィルターを絞り込むだけで、それらを回避することはありません。名前と glob はどの OS でも大文字と小文字を区別します。プロジェクトルート外のパスは `COLLECTION_ERROR` になります。
- ランナーは、一部のテストだけを選択した場合でも、検出されたすべてのテストファイルをインポートします。これにより、選択したテストは別のファイルにあるセッションのセットアップを見つけられます。その他の通常のテストは選択されないままです。コレクションエラーは、選択したファイル内にある場合、または位置引数のない実行ではどのファイルにある場合でも、実行を失敗させます。位置引数で除外されたファイルがインポートやテストの登録に失敗した場合は、通知を出してスキップされます。そのため、別の場所に書きかけのファイルがあっても `npx e2e run tests/login.e2e.ts` は止まりません。その後、選択したテストのセッションにセットアップテストがない場合、エラーはそのファイルをセットアップがある可能性のある場所として示します。
- `-` で始まり、どのファイルも指さない位置引数は使用法エラーで、2 で終了します。`pnpm test:e2e -- --headed` はこのエラーになります。`--` が e2e に届き、そうでなければ `--headed` をファイルとして扱ってしまうためです。メッセージには直接の形式 `pnpm exec e2e run --headed` が示されます。npm では `npm exec -- e2e run --headed` です。npm がフラグを渡すには、バイナリの前に区切りが必要です。
- 実行するものが何も残らない場合、`NO_TESTS` は原因を示します: glob に一致するファイルがない（`tests/login.test.ts` のような似た名前のファイルも示します）、位置引数が何にも一致しない（最も近いパスも示します）、一致したファイルがテストを登録していない、またはすべてのテストがフィルターで除外された、のいずれかです。

<a id="flags" />

##### フラグ

**選択**

| オプション | 説明 |
| --- | --- |
| `--config <path>` | 明示的な設定のパス。デフォルト: 最も近い `e2e.config.ts`、`.mts`、`.js`、または `.mjs`（[読み込み](/reference/config#loading)を参照）。ファイルが存在しない場合は `CONFIG_NOT_FOUND` です。 |
| `--target <ids>` | 名前で指定するターゲット。カンマ区切りまたは繰り返し指定します。デフォルト: 設定されたすべてのターゲット。選択されたターゲットのアプリコマンドのみが起動します。不明な ID は `UNKNOWN_TARGET` です。 |
| `--tag <tags>` | 指定したタグを持つテストのみ。カンマ区切りまたは繰り返し指定します。いずれかのタグ、または `--tag-mode all` ではすべてのタグを持つテストです。 |
| `--tag-mode <mode>` | 複数のタグの組み合わせ方: `any` または `all`。デフォルト: `any`。 |
| `--exclude-tag <tags>` | 指定したタグのいずれかを持つテストを、`--tag` や位置引数で選択されたかどうかにかかわらず除外します。カンマ区切りまたは繰り返し指定します。serial グループは、いずれかのメンバーが選択されていれば引き続き全体が実行されます。フロー全体を除外するには、serial の `describe` にタグを付けてください。 |
| `--grep <pattern>` | タイトルがいずれかの正規表現に一致するテストのみ。繰り返し指定できます。タイトルは describe のタイトルとテストのタイトルを 1 つのスペースで連結したもの（`checkout pays`）で、ファイルやタグは含みません。そのままのパターンは大文字と小文字を区別します。`'/pattern/i'` でフラグを追加できます。コンパイルできないパターンは使用法エラーで、2 で終了します。 |
| `--grep-invert <pattern>` | タイトルがいずれかの正規表現に一致するテストを除外します。繰り返し指定でき、照合するテキストと形式は `--grep` と同じです。両方を指定すると、`--grep` に一致するものから `--grep-invert` に一致するものを除いたテストが残ります。 |
| `--changed-since <ref>` | ref 以降の変更に対して、設定された[テストフィルター](/filters)を実行します。変更とは、ref と `HEAD` のマージベースから差分のあるすべてのファイルで、未コミットや未追跡のファイルも含みます。各ターゲットは、フィルターが最も可能性が高いと評価したテストのファイルから開始します。指定しない場合、フィルターは実行されません。フィルターが設定されていない場合は、すべてのテストが実行されるという警告が出ます。 |
| `--last-failed` | 前回の実行で成功しなかったテストのみ。どのテストが対象かは、これらの表の後のリストを参照してください。 |
| `--shard <index/total>` | 選択したテストの連続した一部（`2/3` など）を実行します。分割は他のすべてのフラグを適用した後に行われます。各シャードのテスト数の差は最大 1 です。serial グループは 1 つとして数えられ、分割されることはありません。各シャードは、自身のテストが必要とするセットアップテストのみを持ち込みます。スキップされたテストは分割の対象外です。その直前に最も近いテストを実行するシャード、なければ最初のシャードが報告するので、報告するのは 1 つのシャードだけです。すべてのシャードは、インデックスだけが異なる同じコマンドを実行します。順序はレポートの順序なので、スイートはどのマシンでも同じように分割されます。テストのないシャードは、`--pass-with-no-tests` がなければ `NO_TESTS` です。[シャーディング](/ci#sharding)を参照してください。 |
| `--pass-with-no-tests` | 何も選択されない場合、`NO_TESTS` ではなく 0 で終了します。実行するもののない実行では、エンジンを準備せず、アプリやサービスのコマンドも起動しません。 |

**実行**

| オプション | 説明 |
| --- | --- |
| `--headed` | エンジンが対応している場合、UI を表示します。 |
| `--agent <names>` | 固定されていないテストを、選択したエージェントごとに 1 回ずつ実行します。カンマ区切りまたは繰り返し指定します。デフォルト: `default`。`{ agent }` を持つテストでは、名前が重なる場合は共通の名前を選択し、そうでなければテスト自身のものを維持します。不明な名前は `INVALID_CONFIG` です。 |
| `--retries <n>` | `config.retries` を置き換えます。0〜10 の整数。デフォルト: 設定。 |
| `--workers <n>` | `config.workers` を置き換えます。1〜1024 の整数。デフォルト: 設定。 |
| `--action-timeout <ms>` | この実行の [`actionTimeout`](/reference/config#actiontimeout) を置き換えます。1〜2147483647 の整数で、それ以外は使用法エラーとなり 2 で終了します。デフォルト: 設定、なければ `30000`。呼び出し自身の `timeout` が引き続き優先されます。テストを書いている間は、`5000` のような小さな値にすると、間違ったロケーターが 30 秒ではなく 5 秒後に `LOCATOR_NOT_FOUND` で失敗します。 |
| `--assertion-timeout <ms>` | この実行の [`assertionTimeout`](/reference/config#assertiontimeout) を置き換えます。1〜2147483647 の整数で、それ以外は使用法エラーとなり 2 で終了します。デフォルト: 設定、なければ `5000`。マッチャー自身の `timeout` が引き続き優先されます。 |
| `--max-failures <n>` | この数（1 以上）のテストが失敗またはタイムアウトした時点で実行を停止します。それ以上はディスパッチされず、他のワーカーで実行中のテストは `interrupted` で終わります。開始されていないテスト（上限に達したテストのファイルの残りを含む）は、原因 `failure-limit`、理由 `run stopped after 3 failures (--max-failures 3)` でスキップされます。終了コードは 130 ではなく、失敗そのもののコードである 1 です。 |
| `--max-duration <ms>` | 1 回の実行について [`maxDuration`](/reference/config#maxduration) を上書きします。1〜2147483647 の整数。デフォルト: 設定。終了コードは 130 ではなく 1 です。 |
| `--repeat-each <n>` | 選択したすべてのテストをこの回数（1 以上）実行します。デフォルト: `1`。各実行はそれぞれ独立した結果で、`repeat` は 0 から `n - 1`、`id` もそれぞれ異なります。list レポーターは 2 回目以降の実行に `(repeat #1)`、`(repeat #2)` というタイトルを付け、その成果物を `repeat-<n>` ディレクトリの下に置きます。セットアップテストは 1 回だけ実行されます。リプレイキャッシュがオンの場合、最初の実行で記録し、残りはリプレイします。毎回モデルを呼び出すには `--no-cache` を追加してください。`list` のサマリーには `Repeats` 行（`1 of 2 tests passed all 5 runs`）と、すべての実行で成功しなかったテストごとに失敗した実行を示す 1 行が追加されます。`markdown` のページにも同じ集計があります。 |
| `--no-cache` | `config.cache` の設定にかかわらず、この実行のリプレイキャッシュをオフにします。 |
| `--strict-cache` | この実行で `cache.strict` をオンにします。記録が存在するのにリプレイできなくなったステップは、エージェントに引き継がずに `REPLAY_STALE` で失敗します。リトライもリプレイし、実行がキャッシュに書き込むことはありません。[古くなった記録で失敗させる](/cache#fail-on-a-stale-recording)を参照してください。 |
| `-u`, `--update-snapshots` | [`toHaveScreenshot`](/reference/expect#screenshot-matchers) が見つからない、または異なると判断した保存済みスクリーンショットをそれぞれ書き込み、マッチャーを成功させます。指定しない場合、見つからないスクリーンショットは書き込まれたうえで失敗します。CI では結果に添付されるだけです。 |
| `-w`, `--watch` | 実行した後、テストファイルや設定が変更されたとき、またはキー入力で再実行します。[ウォッチモード](#watch-mode)を参照してください。 |
| `--step` | 最初のステップを実行し、以降の各ステップはプロンプトでキーが押されるまで待機します。Enter でそのステップを実行し、`n` でテストの残り、`a` で実行の残りを実行し、`h` でキーの一覧を表示し、`q` で停止して 130 で終了します。待機している時間はどのタイムアウトにも数えられません。ターミナルがない場合、実行はバックグラウンドで続き、各コマンドは次の待機中のステップでその画面とともに戻ります。`--step next` でそのステップを実行し、`--step rest` で残りを実行し、`--step stop` で実行を終了します。ワーカー 1 つで実行されます。CI、`--watch`、1 を超える `--workers`、json レポーターとの併用は拒否されます（2 で終了）。[テストをステップ実行する](/debugging#step-through-a-test)と[ターミナルなしで](/debugging#step-through-a-test-without-a-terminal)を参照してください。 |

**出力**

| オプション | 説明 |
| --- | --- |
| `--reporter <ids>` | `config.reporters` の組み込み ID を置き換えます。カンマ区切りで `list`、`json`、`junit`、`markdown`。デフォルト: 設定。`json` と `list` の併用は `INVALID_CONFIG` です。設定内の[レポーターオブジェクト](/reference/reporters)は引き続き実行されます。 |
| `--output <dir>` | この実行の結果ディレクトリで、設定の [`output`](/reference/config#output) より優先されます。レポート、レポーターのファイル、AI トレース、`results/`、`sessions/` が置かれます。デフォルト: 設定、なければ `.e2e`。プロジェクトルートから解決され、ルート自体ではなくその内側のディレクトリである必要があります。それに違反する場合や、実行が所有できないその他のディレクトリ（そこに列挙されています）は `INVALID_CONFIG` です。`results/` はテストの開始時にクリアされます。`--last-failed` の再実行では、前回のレポートが示すものは残されます。 |
| `--cache-dir <dir>` | この実行のリプレイキャッシュディレクトリで、[`E2E_CACHE_DIR`](/reference/environment#replay-cache) や [`cache.dir`](/reference/config#cache) より優先されます。デフォルト: `E2E_CACHE_DIR`、なければ `cache.dir`、なければ `.e2e/cache`。プロジェクトルートから解決されます。`~` または先頭の `~/` はホームディレクトリです。キャッシュモードは設定どおりのままです。カスタムの `cache.store` と併用すると `INVALID_CONFIG` です。 |
| `--timings <file>` | 実行終了時に更新する[タイミング履歴](/ci#cache-the-timings-history)で、`<output>/timings.json` より優先されます。ワーカーが複数ある場合、記録された時間のないファイルを最初に、残りを長い順に開始します。プロジェクトルートから解決されます。ファイルが存在しない、または不正な場合は履歴なしとして扱われ、エラーにはなりません。 |
| `--debug` | 実行後に stderr へフェーズのタイミングとエージェントステップの表を出力します。[デバッグ出力](#debug-output)を参照してください。 |
| `--ai-trace` | すべてのモデル呼び出しを `<output>/ai-trace.json` に記録します。[出力](#output)を参照してください。 |
| `--trace [mode]` | どのテストがトレースページ（`<output>/results/<test>/trace.md`）を保持するか: `off`、`on`、`retain-on-failure`、`on-first-retry`、または `on-all-retries`。デフォルト: 設定。`--trace off` では、独自の `trace` を持たないテストのトレースページは書き込まれません。[trace](/reference/config#trace) を参照してください。 |
| `--video [mode]` | どの試行で動画（ブラウザエンジンでは WebM、デバイスエンジンでは MP4）を記録するか。モードは `--trace` と同じです。デフォルト: 設定。記録できるエンジンのターゲットのみが動画を得ます。それ以外のターゲットは、実行が 1 つの通知でまとめて示します。[video](/reference/config#video) を参照してください。 |

`--trace` と `--video` は、設定と各ターゲットの値より優先されます。テスト自身の `trace` や `video` が引き続き最優先です。値なしのフラグは `on` です。値なしの `--trace` は、すべてのテストのページを保持します。値は省略可能で貪欲に解釈されます。`--trace tests/a.e2e.ts` はファイルをモードとして読み取り、失敗します。`--trace=<mode>` と書くか、テストファイルをフラグの前に置いてください。

削除された `--artifacts <dir>` は、対応する `--output` を示して失敗します。`--artifacts out/artifacts` は `--output out` で、親がプロジェクトルートであるかその外側にあるディレクトリは `--output .e2e` に対応します。

`--last-failed` は、前回の実行で成功しなかったテストを選択します。それらは、この実行が上書きする `report.json`、つまり `<output>/report.json`（`--output`、なければ設定の [`output`](/reference/config#output)）から読み取られます。

- 失敗した、タイムアウトした、または中断されたテスト。
- セットアップ、serial の先行テスト、フック、またはワーカーが失敗したため、あるいは `--max-failures` や `--max-duration` が先に実行を停止したためにスキップされたテスト。
- 失敗した `beforeAll` または `afterAll` が、そのターゲットで、その describe またはファイル内で選択していたすべてのテスト。セットアップの場合は、そのセッションを使用するテスト。フックを再度実行する再実行は、まだ失敗する場合は再びそれを報告します。そのスコープ内のいずれかのテストを失敗なく実行した再実行で、それは解決されます。
- 別のフィルター（`--grep`、`--tag`、`--target`、`--agent`、位置引数）が再実行から除外したテストは、未解決のまま残ります。再実行のレポートは、その最後の結果と、それをスコープに含むフックの失敗を `run.carried` の下に引き継ぎます。次の `--last-failed` はそれを再び選択し、[`@e2e-dev/github`](/github) のページは成功するまで赤いままです（前の実行で中断されたテストは ⏹️）。再実行自身の終了コードとサマリーは、実際に実行したものだけを数えます。
- 再実行は前回のレポートが示す成果物を残し、自身の成果物は各テストの `rerun-<n>/` の下に書き込むので、どの試行も以前の試行のファイルを上書きしません。
- テストはターゲットとエージェントごとに特定されます。
- レポートがない場合は `NO_LAST_RUN` です。前回の実行で何も失敗していない場合は何も選択されず、`--pass-with-no-tests` がなければ `NO_TESTS` になります。

範囲外の `--retries` と `--workers` は、設定値の場合と同様に、何かが始まる前に `INVALID_CONFIG` で失敗します。`--target`、`--tag`、`--exclude-tag`、`--agent` は各名前を 1 回ずつ受け付けます。空の値（`--tag ''`、または変数が未設定の `--tag "$TAGS"`）は使用法エラーで 2 で終了し、選択範囲が広がることはありません。空の `--reporter` も同じ使用法エラーで、レポーターなしの実行にはなりません。

フィルターは絞り込むだけで、それぞれ前のフィルターの後に適用されます: 位置引数、次に `.only`、`--tag`、`--exclude-tag`、`--grep`、`--grep-invert`、`--last-failed`、次にプラットフォームとケイパビリティのルール、最後に `--shard` です。実行するものが何も残らない場合、`NO_TESTS` は各フィルターが除外したテストの数を数え、タグとパターンを示します。どのテストも宣言していないタグにはそれぞれ印を付け、最も近い宣言済みのタグを示します。`--changed-since` を指定した場合、設定された[テストフィルター](/filters)は最後に実行されます。

```console
$ npx e2e run --debug
...
[e2e debug] phase timings (wall 14.2s)
  phase               count   total     avg     max
  scheduler               1   11.8s   11.8s   11.8s
  test.body               6   10.1s   1.7s    3.9s
  session.launch          6    1.1s   183ms   410ms
  engine.prepare          1   612ms   612ms   612ms
  collect                 1   420ms   420ms   420ms
  config.load             1   118ms   118ms   118ms
  realm.import            1    96ms    96ms    96ms
  session.close           6    88ms    15ms    31ms
  engine.init             1    74ms    74ms    74ms

[e2e debug] agent steps (execution order, model openai/gpt-6-luna-fast, total $0.0312)
  step                                   total   model  observe  action  calls  tokens in/out  cached       cost
  act "add a todo named groceries"       3.9s    2.8s    410ms   620ms      3  9412/388       61% (5740)   $0.0198
```

`cached` は、プロバイダーがプロンプトキャッシュから提供した入力トークンの割合で、内訳を報告しない場合は `-` です。レポートにも同じ内容がステップごと（`model.cacheReadTokens`、`model.cacheWriteTokens`）と実行ごと（`usage.modelCachedTokens`）に記録されます。

<a id="output" />

##### 出力

| レポーター | 書き込む内容 |
| --- | --- |
| `list` | ターミナルの進捗、コードフレーム付きの失敗、実行のサマリー。TTY では、ライブ進捗に現在のエージェントステップ、モデルのターン、ツール呼び出し、推論の抜粋が表示されます。stdout がターミナルでない場合（パイプ、リダイレクト、ほとんどの CI）は、各テストが終了するたびに表示されます。出力の最後には、失敗した各テストのファイルと行、エラーの最初の行、そして書き込まれた場合はトレースページが表示されます。信頼できないフィールドは 8 KiB に制限され、制御文字が除去されます。 |
| `json` | stdout へのレポートドキュメントで、stdout には他に何も出力しないため、`e2e run --reporter json \| jq` が使えます。これは `<output>/report.json` のドキュメントで、パッケージ内の `schema/report-v1.schema.json` で記述されています。形式は `schemaVersion` フィールド（現在は `report-1`）が変わるときにのみ変わります。 |
| `junit` | レポートの横の `junit.xml`。ファイルごとに 1 つの `<testsuite>`、テストとターゲットの組ごとに `title > path [target]` という名前の 1 つの `<testcase>` があります。テストクラスのエラーは `<failure>`、それ以外のエラーは `<error>`、スキップは理由付きの `<skipped>` です。中断されたテストは判定に至っていないため、メッセージが `interrupted:` で始まる `<skipped>` になります。[テストフィルター](/filters)が除外したテストは、メッセージが `left out by filter <name>:` で始まる `<skipped>` です。実行が選択しなかったその他のテストは記載されません。実行レベルのエラーは `run` スイートになります。 |
| `markdown` | レポートの横の `summary.md`: 件数、コスト、エラー、失敗の詳細で、トレースページが保持された場合はそれぞれそのページを示します。探索の実行では検出事項が表示されます。[`@e2e-dev/github`](/github) はこのサマリーをプルリクエストのコメントに使います。 |

テストまで到達したすべての実行は、[出力ディレクトリ](/reference/config#output)（デフォルトでは `.e2e`）の下に次のものを書き込みます。

- スクリプト向けの `report.json`（レポーターにかかわらず）
- [`trace`](/reference/config#trace) モードが保持するトレースページ（`results/` の下の各テストのディレクトリ内）
- レポートの横に置かれるレポーターのファイル

テストの前に停止した実行は、これらを何も書き込まず、前回の実行のファイルをそのまま残します。これには、設定やコレクションのエラー、`NO_TESTS`、`NO_LAST_RUN`、`UNSUPPORTED_ARTIFACT`、起動に失敗したアプリコマンド、中断が含まれます。そのエラーはターミナルと終了コードに現れます。書き込めなかった `junit.xml` や `summary.md` は stderr の 1 行になり、実行エラーにはなりません。

`list` レポーターは実行エラーを `Run Errors` の下に表示します。`list` がない場合、各実行エラーは `json` の場合も含めて stderr に `CODE: message` として表示されます。

レポートの `run.summary` は結果を数えます。

- `discovered` はランナーが収集したすべてのテストとターゲットの組、`selected` はこの実行が選択した組です。除外された組は `results` に `selected: false` として含まれますが、他のどの件数にも含まれません。
- `passed`、`failed`（タイムアウトを含む）、`interrupted`、`flaky`、`skipped` は選択された結果を数え、合計すると `selected` になります。
- `interrupted` は、判定の前に実行が停止したテスト（シグナル、`--max-failures`、`--max-duration`、または `MODEL_UNAVAILABLE` のような実行レベルのエラー）で、失敗にはなりません。
- `executed` は、少なくとも 1 回の試行が実行された、選択された結果です。serial のメンバーは、そのグループの試行のいずれかがそのメンバーに到達したときに試行が実行されたとみなされます。つまり本体が開始された（`test.skip()` を呼び出した本体を含む）か、起動時のようにそのメンバーで試行が失敗した場合です。失敗したフック、失敗した先行テスト、または実行の中断によって開始されなかったメンバーは該当しません。

`--ai-trace` を指定すると、実行は AI SDK devtools のデータベースである `<output>/ai-trace.json` も書き込みます。モデルとの往復ごとに 1 つのエントリーがあり、正確なプロンプト、ツール定義、レスポンス、使用量、プロバイダーのメタデータを保持します。その中の観測データはすでに秘匿化されており、インラインの画像やファイルのバイト列はバイト数に置き換えられます。[unbox-ai](https://github.com/e2e-inc/unbox-ai) で開いてください。`npx unbox-ai runs .e2e/ai-trace.json` で実行の一覧が表示されます。[実行のデバッグ](/debugging#agent-steps)を参照してください。[テストフィルター](/filters)のモデル呼び出しは記録されません。

<a id="watch-mode" />

##### ウォッチモード

`--watch` は選択したテストを実行し、サマリーを表示した後、終了せずに待機します。

<CodeGroup>
```bash npm
npx e2e run --watch
npx e2e run --watch tests/checkout.e2e.ts --headed
```

```bash pnpm
pnpm exec e2e run --watch
pnpm exec e2e run --watch tests/checkout.e2e.ts --headed
```

```bash bun
bunx e2e run --watch
bunx e2e run --watch tests/checkout.e2e.ts --headed
```
</CodeGroup>

- 保存されたテストファイル（設定の [`tests`](/reference/config#top-level) の glob に一致するもの）は、位置引数の代わりに、それだけが全体として再実行されます。
- テストの近くにある保存されたソースファイル（ヘルパーやフィクスチャ: glob が指すディレクトリの下、または設定の横にある `.ts`、`.js`、`.json`）や、保存された設定は、選択したテストを再実行します。
- どちらの場合も、コマンドラインの他のフィルターと `p`、`t` のフィルターは維持されます。
- 実行中の変更は実行の終了を待ち、まとめて次に実行されます。最初の実行中は、テストディレクトリが設定から決まるため、設定とそのディレクトリのみが監視されます。
- ターミナルでは、各再実行の前に画面がクリアされ、バナーがトリガーを示します。
- 各再実行は、テストがインポートするヘルパーを含め、プロジェクトのファイルを新たに読み込みます。

ターミナルでは、vitest と同様にキーで操作します。

| キー | 実行するもの |
| --- | --- |
| `a`, `enter` | コマンドラインが選択したすべてのテスト。`p` と `t` のフィルターはクリアされます |
| `r` | `p` と `t` のフィルターの下で、選択したテストを再度実行 |
| `f` | 前回の実行で成功しなかったテスト。`--last-failed` と同様にそのレポートから読み取り、どこにあっても対象になります。位置引数と `p` フィルターでは絞り込まれません |
| `u` | 現在の選択を `--update-snapshots` 付きで実行 |
| `p` | 以降の実行で選択に使う位置引数（ファイル、単純な名前、glob）の入力を求めます。空にするとクリアされます |
| `t` | `--grep` と同様のタイトルのパターンの入力を求めます。空にするとクリアされます |
| `h` | キーを表示 |
| `q` | 終了 |

- 実行中は、これらのいずれかのキー（およびスペースや `c`）で、中断と同様に実行をキャンセルします。2 回目のキーで強制的にキャンセルし、セッションは再び待機します。
- Ctrl-C または Ctrl-D は、`p` や `t` のプロンプト内からでも、実行を中断してセッションを終了します。Escape はプロンプト外では同じ動作をし、プロンプト内ではプロンプトを閉じるだけです。Ctrl-Z は通常どおりプロセスを一時停止します。
- 各再実行は完全な実行です。設定が読み込まれると、実行するものがない場合を除き、`report.json` とレポーターのファイルを書き込み、アプリコマンドを起動・停止します。再実行の間も開発サーバーを起動したままにするには、自分で起動し、コマンドに [`reuseExisting`](/reference/config#command) を設定してください。
- `--last-failed` とテストフィルターは最初の実行にのみ適用されるため、再実行でフィルターのモデルが呼ばれることはありません。何も選択しない再実行は空のまま成功します。
- 終了時の終了コードは、最後に完了した実行のものです。
- stdin にターミナルがない場合、ファイルの変更のみが再実行のきっかけになります。

<Note>
`--watch` は CI 向けではありません。自分では終了しないプロセスはジョブをハングさせるため、`CI` が設定されている場合は拒否されます。また、`--reporter json` と併用した場合も拒否され、設定の `reporters` に `json` が含まれる場合は最初の実行後に 2 で終了します。
</Note>

##### シグナル

シグナルは段階的に強くなります。

1. 最初の `SIGINT` または `SIGTERM` は中断します。実行中のテストは `interrupted` で終わります。その `afterEach` フックとセッションのクローズはクリーンアップの予算内で実行され、各ワーカーはエンジンを破棄します。開始されていないテストは、原因 `infrastructure-unavailable`、理由 `run interrupted before execution` でスキップされます。そのため、レポートには計画されたすべてのテストが記載され、`--last-failed` は中断されたテストと開始されなかったテストを再実行します。ランナーはレポートを書き込み、130 で終了します。テストが開始される前（コレクション中、エンジンの `prepare` 中、アプリの起動中）の中断では、レポートは書き込まれず、前回のレポートがそのまま残ります。
2. 2 回目のシグナルは強制終了です。ワーカーは直ちにエンジンを破棄し、クリーンアップの予算を使い切ると kill されます。レポートは引き続き書き込まれ、`junit` と `markdown` のレポーターがオンの場合は `junit.xml` と `summary.md` も書き込まれます。カスタムレポーターの `onRunFinished` は破棄されます。
3. 3 回目のシグナルでは、実行が起動したすべてのアプリコマンドのプロセスグループを kill した後、その場で終了します。`reuseExisting` で接続したプロセスはそのまま残されます。

ランナーがいなくなったワーカーは、エンジンを破棄し、クリーンアップの予算内で終了します。

#### `e2e explore`

テストファイルなしの実行です。エージェントは目標を受け取り、探索ステップを 1 つずつ計画し、`report_finding` ツールで不具合を報告し、評価で締めくくります。[テストなしで探索する](/explore)を参照してください。

<CodeGroup>
```bash npm

npx e2e explore 'Explore the checkout flow like a first-time buyer and report anything off'
npx e2e explore --target web --max-steps 4 --headed
npx e2e explore 'Hunt for broken forms and dead links' --agent thorough --video
```

```bash pnpm
pnpm exec e2e explore

pnpm exec e2e explore --target web --max-steps 4 --headed
pnpm exec e2e explore 'Hunt for broken forms and dead links' --agent thorough --video
```

</CodeGroup>

| オプション | 説明 |
| --- | --- |
| `[goal]` | 探索する内容を 1 文で。デフォルト: `Explore the app and find bugs`。 |
| `--config <path>` | 明示的な設定のパスで、エラーは `run` と同じです。デフォルト: 検出されたもの。設定が見つからず、stdin と stdout の両方がターミナルの場合、まず作業ディレクトリで [`e2e init`](#e2e-init) のウィザードが実行されます。手作業で行うことが何も残っていなければ探索が続きます。つまり、依存関係がインストールされ、キーが設定されたかサインインが済んだモデルがあり、Web ターゲットがある（探索する URL が示されます）場合です。そうでなければ、init は残りの手順と、入力されたとおりの `e2e explore` コマンドを示して終わります。ターミナルがない場合、設定がなければ `CONFIG_NOT_FOUND` です。 |

| `--agent <name>` | 探索に使う、設定済みのエージェント。デフォルト: `default`。そのモデル、`system`、ツール、コンテキストが再利用されます。自前の `StepExecutor` は、通知とともに組み込みのエージェントに置き換えられます。モデルのないエントリー（カスタムエグゼキューターのものを含む）は、何かが始まる前に `MODEL_UNAVAILABLE` になります。不明な名前は `INVALID_CONFIG` です。 |
| `--session <name>` | サインインした状態で開始します。設定のテストファイルのうち、このセッションを宣言するセットアップテストが最初に実行されます。探索は、`{ session }` を持つテストと同様に、保存された状態を復元します。他のテストは実行されません。どのセットアップテストも宣言していない名前は、アプリのプロセスが起動する前に、宣言済みの名前を示して `COLLECTION_ERROR` になります。[サインインした状態で開始する](/explore#start-signed-in)を参照してください。 |
| `--changed-since <ref>` | ref と HEAD のマージベース以降の変更を探索します。プランナーはそのコミットメッセージとコミット済みの差分を読み取ります。目標がない場合、目標は `Explore what this change affects and find bugs in it` になり、プランナーはユーザーから見えない変更をスキップできます。その場合、実行は `skipped` で終わり、成功します。空の ref、`-` で始まる ref、git が差分を計算できない ref は `INVALID_CHANGED_SINCE` です。レポートは変更を `run.explore.change` として記録します。[プルリクエストの変更を探索する](/explore#explore-a-pull-requests-change)と、モデルが読み取る内容については[セキュリティ](/reference/security#mcp-and-explore)を参照してください。 |
| `--max-steps <n>` | 探索ステップの最大数で、1〜100 の整数。デフォルト: `8`。範囲外は 2 で終了します。 |
| `--timeout <ms>` | 実行の実時間で、180000〜7200000 の整数。デフォルト: `600000`。最後の 1 分は締めくくりの評価のために確保されます。範囲外は 2 で終了します。 |
| `--headed` | エンジンが対応している場合、UI の表示を要求します。 |
| `--reporter <ids>` | `run` と同じです。デフォルト: 解決された設定値。`list` はサマリーの下に探索の行を表示し、`json` はレポートに記録を含め、`markdown` は検出事項を `<output>/summary.md` に書き込みます。 |
| `--output <dir>` | `run` と同じです。デフォルト: 設定、なければ `.e2e`。検出事項の証拠となるスクリーンショットは、`<output>/results` の下の試行の成果物です。 |
| `--debug` | `run` と同じです: フェーズのタイミングとエージェントステップの表。 |
| `--ai-trace` | `run` と同じです。 |
| `--trace [mode]` | `run` と同じです: 探索のトレースページ。デフォルト: 設定。 |
| `--video [mode]` | `run` と同じです: 探索全体の 1 本の動画（ブラウザエンジンでは WebM、デバイスエンジンでは MP4）。デフォルト: 設定。記録できないエンジンでは通知が表示されます。 |

`--trace` と `--video` では、値なしのフラグは `on` で、`retain-on-failure` は探索が成功しなかった場合にのみページや動画を保持します。探索は 1 回の試行なので、リトライのモードでは何も記録されず、計画時の通知が `--trace on`（または `--video on`）を指定するよう伝えます。目標をフラグの前に置くか、`--trace=<mode>` または `--video=<mode>` と書いてください。

##### レポート

- 実行には、仮想ファイル `explore` の下に、目標をタイトルとする 1 つの結果があります。
- 探索はまずアプリを開きます。ターゲットの `app.url`、またはデバイスでは[固定されたアプリ](/mobile#point-at-your-app)を新たに起動します。ビルドはインストールしないため、ローカルのデバイスターゲットには `app.bundleId` が必要です。
- `--session` を指定すると、レポートにはセットアップテストの結果も含まれます。プロジェクトの他のテストは、`run` が位置引数で指定されなかったファイルのテストを列挙するのと同様に、原因 `filtered` でスキップとして列挙されます。
- 探索は、設定にかかわらず、リプレイキャッシュをオフにし、リトライ 0 回で実行されます。`--session` のセットアップテストは、`run` の場合と同様に、設定のエージェント、キャッシュ、リトライで実行されます。
- `<output>/report.json` には `run.explore` が追加されます。目標、予算、実行が終了した理由（`finished`、`skipped`、`step-limit`、`time`、`stuck`、または `aborted`）、評価、`--changed-since` 指定時の変更（`base` と `files`）、ステップ、検出事項が含まれます。
- 成果物は、目標の最初の数語と、目標、ターゲット、エージェントのダイジェストから名付けられたディレクトリ（`<output>/results/explore-check-the-cart-totals-1a2b3c4d5e6f7a8b/` など）に置かれます。同じターゲットとエージェントで同じ目標を再実行すると、同じディレクトリに書き込まれます。

##### ステップの予算

各ステップには独自の予算があります。エージェントが `maxSteps` または `maxModelCalls`（1〜100）を設定しない限り、40 アクションと 40 回のモデル呼び出しです。アクションまたは時間の予算に達したステップはタイムボックスで打ち切られますが、その検出事項は引き続き有効です。失敗したステップで実行が終わることはありません。新しい検出事項のないまま失敗またはブロックされたステップが 3 回続くと、実行は終了します（`stuck`）。

##### 検出事項

- 種類が `issue` の検出事項は機能的な不具合で、`warning` は見た目の問題です。
- 重大度は `trivial`（1）から `critical`（5）までです。レポートは issue を warning より先に、重大度の高いものから順に列挙します。
- 各検出事項には、場所、期待される動作と観測された動作、再現手順、そしてキャプチャが許可されて成功した場合はスクリーンショットが含まれます。

##### 結果

| 結果 | 実行のステータス | 終了コード |
| --- | --- | --- |
| ステップが実行され、`issue` の検出事項がなく、すべてのステップがブロックされたわけではない | passed | 0 |
| `issue` の検出事項が 1 つ以上ある | failed | 1 |
| プランナーが変更をスキップした場合を除き、ステップが 1 つも実行されず何も見つからなかった | blocked | 1 |
| `--changed-since` 指定時に、プランナーがユーザーから見えない変更をスキップした | passed | 0 |
| すべてのステップがブロックされ、`issue` の検出事項がない | blocked | 最初のブロック要因に応じて 1、2、または 3 |
| 設定、エンジン、またはモデルプロバイダーのエラー | error | 2 または 3 |
| Ctrl-C | | 130 |

| オプション | 説明 |
| --- | --- |
| `[files...]` | [`run`](#positional-arguments) と同じです。 |
| `--config`, `--target`, `--tag`, `--tag-mode`, `--exclude-tag`, `--grep`, `--grep-invert`, `--changed-since`, `--last-failed`, `--shard`, `--pass-with-no-tests` | [`run`](#flags) と同じです。`--last-failed` は設定の [`output`](/reference/config#output) の下の `report.json` を読み取ります。設定された[テストフィルター](/filters)は `run` と同様に実行され、その出力行は stderr に出ます。 |

| レポーター | 書き込む内容 |
| --- | --- |
| `list` | 選択順に組ごとに 1 行: `file › title [target]` で、describe のパスは ` › ` で連結されます（`tests/billing.e2e.ts › checkout › pays [web]`）。続けて、宣言された各タグが `#tag` として付きます（`tests/billing.e2e.ts › checkout › pays [web] #smoke #billing`）。スキップされたテストも行が残り、`(skipped: <reason>)` が付加されます。テストフィルターが除外したテストは `(left out by <filter>: <reason>)` で終わります。セットアップテストも他のテストと同様に列挙されます。 |
| `json` | stdout への `{ "pairs": [...] }`。各組には、`id`、`file`、`title`、`titlePath`、`kind`（`test` または `setup`）、`tags`（テストが宣言するタグ。ない場合は `[]`）、宣言が判明している場合は `source`、テストがセッションを使用する場合は `session`、`sessions`、テストが serial グループ内にある場合は `serialId`、`target`、`agent`、`disposition`（`run`、`skip`、またはテストフィルターが除外した場合は `filtered`）、スキップまたは除外された場合は `reason`、そしてテストフィルターが除外した場合はそのフィルターの名前である `filter` が含まれます。 |

選択フラグが除外した組は列挙されません。[`e2e/runner` の `list`](/reference/runner) はプロセス内で同じ選択を実行し、除外された組も返します。

#### `e2e doctor`

何も起動せずに、この場所で `e2e run` を開始できるかどうかを確認します。設定を読み込み、各ターゲットのエンジンのチェックを実行し、各エージェントが解決したモデルを示します。アプリ、エンジンのセッション、ワーカーは起動せず（独自のプロセスで動作するエンジンのサーバーのみ起動します）、`--check-model` を指定しない限りモデルを呼び出しません。

<CodeGroup>
```bash npm
npx e2e doctor
npx e2e doctor --json
npx e2e doctor --check-model
npx e2e doctor --target web --headed
```

```bash pnpm
pnpm exec e2e doctor
pnpm exec e2e doctor --json
pnpm exec e2e doctor --check-model
pnpm exec e2e doctor --target web --headed
```

```bash bun
bunx e2e doctor
bunx e2e doctor --json
bunx e2e doctor --check-model
bunx e2e doctor --target web --headed
```
</CodeGroup>

| オプション | 説明 |
| --- | --- |
| `--config <path>` | [`run`](#flags) と同じです。 |
| `--target <ids>` | これらのターゲットのみを確認します。[`run`](#flags) と同じです。 |
| `--headed` | headless shell ではなくフル版の Chromium ビルドなど、headed での実行に必要なものを確認します。 |
| `--check-model` | 各エージェントのモデルと、それが別のモデルである場合はそのジャッジを、短いプロンプトとエージェントのプロバイダーオプションで 1 回ずつ呼び出します。モデル、プロバイダーオプション、`maxInputTokens` が等しいエージェントは呼び出しを共有します。求めた JSON ではない返答や拒否も、応答として扱われます。 |
| `--json` | チェックごとの 1 行の代わりに、`doctor-1` レポートを表示します。 |

| チェック | ステータス |
| --- | --- |
| `node` | `pass`: Node.js または Bun のバージョン。サポートされていないランタイムでも、`--json` は `node` を `fail` としたレポートを表示します。 |
| `config` | `path` と `targets`（`name`、`platform`、`engine`）を伴う `pass`、または `CONFIG_*` や `UNKNOWN_TARGET` のコードを伴う `fail`。`config` が失敗した場合、それが最後のチェックになります。 |
| エンジンのチェック（`target` 付き） | ターゲットのエンジンが報告する内容です。たとえば Web エンジンの `browser` は、インストール済みなら `pass`、最初の実行でダウンロードされる場合は `warn`、ブラウザプロバイダーや `connect` を使う場合は `skip` です。mobile エンジンの agent-device のチェック（`agent-device`、`toolchain`、`ios-runner-cache`、設定された各デバイスの `device`、`target-app`）と `app-path` では、デバイスプロバイダーの場合は `device` のみが `skip` として報告されます。何も報告しないエンジンはチェックを追加しません。`engine` は、エンジンに `doctor` フックがない場合は `skip`、フックが例外を投げた、タイムアウトした、または不正な形式のチェックを返した場合は `fail` です。 |
| `model`（`agent` 付き） | `model` と `judge` を、AI SDK インスタンスが報告する名前である `provider` と `modelId` として示します。[`e2e login`](/subscriptions) のモデルについては、保存されたログインまたはプロバイダーの API キー変数から `pass` または `fail` となり、エージェントのモデルが 1 つのログインを読む場合は `login` が設定されます。それ以外のモデルは、モデルが自身の認証情報を読むため `unknown` です。`--check-model` を指定すると、すべてのモデルが応答した場合は `pass`、そうでなければエラーコードを伴う `fail` で、エージェントがモデルとジャッジの両方を持つ場合、メッセージには `model:` または `judge:` が前に付きます。エージェントにモデルがない場合は `skip` です。カスタムエグゼキューターが独自のエージェントを持ち込み、モデルもジャッジも宣言しない場合は `executor` を伴う `unknown` です。宣言したモデルはエージェントのモデルと同様にチェックされます。 |

デフォルトでは、doctor はチェックごとに 1 行を表示します。マーク、チェック ID、角括弧内のターゲットまたはエージェント、そして詳細です。最後の行は、実行を開始できるかどうかを示します。

`--json` を指定すると、`doctor-1` レポートを stdout に表示します: `{ "schemaVersion": "doctor-1", "version", "ok", "checks": [...] }`。各チェックは `id`、`status`（`pass`、`warn`、`fail`、`skip`、または `unknown`）と、該当する場合は `target`、`agent`、`code`、`message`、そして上の表のフィールドを持ちます。JSON Schema はパッケージ内に `schema/doctor-v1.schema.json` として同梱されています。

| 終了コード | 条件 |
| --- | --- |
| 0 | 失敗したチェックがありません。`warn`、`skip`、`unknown` は失敗になりません。 |
| 2 | 少なくとも 1 つのチェックが失敗しました。 |
| 130 | Ctrl-C または SIGTERM で中断されました。チェックは停止し、レポートが表示されます。途中で打ち切られたチェックは `CANCELLED` を伴う `fail` となり、それ以降のチェックは省かれます。3 回目の Ctrl-C で直ちに終了します。 |

#### `e2e cache`

リプレイキャッシュを調べる、またはクリアします。各サブコマンドは、検出された設定または `--config <path>` を読み込み、実行が使うのと同じディレクトリを読み取り、ストアが空の場合は 0 で終了します。

<CodeGroup>
```bash npm
npx e2e cache ls
npx e2e cache stats
npx e2e cache clear
npx e2e cache ls --config packages/web/e2e.config.ts
```

```bash pnpm
pnpm exec e2e cache ls
pnpm exec e2e cache stats
pnpm exec e2e cache clear
pnpm exec e2e cache ls --config packages/web/e2e.config.ts
```

```bash bun
bunx e2e cache ls
bunx e2e cache stats
bunx e2e cache clear
bunx e2e cache ls --config packages/web/e2e.config.ts
```
</CodeGroup>

| コマンド | 表示内容 |
| --- | --- |
| `e2e cache ls` | エントリーごとに 1 行: 記録されたテストとターゲット、指示のダイジェストの最初の 12 文字、経過時間、リプレイで実行されるアクション数（記録がアクションの上限に達した場合は `(truncated)`）。行はテスト、次にターゲットでグループ化され、古い順に並びます。 |
| `e2e cache stats` | ストアのディレクトリ、読み取り可能なエントリーの数、その合計サイズ、そして読み取れないファイルがある場合はその数。 |
| `e2e cache clear` | すべてのキャッシュファイルを削除し、ディレクトリに他に何も残っていなければディレクトリも削除して、削除したファイルの数を報告します。 |

| オプション | 説明 |
| --- | --- |
| `--config <path>` | 明示的な設定のパス。デフォルト: 最も近い `e2e.config.ts`、`.mts`、`.js`、または `.mjs`（[読み込み](/reference/config#loading)を参照）。 |
| `--cache-dir <dir>` | ストアのディレクトリ。デフォルト: `E2E_CACHE_DIR`、なければ `cache.dir`、なければ `.e2e/cache/`。 |

```text
TEST                             TARGET  INSTRUCTION   AGE  ACTIONS
tests/billing.e2e.ts::upgrades   web     4f1c0a9d3b62  2h   4
tests/signup.e2e.ts::signs%20up  web     9ab7715ce004  3d   7 (truncated)
```

- エントリーが来歴情報を持つようになる前に記録されたエントリーは、それらの列に `-` が表示されますが、引き続きリプレイされます。
- ストアが読み取れないファイル（切り詰められている、1 MiB の上限を超えている、または新しいスキーマのもの）は、stderr で別途数えられ、実行ではミスとして扱われ、`clear` で削除されます。
- ランナーが書き込んでいないファイルはそのまま残されます。

<Note>
これらのコマンドはファイルストアのみを読み取ります。カスタムの `cache.store` を使っている場合は、その旨を伝えて 2 で終了します。
</Note>

#### `e2e upgrade`

`e2e` を最新のリリース、dist-tag、または特定のバージョンにアップグレードします。同じ `package.json` 内の `@e2e-dev/*` パッケージも更新し、プロジェクトのパッケージマネージャーでインストールします。`e2e update` は同じコマンドです。

<Note>
`npx e2e` はインストール済みのバージョンを実行します。そのバージョンにまだ `upgrade` コマンドがない場合は、一度だけ `npx e2e@latest upgrade` を実行してください。
</Note>

<CodeGroup>
```bash npm
npx e2e upgrade             # the latest release
npx e2e upgrade 0.21.0      # one version
npx e2e upgrade nightly     # a dist-tag
npx e2e update --dry-run    # show the plan, change nothing
```

```bash pnpm
pnpm exec e2e upgrade             # the latest release
pnpm exec e2e upgrade 0.21.0      # one version
pnpm exec e2e upgrade nightly     # a dist-tag
pnpm exec e2e update --dry-run    # show the plan, change nothing
```

```bash bun
bunx e2e upgrade             # the latest release
bunx e2e upgrade 0.21.0      # one version
bunx e2e upgrade nightly     # a dist-tag
bunx e2e update --dry-run    # show the plan, change nothing
```
</CodeGroup>

```console
$ npx e2e upgrade

  e2e              0.19.0 → 0.21.2
  @e2e-dev/web     0.13.0 → 0.15.2
  @e2e-dev/kernel  0.1.2 → 0.2.1
package.json: "e2e": "^0.21.2", "@e2e-dev/web": "^0.15.2", "@e2e-dev/kernel": "^0.2.1"
$ npm install
...
Upgraded: e2e 0.21.2, @e2e-dev/web 0.15.2, @e2e-dev/kernel 0.2.1
Release notes: https://github.com/e2e-inc/e2e/releases/tag/e2e%400.21.2
Updated the agent skill in .agents/skills/e2e/ (12 files)
```

| オプション | 説明 |
| --- | --- |
| `[version]` | `0.22.0` のようなバージョン、または `latest` や `nightly` のような dist-tag。範囲は拒否されます。デフォルト: `latest`。 |
| `--dry-run` | バージョン、新しい指定、インストールコマンド、更新するスキルのコピーを表示し、何も変更しません。 |

- **プロジェクト。** 作業ディレクトリから上にたどって最も近い、`e2e` を記載している `package.json`。
- **ターミナルでは。** 新しい `e2e` のインストール後に、e2e のロゴと、GitHub で e2e にスターを付けるためのリンクが続きます。CI やパイプされた出力では表示されません。
- **兄弟パッケージのバージョン。** 各 `@e2e-dev/*` パッケージには、同じ dist-tag（バージョンを指定した場合は `latest`）のリリースが、そのリリースの peer の範囲が新しいバージョンを受け入れる場合に使われます。そうでなければ、受け入れる最新のリリースが使われます。該当するものがない場合、コマンドは 2 で終了します。非推奨のリリースが選ばれることはなく、プレリリースは `e2e` がプレリリースになる場合にのみ選ばれます。インテグレーションは、接続先のエンジンに従います。
- **追加される peer。** それらのリリースが peer として依存する `@e2e-dev/*` パッケージ（エンジンにとっての `@e2e-dev/core` など）は、`package.json` に記載されていない場合、それを必要とするパッケージの横に追加されます。Yarn はプロジェクトが記載していない peer をインストールしないためです。バージョンは新しい `e2e` が依存するものになります。
- **パッケージマネージャー。** プロジェクトのロックファイルまたは `packageManager` フィールドが示すもの、または pnpm ワークスペースのルートでは pnpm です。どちらも持たないワークスペースのメンバーは、ワークスペースのルートのものを使います。どのワークスペースにも記載されていないプロジェクトより上にあるロックファイルは対象外です。
- **インストール。** 新しい指定は、それぞれ元のセクションに入る形で `package.json` に書き込まれ、その後 1 回の `install` でまとめて解決されます。CI でもロックファイルを変更できるよう、pnpm には `--no-frozen-lockfile`、Yarn には `YARN_ENABLE_IMMUTABLE_INSTALLS=false` が渡されます。Ctrl-C はパッケージマネージャーに届き、コマンドはその停止を待ちます。
- **インストールの失敗。** `package.json` と、インストールが変更したロックファイルは元に戻ります。`node_modules` には、次のインストールまで一部の新しいバージョンが残ることがあります。
- **保存される範囲。** インストールされるバージョンが変わるパッケージのみが新しい指定を得ます。指定したバージョンやプレリリースは正確に固定され、dist-tag は古い指定の `^` や `~` を維持します。インストール済みの 0.21.3 に対する `e2e upgrade 0.21.3` では、`^0.21.3` が書かれたまま残ります。
- **そのまま残されるもの。** `workspace:`、`file:`、`link:`、`catalog:`、パス、git URL でリンクされたパッケージ、およびレジストリにない `@e2e-dev/*` パッケージ。`e2e` 自体がリンクされている場合、コマンドは 2 で終了します。
- **何もすることがない場合。** インストール済みのすべてのバージョンがすでに一致している場合、コマンドは何もインストールしません。Yarn Plug'n'Play のように `node_modules` がない場合は、代わりに `package.json` の指定を比較します。
- **レジストリ。** パッケージマネージャーが設定する場合は `npm_config_registry`、それ以外は `https://registry.npmjs.org/`。
- **エージェントスキル。** `.agents/skills/e2e` または `.claude/skills/e2e` にあるコピーは、インストール後、およびすべてがすでに最新だった場合にも、インストール済みのバージョンのものに更新されます。`.agents/skills` のコピーへの `.claude/skills/e2e` シンボリックリンクはそれに追従します。新しいスキルが同梱しなくなったファイルは残ります。プロジェクト外のコピーへのシンボリックリンクを通して書き込むことはなく、Yarn Plug'n'Play のように `node_modules` がない場合は、コマンドは代わりに `e2e init` を示します。

| 終了コード | 条件 |
| --- | --- |
| 0 | パッケージがインストールされた、すでに目的のバージョンだった、または `--dry-run` が計画を表示しました。 |
| 2 | 範囲、不明なバージョンや dist-tag、`e2e` を記載した `package.json` がない、リンクされた `e2e`、適合するリリースのない兄弟パッケージ、またはインストールの失敗。 |
| 3 | レジストリへのリクエストが失敗した、エラーステータスで応答した、またはコマンドが読み取れないメタデータを送ってきました。 |
| 130 | インストール中の Ctrl-C または SIGTERM。`package.json` とロックファイルは元に戻ります。 |

#### `e2e feedback`

e2e 自体についてのレポートを 1 件、e2e チームに送ります。何かが壊れている、ドキュメントやスキルが誤解を招いた、または機能が不足している、といった内容です。コーディングエージェントは、テスト対象のアプリではなく e2e の問題に遭遇したときに送ることができます。その場合は、まずユーザーに `--dry-run` の出力を見せ、同意を得ます。

<CodeGroup>
```bash npm
npx e2e feedback --type bug -m "list ignores --grep" --command "e2e list --grep checkout" \
  --repro "e2e list --grep checkout lists every test"
npx e2e feedback --type docs -m "The mcp topic never says how to close a session"
npx e2e feedback --type feature -m "Need a way to set the viewport per test" --dry-run
```

```bash pnpm
pnpm exec e2e feedback --type bug -m "list ignores --grep" --command "e2e list --grep checkout" \
  --repro "e2e list --grep checkout lists every test"
pnpm exec e2e feedback --type docs -m "The mcp topic never says how to close a session"
pnpm exec e2e feedback --type feature -m "Need a way to set the viewport per test" --dry-run
```

```bash bun
bunx e2e feedback --type bug -m "list ignores --grep" --command "e2e list --grep checkout" \
  --repro "e2e list --grep checkout lists every test"
bunx e2e feedback --type docs -m "The mcp topic never says how to close a session"
bunx e2e feedback --type feature -m "Need a way to set the viewport per test" --dry-run
```
</CodeGroup>

| オプション | 説明 |
| --- | --- |
| `-m`, `--message <text>` | 必須。問題についての 1〜2 文。 |
| `--type <type>` | `bug`、`docs`、`feature`、または `other`。デフォルト: `other`。 |
| `--task <text>` | 何をしようとしていたか。 |
| `--expected <text>` | 何が起こると期待していたか。 |
| `--actual <text>` | 代わりに何が起こったか（エラーメッセージを含む）。 |
| `--error-code <code>` | 関係する e2e のエラーコード（`LOCATOR_AMBIGUOUS` など）。 |
| `--repro <text>` | バグの場合: 毎回再現する手順。アプリのコンテンツは含めません。 |
| `--approach <text>` | 試したこと（回避策を含む）。 |
| `--command <text>` | 関係する e2e のコマンドまたは API。 |
| `--agent <text>` | 送信するコーディングエージェントとモデル。 |
| `--allow-outdated` | より新しい e2e のリリースがある場合でも送信します。 |
| `--dry-run` | 送信されるイベントを表示し、何も送信しません。 |

`--message` は最大 2000 文字、`--command` と `--agent` は 200 文字、`--task`、`--expected`、`--actual`、`--repro`、`--approach` は 1500 文字までです。

- **バグには `--repro` が必要です。** ない場合、コマンドは何も送信せず、代わりに事前入力された [GitHub issue](https://github.com/e2e-inc/e2e/issues/new?template=bug_report.yml) を表示します。そこでは e2e チームが再現手順を求めることができます。最小限の再現手順を追加し、自分で送信してください。
- **古いリリースは拒否されます。** 送信前に、コマンドは npm レジストリに最新の e2e のリリースを問い合わせます。あなたのリリースが古い場合、問題はすでに修正されている可能性があるため、2 で終了し何も送信しません。[`e2e upgrade`](#e2e-upgrade) でアップグレードし、まだ問題が起こることを確認してから再度送信するか、`--allow-outdated` を指定してください。オプトアウトの変数が設定されている場合、コマンドはこのチェックをスキップします。
- **送信先。** 1 つの `e2e_feedback` イベントが、[テレメトリ](/telemetry#feedback)と同じ PostHog プロジェクトに、すべてのテレメトリイベントが持つ匿名のマシン情報とともに送られます。
- **オプトアウト。** フィードバックはコマンドを実行したときにのみ送信されるため、保存された `e2e telemetry disable` では止まりません。`E2E_TELEMETRY_DISABLED=1` と `DO_NOT_TRACK=1` では止まります。どちらかが設定されている場合、コマンドは何も送信せず、本来送信するはずだったレポートは 2 で終了します。そのため、オプトアウトした CI ジョブやマシン群は、エージェントが実行した場合でも何も送信しません。`--dry-run`、`E2E_TELEMETRY_DEBUG=1`（`--dry-run` と同様にイベントを表示します）、`--repro` のないバグはいずれにしても何も送信しないため、0 で終了します。

| 終了コード | 条件 |
| --- | --- |
| 0 | PostHog がイベントを受け付け、コマンドが参照 ID を表示しました。`--dry-run`、`E2E_TELEMETRY_DEBUG=1`、`--repro` のない `--type bug` も同様です。これらはいずれも送信しないため、オプトアウトの変数が設定されていても 0 で終了します。古いリリースのチェックが先に実行されるため、`--allow-outdated` かオプトアウトの変数が設定されていない限り、古いインストールではこれらの場合も 2 で終了します。 |
| 2 | 空または長すぎるテキスト値、`--allow-outdated` もオプトアウトの変数も設定されていない古いリリース、または `E2E_TELEMETRY_DISABLED=1` か `DO_NOT_TRACK=1` が設定されている状態で送信されるはずだったレポート。 |
| 3 | PostHog がイベントを確認しませんでした。レポートは届いている可能性があるため、メッセージにはその参照 ID が示されます。 |

<Warning>
送信前に、名前に `KEY`、`TOKEN`、`SECRET`、`PASS`、`_PWD`、`CREDENTIAL`、`AUTH`、`COOKIE`、`PRIVATE` のいずれかを含むすべての環境変数の値は、6 文字以上であれば `<secret:NAME>` に置き換えられます。これは設定のシークレットの最小長です。より短いものを対象にすると通常の単語まで書き換えてしまいます。Bearer トークン、URL の認証情報、秘密鍵、JWT、一般的な API キーの形式は `<redacted>` に置き換えられます。アプリのデータ、ページのコンテンツ、テストファイルは貼り付けないでください。
</Warning>

#### `e2e telemetry`

匿名の利用状況テレメトリがオンかどうかを表示し、切り替えます。送信されるすべてのプロパティは[テレメトリ](/telemetry)に記載されています。

<CodeGroup>
```bash npm
npx e2e telemetry
npx e2e telemetry disable
E2E_TELEMETRY_DEBUG=1 npx e2e run
```

```bash pnpm
pnpm exec e2e telemetry
pnpm exec e2e telemetry disable
E2E_TELEMETRY_DEBUG=1 pnpm exec e2e run
```

```bash bun
bunx e2e telemetry
bunx e2e telemetry disable
E2E_TELEMETRY_DEBUG=1 bunx e2e run
```
</CodeGroup>

| コマンド | 効果 |
| --- | --- |
| `e2e telemetry`, `e2e telemetry status` | `Status: enabled`、または理由付きの `Status: disabled` を表示します。理由は、設定されている変数、保存された選択、または書き込めない設定ディレクトリです。`status` がデフォルトです。 |
| `e2e telemetry disable` | オプトアウトを `~/.config/e2e/telemetry.json`（設定されている場合は `$XDG_CONFIG_HOME/e2e/`、Windows では `%APPDATA%\e2e\`）に保存し、ステータスを表示します。 |
| `e2e telemetry enable` | オプトインを保存し、ステータスを表示します。環境で設定された変数が引き続き優先され、ステータスにもそれが示されます。 |

- `E2E_TELEMETRY_DISABLED=1` と `DO_NOT_TRACK=1` は、ファイルに触れずにテレメトリをオフにします。
- `E2E_TELEMETRY_DEBUG=1` はすべてのイベントを stderr に表示し、何も送信しません。
- マシン上での最初のコマンド（`e2e init` と `e2e telemetry` を除く）は、一度だけ通知を表示します。CI では何も表示されず、ファイルも書き込まれません。

## 終了コード

| コード | 意味 |
| ---: | --- |
| 0 | 選択されたすべてのテストが成功した、flaky だった、または明示的にスキップされた |
| 1 | テストまたはセットアップの最終的な失敗、またはテストのタイムアウト |
| 2 | CLI、設定、コレクション、依存関係、認証情報、モデル設定、またはポリシーのエラー |
| 3 | エンジン、アプリのプロセス、モデルプロバイダー、成果物、またはクリーンアップのインフラの失敗。配信できなかった `e2e feedback`。レジストリに到達できなかった `e2e upgrade` |
| 4 | ランナー内部の不変条件違反、または処理されなかったランナーのエラー |
| 130 | ユーザーまたは CI のシグナル、`--step` プロンプトでの `q`、または `e2e run --step stop` による中断 |

- 混在した実行での優先順位は `130 > 4 > 3 > 2 > 1 > 0` です。レポートは個々の結果をすべて保持します。優先順位が影響するのはプロセスの終了コードだけです。
- 引数の解析に失敗すると、stderr に 1 行のエラーを出して 2 で終了します。

## 診断

- 名前を拒否するメッセージは、最も近い有効な名前を提案します。
- 他のランナーの設定のキー（`testDir`、`baseURL`、`webServer`、`projects`）には、ここでその情報がどこにあるかが示されます。
- 設定やテストファイルで失敗する `import` は、プロジェクトのパッケージマネージャー向けの install または add コマンド、あるいはパッケージがエクスポートするサブパスで締めくくられます。
- プロバイダーが拒否したモデルの認証情報には、プロバイダーが読み取る変数が示されます。

## Bun

Bun 1.4.3 以降では、CLI は Node.js なしで動作します。Node.js がインストールされている場合、`bunx e2e` と `bun run` は CLI の `node` シバンに従い、Node.js 上で実行します。`bunx --bun e2e` と `bun --bun run` は Bun 上で実行します。Node.js がない場合は、いずれも Bun 上で実行します。Web エンジンは Bun 上で動作します。`@e2e-dev/mobile` とインテグレーションは、まだ Bun 上での動作が検証されていません。

Bun は設定ファイルとテストファイルを独自の TypeScript サポートでコンパイルします。Node.js と異なる点は次のとおりです。

- ディレクトリにマップされる `#` インポートは、その index を読み込みません。インポートをファイルにマップしてください。
- `.cts` ファイル内のレガシーデコレーターは読み込みに失敗します。クラスを `.ts` ファイルに移動してください。
- `e2e run --watch` と `e2e mcp` は、`tsconfig.json` と、`import()` や `require()` が計算されたパスで指定するファイルを一度だけ読み込みます。いずれかを編集した後や、インポートが見つけられなかったファイルを追加した後は再起動してください。
- `e2e mcp` は一度に 1 つのセッションを開き、`--max-sessions` を無視します。
- [`e2e/runner`](/reference/runner) には Node.js が必要です。
- `executable: 'node'` を持つアプリの `command` には、`bun run` または `bunx` が CLI を起動した場合を除き、Node.js が必要です。これらは Bun を実行する `node` を `PATH` に置くためです。
- ヘルパーが `await` の後に宣言したテストは、ヘルパー内の行を報告します。
