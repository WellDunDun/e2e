レポーターは、実行のイベントを発生と同時に受け取り、レポートの書き込みが終わると完了した実行を受け取ります。`e2e.config.ts` の `reporters` には、組み込みレポーターの ID とレポーターオブジェクトを並べて列挙します。

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { web } from '@e2e-dev/web';
import { github } from '@e2e-dev/github';

export default {
  targets: [{ engine: web(), app: { url: 'http://localhost:3000' } }],
  reporters: ['list', 'junit', github()],
} satisfies E2EConfig;
```

## リファレンス

### 組み込みレポーター

| レポーター | 説明 |
| --- | --- |
| [`list`](#list) | ターミナルの進捗表示と実行のサマリー |
| [`json`](#json) | レポートドキュメントを stdout に出力 |
| [`junit`](#junit) | `<output>/junit.xml` を書き込み |
| [`markdown`](#markdown) | `<output>/summary.md` を書き込み |
| [`github()`](#github) | プルリクエストのコメントとジョブサマリー |
| [`htmlReporter()`](#htmlreporter) | `<output>/report.html` を書き込み |

| スローされるエラー | 条件 |
| --- | --- |
| `INVALID_CONFIG` | `reporters` が配列ではない場合。 |
| `INVALID_CONFIG` | `list`、`json`、`junit`、`markdown` 以外の ID が指定された場合。 |
| `INVALID_CONFIG` | ID でも、`name` と少なくとも 1 つのハンドラーを持つオブジェクトでもないエントリーがある場合。 |
| `INVALID_CONFIG` | `json` と `list` を併用した場合。 |

#### `list`

ターミナルの進捗、失敗、実行のサマリーを表示します。

```ts
reporters: ['list'], // default
```

- [`onEvent`](#onevent) が受け取るのと同じイベントを表示します。
- TTY では、ライブビューに実行中のテストが表示されます。stdout がターミナルでない場合（パイプ、リダイレクト、ほとんどの CI）、各テストは完了時に出力されます。
- レポーターが返す[サマリー行](#onrunfinished)は、そのサマリーの下に出力されます。
- 出力の最後には、失敗したテストごとに `Failed` 行が表示されます。そのファイルと行、エラーの 1 行目、トレースページが書き込まれた場合はそのトレースページが含まれるため、`e2e run | tail` でも何が壊れたかがわかります。

#### `json`

レポートドキュメントを stdout に出力します。

```ts
reporters: ['json'],
```

#### `junit`

レポートと同じ場所に `junit.xml` を書き込みます。

```ts
reporters: ['list', 'junit'],
```

- `run.report` を読み取り、`run.reportPath` と同じ場所に `junit.xml` を書き込み、そのファイルを示す行を 1 つ返します。レポーターの最小の完全な例です。
- 失敗した、タイムアウトした、リトライでのみパスした、または [`test.fail`](/reference/test#fail) の期待どおりに失敗したテストが失敗時のスクリーンショットを記録した場合、その `<testcase>` は `<system-out>[[ATTACHMENT|<path>]]</system-out>` としてリンクします。GitLab CI はこれをパイプラインのテストレポートに表示します。パスは `$CI_PROJECT_DIR` からの相対パスで、それが未設定の場合はプロジェクトルートからの相対パスです。その外にあるスクリーンショットにはリンクが付きません。
- 2 回目の Ctrl-C でもファイルの書き込みは行われるため、新しいレポートの横に前回の実行のファイルが残ることはありません。

#### `markdown`

レポートと同じ場所に `summary.md` を書き込みます。

```ts
reporters: ['list', 'markdown'],
```

`junit` と同じことを、2 回目の Ctrl-C の扱いも含め、`summary.md` について [`renderMarkdownReport`](#rendermarkdownreport) を通じて行います。

<a id="rendermarkdownreport" />

##### `renderMarkdownReport`

`markdown` レポーターが書き込む Markdown ページとしてレポートをレンダリングします。独自のレポーターで同じページを別の場所に投稿できます。

```ts
import { renderMarkdownReport, type Reporter } from 'e2e';

const reporter: Reporter = {
  name: 'wiki',
  async onRunFinished(run) {
    const page = renderMarkdownReport(run.report, { traces: run.traces });
    await fetch('https://wiki.example.test/runs', { method: 'POST', body: page });
  },
};
```

- `traces` は、結果 ID によって各ブロックをそのトレースページにリンクします。
- [`@e2e-dev/github`](/github) は、GitHub Actions 向けのそのようなレポーターです。

#### `github()`

`@e2e-dev/github` は、GitHub Actions から実行結果を 1 つのプルリクエストのコメントとして投稿し、再実行時にも最新の状態に保ち、同じテキストをジョブサマリーに書き込みます。

```ts
import { github } from '@e2e-dev/github';

const reporter = github({ key: 'chromium' });
```

- `key` は、マトリックスのようにワークフロー、ジョブ、プロジェクトが同じ場合に、あるジョブのコメントを別のジョブのコメントと区別します。指定しない場合、1 つのジョブのマトリックスのレプリカが 1 つのコメントを共有し、最後に完了したものが優先されます。実行 ID は決して使わないでください。再実行時に古いコメントを見つける必要があるためです。キーはコメントの見出しにも名前として使われます：`e2e chromium: 77 passed`。
- トークン、イベント、リポジトリは実行の完了時に読み取り、設定の読み込み時には読み取りません。
- `--last-failed` を指定すると、再実行を [`lastRun`](#onrunfinished) に統合し、両方の実行を 1 つのコメントとして表示します。
- セットアップと権限については[プルリクエストのコメント](/github)を参照してください。

#### `htmlReporter()`

`@e2e-dev/html-reporter` は、実行結果をブラウザで開く 1 つのページとして書き出します。ステータスタブと検索ボックス付きでファイルごとにテストが並び、各テストについてその試行、エラー、ステップ、スクリーンショット、動画が表示されます。

```ts
import { htmlReporter } from '@e2e-dev/html-reporter';

const reporter = htmlReporter({ media: 'embed' });
```

- レポートと同じ場所に、レポートドキュメントを埋め込んだ `report.html` を書き込みます。このページはサーバーなしでディスクから開けます。
- `media` は、スクリーンショット、動画、ダウンロードの扱いを決めます。

  | `media` | ページの内容 | 共有方法 |
  |---|---|---|
  | `'link'`（デフォルト） | `<output>/results/` から相対パスでリンクします | 出力ディレクトリを 1 つの CI アーティファクトとしてまとめて保持します |
  | `'embed'` | それらを内包するため、1 つのファイルでレポート全体になります | ファイルを送ります。デバイスの動画があると 1 分あたり数十メガバイトになります |
  | `'none'` | それらを除外し、テキストのみを表示します | ファイルを送ります |

  ダウンロードのリンクは、ファイルを開くのではなく保存します。PDF や zip のように、ランナーがシークレットをスキャンできなかったダウンロードは埋め込みページには含まれず、ホスト型ブラウザやデバイスサービスが保持する動画はそこへのリンクのままになります。
- `outputFile` は、プロジェクトルートからのパスとして、ページを別の場所に置きます。
- ページには、それを書き込んだ実行のみが表示されます。`--last-failed` の後では、引き継いだ失敗を除いた再実行のテストが、`e2e explore` の下では、発見事項を除いた探索が表示されます。
- テストはツリーとして一覧表示されます。各ファイル、その describe ブロック、そしてそのテストの順で、失敗したものが先に表示されます。ファイルのパスを選択すると、そのテストが折りたたまれます。
- 各ステップには、試行の動画内での開始位置が表示されます。時刻を選択するとそこから動画が再生され、動画が再生中のステップはハイライトされたままになります。動画のタイムラインには各ステップの開始位置がマークされ、速度ボタンで 0.25× から 4× まで切り替えられます。5 秒未満の録画はスロー再生で始まります。スマートフォンの録画は、ステップの上ではなく横に配置されます。
- 期待値と受信値を報告する失敗したアサーション（たとえばロケーターのアサーション）は、異なる文字をマークしてそれらを表示します。テストファイルがプロジェクト内にある場合、失敗には失敗した呼び出しの周辺のコードが表示され、各ステップを開くとそれを実行したコードが表示されます。このためにページは各ステップの周辺のテストファイルの数行を保持するため、共有されたレポートでもそれらが表示されます。
- 失敗した試行のエラーにある **copy prompt** は、コーディングエージェント向けに失敗内容をコピーします。エラー、ステップ、失敗したステップが行ったこと、そしてトレースページ、画面ツリー、スクリーンショット、動画のうち存在するもののプロジェクトルートからのパスが含まれます。
- エージェントステップには、その説明、実行したアクション、モデル、トークンとコスト、キャッシュからリプレイされたかどうか、最後のターンが表示されます。
- ページはシステムのライトテーマまたはダークテーマに従います。上部の太陽と月のアイコンでテーマを固定でき、ブラウザはその選択を開くすべてのレポートで保持します。

### カスタムレポーター

レポーターオブジェクトは、`name` と少なくとも 1 つのハンドラーを持ちます。ライブの進捗には `onEvent` を、最終的なレポートとアーティファクトの処理には `onRunFinished` を使用してください。

```ts title="e2e.config.ts"
import type { E2EConfig, Reporter } from 'e2e';
import { web } from '@e2e-dev/web';

const upload: Reporter = {
  name: 'upload',
  async onRunFinished(run) {
    const response = await fetch('https://example.test/runs', {
      method: 'POST',
      body: JSON.stringify(run.report),
    });
    const { url } = (await response.json()) as { url: string };
    return [{ label: 'Results', text: url }];
  },
};

export default {
  targets: [{ engine: web(), app: { url: 'localhost:3000' } }],
  reporters: ['list', upload],
} satisfies E2EConfig;
```

| メンバー | 型 |
| --- | --- |
| [`name`](#name) | `string` |
| [`onEvent`](#onevent) | `(event: RunEvent) => void` |
| [`onRunFinished`](#onrunfinished) | `(run, signal) => Promise<…>` |

```ts
interface Reporter {
  readonly name: string;
  onEvent?(event: RunEvent): void;
  onRunFinished?(run: FinishedRun, signal: AbortSignal): Promise<ReporterSummary | void>;
}
```

キャッシュされたステップは、記録がその情報を持つ場合、`report.json` とトレースページで `cache.recordedBy: { provider, model }` を公開します。古い記録にはこれがありません。コンソールは、その識別情報が設定されたモデルと異なる場合にのみ `replayed · recorded with provider/model` を出力します。マルチエージェントの実行や、モデルが実行のヘッダーにない固定エージェントについては表示されません。

#### `name`

診断におけるレポーターのラベルです。必須で、空であってはいけません。

```ts
name: 'upload',
```

#### `onEvent`

すべての実行イベントを、発生と同時にプレーンな JSON として受け取ります。

```ts
onEvent(event) {
  switch (event.type) {
    case 'test-finished':
      console.log(event.result.test.title, event.result.status);
      break;
    default:
  }
},
```

イベントの一覧は[イベント](#events)にあります。

<Note>
`onEvent` はブロックしてはならず、スローしてもいけません。時間のかかる処理は `onRunFinished` で行ってください。スローすると、そのレポーターは実行の残りの間隔離され、レポーター、イベントの種類、エラーを示す 1 行が stderr に出力されます。実行の結果は変わりません。
</Note>

#### `onRunFinished`

レポートが書き込まれ、ターミナルのサマリーが出力された後に、完了した実行と `AbortSignal` を受け取って 1 回実行されます。

```ts
async onRunFinished(run, signal) {
  await fetch('https://example.test/runs', { method: 'POST', body: JSON.stringify(run.report), signal });
  return [{ label: 'Results', text: 'https://example.test/runs/0192c' }];
},
```

```ts
interface FinishedRun {
  readonly report: Report;                 // the report-1 document, as written
  readonly status: RunStatus;              // report.run.status
  readonly exitCode: RunExitCode;
  readonly projectRoot: string;            // what the terminal shows paths relative to
  readonly reportPath: string | undefined; // absent when the write failed
  readonly artifactsRoot: string;          // what the report's artifact paths are relative to
  readonly aiTracePath: string | undefined;
  readonly traces: ReadonlyMap<string, string>;      // result id -> its trace page, from the project root
  readonly lastRun?: Report;               // with --last-failed, the report the rerun selected from
  redact(text: string): string;            // masks the config's fixed secret values (not provider-resolved ones) in text from outside the report
}

type ReporterSummary = readonly { label: string; text: string }[];
```

- すべてのレポーターは並行して実行され、それぞれに 1 分の期限があります。
- タイムアウト、例外、無効な戻り値は stderr に報告されます。実行のステータス、終了コード、レポートは変わりません。
- 1 回目の Ctrl-C では、レポーターは引き続き完了まで実行されます。2 回目の Ctrl-C では、[`junit`](#junit) と [`markdown`](#markdown) を除き、それらの完了を待たなくなります。
- `signal` は、予算を使い切ったとき、または実行が強制停止されたときに中断されます。
- ランナーは、`onRunFinished` を呼び出す前にトレースページ `results/<test>/trace.md` を書き込みます。

<Note>
すべてのリクエストとタイマーに `signal` を渡してください。CLI は放棄したレポーターを待たずに終了するため、その処理は途中で打ち切られます。[`e2e/runner`](/reference/runner) の下では、その処理によってプロセスが終了しなくなります。
</Note>

##### サマリー行

レポーターが解決する行は、`list` のサマリーの下に、そのサマリー自身の行と同じレイアウトで出力されます。`json` レポーターはこれを含めません。

```
   Test Files  2 passed (2)
        Tests  6 passed (6)
     Start at  14:02:11
     Duration  8.41s

        JUnit  .e2e/junit.xml
      Results  https://example.test/runs/0192c…
```

##### アーティファクト

- レポート内のアーティファクトのパスは、`artifactsRoot` からの相対パスで、POSIX 形式です。
- `path`、`size`、`sha256` は省略可能です。ファイルが作成されなかったアーティファクトや、マスキングによって伏せられたアーティファクトは、これらなしで記録されます。読み取る前に `path` の有無を確認してください。
- ホスト型サービスが保持する動画は、`path` の代わりに `http(s)` の `url` を持ちます。

##### `--last-failed` による再実行

- 再実行自体のレポートでは、除外したテストが未選択として列挙されます。`@e2e-dev/github` がプルリクエストのコメントを最新に保つように 1 か所を最新に保つレポーターは、再実行を `lastRun` に統合して両方の実行を 1 つとして表示します。
- 再実行が対象とすべきだったものの、別のフィルターによって除外されたテストは、再実行の `run.carried` に含まれます。そこには、それを報告した過去の実行から、テストの最後の結果、その試行が属するシリアルグループ、そのテストをスコープに含む `beforeAll` または `afterAll` の失敗が保持されます。
- 統合では、未選択の結果の代わりに引き継がれた結果が表示され、引き継がれた失敗やフックのエラーは結果に反映されます。
- 両方のレポートが参照するアーティファクトは、`artifactsRoot` 配下のディスク上にあります。

<a id="test-filters" />
##### テストフィルター

- [テストフィルター](/filters)が除外したテストは、`skip.cause` が `filtered` で、`skip.filter` がそのフィルターを示す、未選択の結果になります。
- `run.filters` は、呼び出されたフィルターごとに 1 つの記録を順に保持します：`name`、`candidates`、`excluded`（シリアルグループがメンバーを取り戻した後に除外されたテスト）、`note`（1024 文字で切り詰められます。失敗またはタイムアウトしたフィルターでは、その理由を示す警告です）、`outcome` です。`outcome` はフィルターが何も除外しなかった場合に設定され、スローしたか無効な結果を返した場合は `failed`、5 分を超えて実行された場合は `timed-out` になります。対象のテストがないフィルターは呼び出されず、記録もありません。
- フィルターの判断が終わると、`run.changes` は、フィルターが判断した変更を件数で保持します：`base`（マージベース）、`files`、`skipped`（`no files changed since abc1234` のような、フィルターが実行されなかった理由）です。フィルターが設定され、実行で `--changed-since` が指定された場合に存在します。ただし、`e2e explore` の下、`--watch` の再実行、フィルターの判断前に実行が終了した場合を除きます。`--last-failed` の場合や、判断するテストがない場合は、`skipped` のみを保持します。
- 存在しないコミットを指す ref に対する `INVALID_CHANGED_SINCE` のような、フィルターの判断中の失敗は、`phase` が `filter` として `run.errors` に含まれます。不正な形式の `changedSince` は `phase` が `config` になります。

## イベント

`onEvent` は以下のいずれかのファクトを受け取ります。各イベントには、シーケンス番号 `seq` と ISO タイムスタンプ `at` もあります。

```ts
type RunEventFact =
  | { type: 'run-started'; runId; projectId; projectRoot; artifactsRoot; ci; targets; agents?; model?; judge? }
  | { type: 'plan'; total; files: { file; target; tests }[] }
  | { type: 'notice'; target; message }
  | { type: 'output'; target; pair; stream: 'stdout' | 'stderr'; text }
  | { type: 'setup'; step: SetupStep; state: 'started' }
  | { type: 'setup'; step: SetupStep; state: 'finished'; durationMs; outcome?: 'reused' | 'failed' | 'timed-out' }
  | { type: 'test-started'; testId; agent; repeat; title; file; serialId; target }
  | { type: 'step'; testId; agent; repeat; target; progress: StepProgress }
  | { type: 'test-finished'; result: RunEventResult }
  | { type: 'serial-group'; group: SerialGroupRecord }
  | { type: 'explore'; progress: ExploreProgress }
  | { type: 'run-error'; error: SerializedError }
  | { type: 'run-interrupted'; mode: 'graceful' | 'forced' }
  | { type: 'run-stopped'; failures; limit }
  | { type: 'run-finished'; status; exitCode; reportPath?; aiTracePath?; traces? };
```

- `run-started` が最初に、`run-finished` が最後に来ます。
- `run-started` の `targets` は、実行が `--target` で選択したターゲットを設定の順序で示します。`--target` がない場合、または `--target` が不明なターゲットを指定した場合（実行は `UNKNOWN_TARGET` で失敗します）は、設定されたすべてのターゲットを示します。レポートの `run.targets` には、引き続き設定されたすべてのターゲットが列挙されます。
- `run-started` の `judge` は実行エージェントのジャッジモデルで、判定に `model` 以外のモデルを使う場合にのみ存在します。
- `setup` は、テストの開始前の作業を囲みます。その `step.kind` は `collect`、`filter`（`name` で示される 1 つの[テストフィルター](/filters)）、`prepare`、`service`、`app` のいずれかです。`app` ステップの `url` は、その準備状況のプローブがポーリングする URL で、空きポートが埋め込まれ、userinfo やクエリは含まれません。`outcome` は、サービスやアプリのコマンドがすでにその URL を提供しているプロセスにアタッチした場合は `reused`、フィルターがスローしたか無効な結果を返した場合は `failed`、フィルターが 5 分を超えて実行された場合は `timed-out` です。
- `notice` は、その行が何についてのものかを `target` で示します：ターゲット、`app`、`collect`、テストフィルターの進捗とサマリーについての `filter`、または `run` です。
- `output` は、テストが stdout または stderr に行った 1 回の書き込みです。`pair` はその時点で実行中のテストを示し、テストの合間では undefined です。
- `test-finished` は、すべての試行のアーティファクトを含む、完全な結果の記録を持ちます。
- `explore` は `e2e explore` の実行でのみ現れます：`started`、`planning`、`step-started`、`step-finished`、`finding`、`finished` です。そのすべての記録はレポートの `run.explore` にあります。
- 新しいイベントの種類は随時追加されます。既知の種類を処理し、それ以外は無視してください。`switch` の `default` 分岐は空のままにしてください。

### テストと試行

- 複数のエージェントに固定されたテストは、エージェントごとに 1 回開始と終了を行うため、実行中の状態はテスト ID、ターゲット、エージェントの組み合わせをキーにしてください。
- 通常のテストは、その組み合わせについて `test-started` を 1 回発行します。シリアルグループのメンバーは、実行するグループの試行ごとに発行します。
- リトライを区別するには、ステップ進捗の[識別情報](#step-progress)を使用してください。
- いずれかのステップの前に失敗した試行は、ステップの進捗を発行せず、最終的な結果に表示されます。

<Note>
シークレットは、イベントが構築される前にマスキングされます。エラーメッセージとスキップ理由からは、ANSI エスケープと、タブ、改行、`\r\n` の改行の `\r` 以外の制御文字が取り除かれるだけなので、信頼できないものとして扱ってください。
</Note>

### ステップの進捗

`phase` フィールドがステップの進捗を表します。

- `start` と `end` はステップの境界を示します。
- `event` は、完了したモデルのターン、ツール呼び出し、または観測を報告します。
- `activity` は、作業の開始を報告します：`observe`、`action`、`model` のいずれかです。
- `replay` は、キャッシュからのリプレイが開始したとき、またはエージェントに制御を戻したときに報告します。

```ts
type StepProgress = (
  | { phase: 'start'; kind: StepKind; api: string; label: string }
  | {
      phase: 'end';
      kind: StepKind;
      api: string;
      label: string;
      status: 'passed' | 'failed' | 'blocked' | 'timed-out' | 'cancelled';
      durationMs: number;
      modelCalls: number;
      error?: SerializedError;
      explanation?: string;
    }
  | { phase: 'event'; api: string; event: StepEvent }
  | { phase: 'activity'; api: string; activity: 'observe' | 'model' | 'action' }
  | { phase: 'replay'; api: string; active: boolean }
) & { identity?: StepProgressIdentity };
```

`end` フェーズの `error` と `explanation` はマスキングされています。`blocked` と `cancelled` を含め、その `status` を保持してください。パスしなかったステップをすべてプロダクトの不具合として扱わないでください。

ランナーが発行するすべてのステップフェーズには `progress.identity` が含まれます。

```ts
{ attemptId: string; attemptIndex: number; stepId: string; stepIndex: number }
```

- ID は最終的なレポートと一致します。どちらのインデックスも 0 から始まります。
- リトライでは新しい試行 ID とより大きな試行インデックスが付き、ステップのインデックスは再び 0 から始まります。
- シリアルグループのメンバーは、グループの試行 ID とインデックスを共有します。各メンバーのステップ ID は区別されたままです。
- ネストしたステップも含め、start、activity、event、replay、end の各フェーズを照合するには `stepId` を使用してください。
- レポーターが古いストリームも受け付けられるよう、型の上では `identity` は省略可能です。

## `--reporter` がレポーターオブジェクトに与える影響

`--reporter` が置き換えるのは組み込みレポーターのみです。設定されたレポーターオブジェクトは引き続き実行されます。

<CodeGroup>
```bash npm
npx e2e run --reporter list,junit
```

```bash pnpm
pnpm exec e2e run --reporter list,junit
```

```bash bun
bunx e2e run --reporter list,junit
```
</CodeGroup>

- レポーターオブジェクトのみを持つ設定には、組み込みのターミナル出力がありません。実行エラーは引き続き stderr に、それぞれ `CODE: message` の形式で出力されます。

## レポーターが実行される場所

ハンドラーはランナーのプロセスで実行されます。ワーカーも設定を読み込むため、レポーターの構築には副作用があってはいけません。

- トークンの読み取りやリクエストの開始は、ハンドラー内で行ってください。
- レポーターを追加しても、[キャッシュされたトレース](/cache#what-must-match)は有効なままです。

## 型

`Reporter`、`FinishedRun`、`ReporterSummary`、`Report`、`RunEvent`、`RunEventOf` はメインのエントリーポイントからエクスポートされており、`renderMarkdownReport(report, options)` も同様です。
