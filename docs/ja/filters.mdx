`--changed-since <ref>` を指定すると、テストフィルターはその ref 以降の変更が影響しえないテストを除外し、
失敗する可能性が最も高いテストのファイルから先に開始します。デシジョンフィルターは、Jev などの
[デシジョンモデル](/decision-models)に各テストについて問い合わせます。このフラグがない場合は、
`main` やローカルと同様に、すべてのテストが実行されます。

## デシジョンフィルターを追加する

<CodeGroup>
```bash npm
npm install -D @e2e-dev/decision ai
```

```bash pnpm
pnpm add -D @e2e-dev/decision ai
```

```bash bun
bun add -d @e2e-dev/decision ai
```
</CodeGroup>

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { web } from '@e2e-dev/web';
import { gateway } from 'ai';
import { decisionFilter } from '@e2e-dev/decision';

export default {
  targets: [{ engine: web(), app: { url: 'http://localhost:3000' } }],
  filters: [decisionFilter({ model: gateway.decisionModel('typesafe-ai/jev') })],
} satisfies E2EConfig;
```

CI では、プルリクエストで `--changed-since` を渡し、e2e のステップに
AI Gateway のキーを渡します。

```yaml title=".github/workflows/e2e.yml"
steps:
  - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
    with:
      fetch-depth: 0
  # ...
  - run: npx e2e run ${{ github.event_name == 'pull_request' && format('--changed-since origin/{0}', github.base_ref) || '' }}
    env:
      AI_GATEWAY_API_KEY: ${{ secrets.AI_GATEWAY_API_KEY }}
```

このフラグは `pull_request` の実行にだけ付くため、push、マージキュー、
スケジュール実行ではフラグが渡されず、すべてのテストが実行されます。
`pull_request_target` では決して渡さないでください。その実行はシークレットを保持しており、
フォークの差分がモデルを言いくるめてテストを除外させる可能性があります。`fetch-depth: 0` により、
ベースブランチとマージベースがチェックアウトに含まれます。これらがないと、実行は
`INVALID_CHANGED_SINCE` で失敗します。

変更とは、ref と `HEAD` のマージベースから差分のあるすべてのファイルで、
コミットされていないファイルや追跡されていないファイルも含みます。モデルが読むのは、
コミットが変更した内容の差分、テストファイル、そしてセッションを保存するセットアップファイルで、
シークレットはマスクされます（ただし、シークレットプロバイダーが返す値は除きます）。
作業ツリーだけが変更したファイル（コミットされていないファイルや追跡されていないファイル）は、
名前だけが渡され、内容は決して渡されません。そのため、CI のステップが書き込んだファイルが
モデルに届くことはありません。

フィルターは、モデルがテストとそのセットアップの両方について、影響を受ける可能性を
20% 未満と評価した場合にそのテストを除外します。モデルが判断できないテストは実行され、
フィルターのメモにその理由が示されます。理由は、60 kB を超える差分、差分と一緒に送るには
大きすぎるテストファイルやセットアップファイル、または一部の呼び出しの失敗です。
フォークからのプルリクエストでキーがない場合のように、すべての呼び出しが失敗すると、
フィルターは失敗します。実行は警告を出してすべてのテストを実行し、テストファイル、
セットアップファイル、または保存済みのスクリーンショットが変更されたテストを先に開始します。
git がない、プロジェクトがリポジトリ内にない、または ref が `HEAD` と履歴を共有していないために
git が変更を測定できない場合、実行は `INVALID_CHANGED_SINCE` で失敗します。
このフィルターには `ai` 7.0.134 以降が必要です。

`boolean` の質問に答える[デシジョンモデル](/decision-models)であれば、
どれでも使えます。たとえば TypeSafe を直接経由した Jev として、
`@ai-sdk/typesafe-ai` の `typeSafeAi.decisionModel('jev-latest')` を、
`TYPESAFE_AI_API_KEY` を設定して使えます。`providerOptions` は、
`{ gateway: { zeroDataRetention: true } }` のように、すべての呼び出しに渡されます。

## ローカルでプレビューする

<CodeGroup>
```bash npm
npx e2e list --changed-since origin/main
```

```bash pnpm
pnpm exec e2e list --changed-since origin/main
```

```bash bun
bunx e2e list --changed-since origin/main
```
</CodeGroup>

`e2e list` は、フィルターが除外する各テストを理由とともに表示します。アプリは起動せず、
実行時と同じモデル呼び出しを行います。先にコミットしてください。デシジョンフィルターは
コミットが変更した内容だけを読みます。

## 常に実行されるもの

- 実行に `--changed-since` がない場合、またはマージベース以降に変更された
  ファイルがない場合は、すべてのテスト。
- `--last-failed` による再実行。そのため `e2e run || e2e run --last-failed` は安全です。
  また、最初の実行後のすべての `--watch` による再実行。

デシジョンフィルターは、次のものも実行します。

- 変更されたテストファイル、または保存済みのスクリーンショットが変更されたテストファイル内の
  テスト、およびそのようなセットアップファイルのセッションを使うテスト。
- 実行が読み込んだ設定が（名前に関係なく）変更された場合、または `e2e.config.ts`
  （`.mts`、`.js`、`.mjs`）という名前のファイル、Gradle の `libs.versions.toml`、
  ロックファイルが、プロジェクトのディレクトリ、その内部、またはワークスペースのルートのような
  その上位のディレクトリで変更された場合は、すべてのテスト。ロックファイルは
  `pnpm-lock.yaml`、`Podfile.lock`、`gradle.lockfile`、`Gemfile.lock`、`go.sum`、
  `Cargo.lock` などの名前で識別されます。それ以外のファイルや、兄弟プロジェクトの
  ファイルは、モデルが判断します。

例外を投げたフィルター、`{ exclude, relevance?, note? }` 以外のものを返したフィルター、
または 5 分を超えて実行されたフィルターは何も除外せず、その旨の警告が表示されます。
次のフィルターは、渡されたすべてのテストを引き続き判断します。失敗したフィルターは、
[独自のフィルターを書く](#write-your-own)のように、投げたエラーが `relevance` を持っている場合を除き、
スコアも付けません。5 分を超えて実行されたフィルターは破棄され、その後に投げたものは
何も考慮されません。

ほかの CI サービスでは、プルリクエストのビルドでのみ `--changed-since origin/main` を渡し、
マージベースに届くだけの履歴を取得してください。GitLab については、
[影響を受けるテストだけを実行する](/ci/gitlab#run-only-affected-tests)を参照してください。
`--shard` を指定すると、各マシンのフィルターはそのマシンの担当分だけを判断します。

## 可能性の高いものから開始する

デシジョンフィルターは残した各テストにスコアを付け、各ターゲットは可能性の最も高いテストの
ファイルから開始します。これにより失敗が早く現れ、`--max-failures` を使う場合や、
CI のデフォルトであるワーカー 1 つの場合に最も時間を節約できます。

| テスト | スコア |
| --- | --- |
| テストファイル、セットアップファイル、または保存済みのスクリーンショットが変更された | 100% |
| その他のすべてのテスト | テスト自身の評価とセットアップの評価のうち高い方。モデルが評価しなかった場合は 50% として扱います |

- ファイルは 4 つの帯で開始されます。75% 以上、50% 以上 75% 未満、25% 以上 50% 未満、
  25% 未満です。ファイルは、その中で最も可能性の高いテストの帯に入ります。
- ワーカーが複数ある場合、帯の中では
  [タイミング履歴](/ci#cache-the-timings-history)上で最も長いファイルが最初に開始します。
  時間の記録がないファイルは、記録のあるファイルより前に開始します。
- ターゲットは最良のファイルの帯の順に並び、同順位は設定の順になります。各ターゲットは
  自身のファイルをその順に開始します。ターゲットのセットアップテストは、引き続き最初の
  テストファイルが開始する前に完了します。
- 短くて可能性の高いファイルが、長くて可能性の低いファイルより前に開始することがあるため、
  複数のワーカーでは、全体を完了する実行の終了が遅くなる場合があります。レポートは元の順序を保ち、
  `e2e list` は順序を表示しません。

自分で書くフィルターは、[独自のフィルターを書く](#write-your-own)のように、`relevance`
でテストにスコアを付けます。

## 表示される内容

- **ターミナル**: フィルターごとに 1 行、たとえば
  `decision kept 7 of 77 tests, left out 70 (1 call, 17.6k tokens, $0.0007)` のように表示されます。
  デシジョンフィルターのメモの末尾には、その消費量が示されます。モデル呼び出し数、トークン数、
  そして AI Gateway のようにプロバイダーが報告する場合はコストです。スコアによってテストが
  複数の帯に分かれた場合は、`ranked 7 of 7 tests by relevance, likeliest first` のような行が
  続きます。サマリーには `Left out` の行が続きます。フィルターが実行するものを何も残さなかった場合、
  実行は成功し、アプリは起動しません。
- **[プルリクエストのコメント](/github)と `summary.md`**: 見出し
  `7 passed, 70 left out by filters` と、テストとその理由を示す折りたたまれた表です。
- **`junit.xml` と `report.json`**: 除外された各テストはスキップされたケースとなり、
  レポートでは `run.filters` と `run.changes` と並んで `skip.filter` が記録されます。
  [レポーター](/reference/reporters#test-filters)を参照してください。

## デシジョンフィルターを調整する

デシジョンフィルターをラップすると、判断する対象を変更できます。次の例は、`infra/` が
変更されたときにすべてのテストを実行し、これらのテストが到達しない `apps/mobile/` を
変更から除き、`smoke` テストを常に実行します。

```ts title="tuned-filter.ts"
import type { TestFilter } from 'e2e';
import { gateway } from 'ai';
import { decisionFilter } from '@e2e-dev/decision';

const decision = decisionFilter({ model: gateway.decisionModel('typesafe-ai/jev') });

export const tuned = {
  name: 'decision',
  filter(tests, context) {
    if (context.changes.files.some((file) => file.startsWith('infra/'))) return { exclude: {}, note: 'infra/ changed' };
    const judged = tests.filter((test) => !test.tags.includes('smoke'));
    const files = context.changes.files.filter((file) => !file.startsWith('apps/mobile/'));
    if (files.length === 0) return { exclude: Object.fromEntries(judged.map((test) => [test.id, 'only apps/mobile/ changed'])) };
    return decision.filter(judged, { ...context, changes: { ...context.changes, files } });
  },
} satisfies TestFilter;
```

`decisionFilter(...)` の代わりに `tuned` を `filters` に入れてください。特定のプルリクエストで
すべてのテストを実行するには、`all-tests` ラベルが付いているときに `--changed-since` を
省きます。ラベルの追加で実行が始まるように、イベントに `labeled` を追加します。

```yaml title=".github/workflows/e2e.yml"
on:
  pull_request:
    types: [opened, synchronize, reopened, labeled]
# ...
      - run: npx e2e run ${{ github.event_name == 'pull_request' && !contains(github.event.pull_request.labels.*.name, 'all-tests') && format('--changed-since origin/{0}', github.base_ref) || '' }}
```

## 独自のフィルターを書く

フィルターは `{ name, filter }` です。`filter` はテストと変更を受け取り、除外するテストを
それぞれの理由とともに返します。また、残りのテストに `relevance` で 0 から 1 のスコアを
付けることもできます。次の例は、変更されたパスをテストのタグに対応付け、変更が及ぶ領域の
テストを先に開始します。

```ts title="areas-filter.ts"
import type { TestFilter } from 'e2e';

/** The test tags each part of the app reaches, by path from the repository root. */
const AREAS: Readonly<Record<string, readonly string[]>> = {
  'src/todos/': ['todos'],
  'src/auth/': ['auth', 'smoke'],
  'src/checkout/': ['checkout'],
};
/** Every tag an area reaches; a test without one always runs. */
const AREA_TAGS: ReadonlySet<string> = new Set(Object.values(AREAS).flat());

export const areas = {
  name: 'areas',
  filter(tests, { changes }) {
    const reached = new Set<string>();
    let unmapped: string | undefined;
    for (const file of changes.files) {
      const area = Object.keys(AREAS).find((prefix) => file.startsWith(prefix));
      if (area === undefined) unmapped = file;
      else for (const tag of AREAS[area] ?? []) reached.add(tag);
    }
    const exclude: Record<string, string> = {};
    const relevance: Record<string, number> = {};
    for (const test of tests) {
      const tags = test.tags.filter((tag) => AREA_TAGS.has(tag));
      if (tags.some((tag) => reached.has(tag))) relevance[test.id] = 1;
      else if (tags.length > 0 && unmapped === undefined) exclude[test.id] = 'the change reaches none of its areas';
    }
    if (unmapped === undefined) return { exclude, relevance };
    return { exclude, relevance, note: `${unmapped} is in no area, so areas leaves nothing out` };
  },
} satisfies TestFilter;
```

これをデシジョンフィルターの前に置くと、モデルは `areas` が残したテストだけを
判断します。

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { web } from '@e2e-dev/web';
import { gateway } from 'ai';
import { decisionFilter } from '@e2e-dev/decision';
import { areas } from './areas-filter.ts';

export default {
  targets: [{ engine: web(), app: { url: 'http://localhost:3000' } }],
  filters: [areas, decisionFilter({ model: gateway.decisionModel('typesafe-ai/jev') })],
} satisfies E2EConfig;
```

- 名前を挙げなかったテストはすべて実行されます。また、名前を挙げたテストでも、
  同じシリアルグループ内の別のテストが実行される場合は実行されます。
- `relevance` はテスト ID と 0 から 1 の数値を受け取ります。どのフィルターも名前を挙げなかった
  テストは 0 として扱われ、複数のフィルターが名前を挙げたテストは最も高い値を保ちます。
  それ以外のものは、`exclude` と同様にフィルターを失敗させます。
- 失敗したフィルターでもスコアを付けられます。結果と同じ形で同じようにチェックされる
  `relevance` プロパティを持つエラーを投げると、テストに同じようにスコアが付きます。それでも
  失敗としての警告は出され、何も除外されません。デシジョンフィルターはこれを行うため、
  キーのない実行でも、変更が触れるテストが先に開始します。チェックに通らないスコアは破棄され、
  警告にその旨が示されます。
- 各フィルターは、前のフィルターが残したテストだけを判断し、テストが何も残っていない場合は
  呼び出されません。
- すべての呼び出しに `signal` を渡し、モデルに送る内容は `redact` してください。これは
  固定値の各シークレットと認証情報のパスワード、さらにそれらの文字が 8 文字以上連続する部分を
  置き換えます。そのため、パスワードが `Password123!` のときの `Password` のように、
  いずれかと 8 文字を共有するテキストもマスクされます。シークレットプロバイダーが返す値は
  そのまま通過します。
- 処理は `filter` の中で行ってください。ワーカーも設定を読み込みますが、`filter` を
  呼び出すのはランナーだけです。

型については [`TestFilter`](/reference/config#testfilter) を参照してください。
