リプレイキャッシュは、後続のチェックが結果を検証したあとで、`agent.act()` ステップのアクションを記録します。次の実行では、ランナーがそれらのアクションをモデル呼び出しなしでリプレイします。コントロールや期待される最終状態が一致しなくなった場合は、エージェントが現在の画面から処理を引き継ぎます。[セルフヒーリングテスト](/self-healing)を参照してください。

`agent.assert`、`agent.waitFor`、`agent.extract` は常にライブで実行されます。実行サマリーは結果を集計します。

```text
           AI  4.1k tokens · 2 model calls · openai/gpt-6-luna-fast
        Cache  4 replayed · 1 handed off · 1 missed · 1 not saved
```

`not saved` は、合格したテストおよび flaky なテストのステップのうち、合格した試行での [`step.cache.write`](#when-a-recording-is-written) が `unconfirmed`、`no-change`、`not-written` のいずれかであるものを数えます。

## 記録が書き込まれるタイミング

テストの最後に、その結果をチェックしてください。`read-write` モードでは、後続の検証ステップが合格した場合、ランナーは試行の終了時に各 `act` の記録を保存します。最後に 1 つチェックを置けば、それより前のすべての `act` が確認されます。

```ts title="tests/cart.e2e.ts"
import { expect, test } from 'e2e';

test('adds an item', async ({ app, agent, screen }) => {
  await app.open('/cart');

  await agent.act('add one item to the cart');

  await expect(screen.getByRole('status')).toHaveText('1 item');
});
```

| 検証として数えられるもの | 数えられないもの |
| --- | --- |
| `expect(locator).toHaveText(...)` などのロケーターのマッチャー | 単なる値に対する `expect(value).toBe(...)` |
| `expect(browser).toHaveURL(...)` などのエンジンのアサーション | `expect.poll(...)` |
| `locator.waitFor()`、`browser.waitForURL()` | `locator.textContent()` などの読み取り |
| `agent.assert(...)`、`agent.waitFor(...)` | `agent.extract(...)`、別の `act`、試行の合格 |

`step.cache.write` はレポートにのみ含まれ、試行の終了時に記録がどうなったかを示します。

| `step.cache.write` | 意味 |
| --- | --- |
| `saved` | 次の実行のために記録されました。 |
| `kept` | エントリーはそのまま残ります。 |
| `unconfirmed` | 保存されていません。ステップのあとに合格したチェックがありません。テストの最後にロケーターやエンジンのアサーション、または `agent.assert` を置くか、`locator.waitFor()` や `agent.waitFor` で状態を待機してください。 |
| `evicted` | エントリーは削除されました。リプレイが失敗または修復で終わったか、試行が失敗する前にどのチェックもそれを確認しませんでした。 |
| `no-change` | 何も記録されていません。コントロールが現れることも、消えることも、状態が変わることもなく、ルートも同じままでした。変化が[別サイトのフレーム](/browser#reach-into-an-iframe)の中だけで起きたステップもこれに含まれます。このようなステップは毎回ライブで実行されます。 |
| `not-written` | 保存されていません。ストアが書き込みを拒否したか、記録を受け付けませんでした。たとえば、ファイルストアのサイズ上限を超える記録などです。 |

アクションを取らなかったステップは何も記録せず、`write` も報告しません。

失敗した試行でも、失敗より前に検証されたステップは保存されます。未検証のエントリーと、失敗に関わったリプレイは削除されます。失敗しているアサーションを修正する間もセットアップのゴールを記録したままにするには、`locator.waitFor()` などでセットアップの状態を待機してセットアップを終えてください。カスタムストアでこれを行うには `delete` メソッドが必要です。実行をキャンセルした場合、キャッシュは変更されません。

<Accordion title="モデルが応答しなかった失敗">
モデルが応答しなかった失敗だけで終わった試行は、何も削除しません。これらはアプリについて何も示さないためです。

- `MODEL_UNAVAILABLE`: モデルが設定されていないか、GitHub Copilot がそのアカウントにモデルを提供していません。
- `MODEL_PROVIDER_FAILED`: プロバイダーがエラーを返しました。たとえば、キーの欠落や拒否、レート制限、5xx などです。または、リクエストが 120 秒以内に応答を得られませんでした。

そのため、モデルにアクセスできない `read-write` の実行でも記録は保持されます。モデルに到達できなかった `agent.assert` の前にリプレイされたステップも含まれます。

次のものはフローの失敗として数えられます。使用できないモデルの回答 (`MODEL_OUTPUT_INVALID`、`CONTEXT_OVERFLOW`)、拒否 (`MODEL_REFUSED`)、`STEP_TIMEOUT` (リクエストがまだ開いている場合も含む)、そして同じ試行内のその他の失敗 (`afterEach` のアサーションなど) です。
</Accordion>

## 一致が必要なもの

キャッシュエントリーは、1 つのテスト、ターゲット、指示、パラメーターのセット、エージェントに属します。次のいずれかを変更するとミスになります。

- テスト、その `describe` グループ、またはターゲットの名前の変更、あるいはテストファイルの移動
- 指示または通常のパラメーターの変更
- 設定済みの別のエージェントでの実行 (`agent: ['buyer', 'admin']` はそれぞれ 1 つのエントリーを記録します)、またはエージェントの `context` やテストの `agentContext` の変更 (その中のシークレットは名前だけがキーに入ります)
- 別のエンジンへの切り替え、またはプロジェクト ID やアプリのアイデンティティの変更

モデルを変更してもミスにはならず、エンジンをアップグレードしてもミスにはなりません。新しいバージョンが異なる解決をするノードは、リプレイ時にミスになります。

新しいモデルを評価するには `--no-cache` を使ってください。エントリーに来歴がある場合、リプレイは `step.cache.recordedBy` を公開します。古いエントリーや帰属のないエントリーでは省略されます。

タイムスタンプや新しいメールアドレスは毎回ミスになります。そのような値は `unique()` で包んでください。リプレイ時にランナーが現在の値を入れます。

```ts
import { unique } from 'e2e';

const name = `E2E ${Date.now()} Company`;
await agent.act('create a company named {name}', { params: { name: unique(name) } });
await expect(screen.getByRole('heading', { name })).toBeVisible();
```

`unique()` はフローが入力またはチェックするデータに使い、プラン名のようにフローを変える選択肢には通常のパラメーターを使ってください。置換は、URL で表記される形の値 (`%20`、`+`) や、画面上で 1 行に表示される複数行の値にも適用されます。`unique()` の値が別のパラメーターの値と等しいか、その中に含まれる場合、そのステップは記録されません。`step.cache.notRecorded` は `param-collision` となり、次の実行で記録されます。

デプロイごとに変わるプレビュー URL の場合は、[`app.identity`](/reference/config#the-app-under-test) を設定して 1 つのキャッシュのアイデンティティを保ってください。デバイスでは、リプレイはパスとして[画面のタイトル](/reference/mobile#replay-cache-on-a-device)を使います。

## 修正中にテストを再実行する

失敗しているテストを修正している間は、ローカルのデフォルトである `read-write` モードでキャッシュをオンにしておき、書き込みを一切行わない[厳格モード](#fail-on-a-stale-recording)の外で実行してください。`CI` が設定されている場合、未設定のモードは `read-only` になります。失敗した実行でも、失敗より前にチェックが[確認](#when-a-recording-is-written)した記録は保持されます。次の実行では、各リプレイが画面とまだ一致する限り、それらのゴールをモデル呼び出しなしでリプレイします。

1. そのテストだけを、`test(` が始まる行を指定して実行します:
   `npx e2e run tests/cart.e2e.ts:3`。
2. テストの名前を変えたり、合格しているゴールの言い回しを変えたりしないでください。どちらも[ミスの原因](#what-must-match)になります。名前の変更はテスト内のすべてのゴールに、言い回しの変更はそのゴール自体に影響します。
3. リトライが有効な場合 (設定の `retries`、または `CI` の設定)、`--retries 0` を追加してください。テストやその `describe` の `retries` オプションはフラグより優先されます。リトライはリプレイしないため、すべてのゴールをライブで実行します。
4. テストが合格したら、`--no-cache` で 1 回実行してください。すべてのゴールがライブで実行され、記録なしでもエージェントがまだゴールに到達できることを確認できます。

## リプレイの仕組み

1. 開始画面をチェックします。同じルートである必要があります。
2. 記録された各コントロールをロール、名前、テスト ID、周囲のコンテキストで見つけ、そのアクションを繰り返します。ランナーは見つからないコントロールを待機し、一致が曖昧な場合は停止します。
3. 最終的なルートと、元のステップが変更したものをチェックします。現れたコントロール (チェック、選択、展開、押下の状態を含む) と、消えたコントロールです。
4. モデル呼び出しなしで完了するか、何が実行されたか、なぜリプレイが停止したかの記録とともにエージェントに続行させます。

入力された値は記録どおりにリプレイされます。シークレットの入力は、名前で現在の値を解決し、再度認可を経ます。

リプレイは、記録された変化が表示された時点で完了します。これは、その下のコンテンツが読み込まれる前の場合があります。ステップのあとに読み込まれるコンテンツをチェックするには、画面を 1 回だけ判定する `agent.assert` ではなく、コンテンツを待機する `agent.waitFor` を使ってください。

<Accordion title="同じルートとみなされるもの">
ルートは、オリジン、パス、クエリで構成されます。レコード ID とフラグメントは含まれません。パスやクエリ内の ID、トークン、タイムスタンプ、キャッシュバスターは ID のプレースホルダーとして読まれるため、`/orders/42?t=1727780000` と `/orders/7?t=1727780999` は 1 つのルートです。

それ以外のクエリの値はすべてルートの一部です。`?mode=safe` と `?mode=unsafe` は異なり、`/companies` と `/companies?tab=notes`、あるいは新しいトラッキングパラメーターも異なります。`/products/summer-sneaker` と `/products/winter-boot` も別のルートです。

アプリ自身のオリジン上の場所はパスで比較されるため、記録は同じ `app.identity` を共有するプレビューデプロイメントにもアプリに追従します。それ以外のオリジンのページは別のルートです。
</Accordion>

<Accordion title="終了チェックが画面を読む方法">
- リプレイ中に、記録された変化が少なくとも 1 つ起きる必要があります。アクションの前からすでに画面にある結果は何も証明しません。ステップの最後のアクションが別のルートに移動した場合は、その移動が証拠になります。
- リプレイが発生させ、記録には一度も現れなかったアラートは、リプレイを停止させます。Web エンジンは Next.js App Router のルートアナウンサーを監視しないため、そのタイトルのエコーは数えられません。
- 日付、所要時間、ID など、実行ごとに異なるテキストは、ステップの差分のどちらかの側 (何かが現れた側か消えた側か) に安定した変化がある間はスキップされます。ほかに何もない場合は保持され、値が変わるとリプレイはエージェントに引き継がれます。アラート内では、プレースホルダーとして読まれます。アプリが生成するテスト ID (`node-<uuid>`) でしか識別できないノードも同様にスキップされます。保持された場合、現れたノードはそのパターンを持つ任意の ID でよく、消えたノードは正確な ID で引き続きチェックされます。
- `3 records imported` のように数える対象を示すカウントは、ステップが操作した画面にそれを表示させた場合、リプレイ時にも同じである必要があります。単に変化しただけのカウント (`41 items` から `42 items`) や、ステップが移動した先の画面にあるカウントは、それ自体の側の差分に安定した変化がある場合にのみスキップされます。そうでない場合、反対側に安定した変化があってもカウントは残ります。バッジのような数字だけのものは、上記のテキストのルールに従います。
- 名前のないコントロールは、同じ名前付きの行、リスト項目、グループ内にある同種の名前のないコントロールの中での位置で見つけられます。生成されたテスト ID でしか識別できないコントロールは、同様に ID のパターンで見つけられるか、そのパターンを持つ唯一のものだった場合に見つけられます。
</Accordion>

## ステップがリプレイされなかった理由

各 `act` ステップは `step.cache` を報告します。そのステップでキャッシュがオフの場合は存在しません。`agent.act()` はこれを `write` なしの `result.cache` として返し、[トレースページ](/debugging#traces)はステップの下に表示します。

| 実行サマリー | `step.cache.mode` | 意味 |
| --- | --- | --- |
| `replayed` | `self-finalized` | 記録がモデル呼び出しなしで完了しました。 |
| `handed off` | `agent-concluded` | リプレイが始まり、その後エージェントが引き継ぎました。 |
| `missed` | `missed` | エージェントがステップを最初から実行しました。 |

どちらも `step.cache.reason` を持ち、`step.cache.detail` はリプレイがどこでなぜ停止したかを示します (`at action 2 of 3, tap button "Apply": ...`)。`end-mismatch` のあとは、表示されなかった記録済みノード、消えなかったノード、記録には現れなかったアラートを挙げるか、リプレイがアクションを行う前から結果がすでに表示されていたことを示します。`step.cache.entry` はエントリーのキーであり、ファイルストアでのファイル名 (`<entry>.json`) です。

| 理由 | 何が起きたか | 対処 |
| --- | --- | --- |
| `no-entry` | このステップとそのパラメーターに一致する記録がありません。 | ステップの `step.cache.write` が `no-change` でない限り、次に検証された合格で記録されます。 |
| `retry` | `--strict-cache` または `cache.strict` の場合を除き、リトライはリプレイしません。 | 何もしなくて構いません。 |
| `invalid-entry` | ファイルが読み取れないか、1 MiB を超えているか、別のスキーマバージョンのものです。 | `npx e2e cache clear`。 |
| `truncated` | 記録が上限に達しました。[下記](#limits-and-gaps)を参照してください。 | ステップを分割するか、シークレットを `Secret` として渡してください。 |
| `wrong-context` | アプリが、ステップの記録時とは別のルートにありました。[リプレイの仕組み](#how-a-replay-works)を参照してください。 | ステップの前に同じ画面を開いてください。 |
| `target-not-found` | 記録されたコントロールが 15 秒以内に現れなかったか、名前がなく、同じものと区別するための名前付きコンテナもありません。 | UI が変わりました。次に合格する実行で再度記録されます。名前のないコントロールには、ラベルを付けるか、名前付きの行やグループに入れてください。 |
| `target-ambiguous` | 一致するコントロールの数が変わりました。 | 繰り返されるコントロールに別々の名前を付けるか、一意のテストデータを使ってください。 |
| `gap` | リプレイできないアクションがあります。[下記](#limits-and-gaps)を参照してください。 | この部分はエージェントがライブで行います。安定した値は `params` に入れてください。 |
| `action-failed` | アプリがリプレイされたアクションを拒否しました。 | アプリを確認してください。 |
| `action-uncertain` | リプレイされたアクションが失敗し、それが効果を持ったかどうか不明です。エージェントは再度アクションを行う前に確認するよう指示されます。 | アプリを確認してください。 |
| `viewport-changed` | 座標のみのタップ、ホバー、ドラッグが、別のサイズのビューポートで記録されていました。 | ビューポートを固定してください。 |
| `end-mismatch` | すべてのアクションは実行されましたが、[終了チェック](#how-a-replay-works)が失敗しました。 | 以前の実行の残りデータ、表示されたりされなかったりするバナー、またはリグレッションです。一意のテストデータと `afterEach` でのクリーンアップが役立ちます。 |

失敗の原因からキャッシュを除外するには、キャッシュなしで 1 回実行してください。

<CodeGroup>
```bash npm
npx e2e run --no-cache
```

```bash pnpm
pnpm exec e2e run --no-cache
```

```bash bun
bunx e2e run --no-cache
```
</CodeGroup>

### 上限とギャップ

ステップが次のいずれかに該当する場合、記録は `truncated` になります。

- 50 を超えるアクションを行った (`maxSteps` が 50 を超える場合にのみ起こり得ます)
- 4,096 文字を超える値や URL、または登録済みのシークレットを含む値を入力した
- 使用可能な説明のないコントロールを操作した

`gap` は、キャッシュが繰り返せないアクションです。変更を伴う[プロジェクトツール](/tools)、あるいはエージェントが画面から読み取った値、スクリーンショットを見たあとに入力した値、日付から算出した値です。`step.cache.derived` はそのルールを示します。`whole-node` (コントロールの名前やテキスト全体)、`minted-token` (アプリが独立した単語として表示したコードや ID)、`date`、`pixels` のいずれかです。指示や `params` からの値、およびエージェント自身が組み立てた値はリプレイされます。

## 記録の内容

各エントリーは `.e2e/cache/` 以下の JSON ファイルで、キーのハッシュで名前が付けられます。アクション、ターゲットの説明、入力されたテキスト、ステップの要約、そして終了チェック (ルートと、現れたコントロール最大 8 個、消えたコントロール最大 8 個) を保持します。エントリーには、プロンプト、会話、スクリーンショット、観測したツリー、シークレットの値は含まれません。シークレットの入力では、シークレットの名前だけが保存されます。

<Warning>
その他の入力値は入力されたとおりに保存されます。記録を共有する前に確認してください。[キャッシュの信頼性](/reference/security#cache-trust)を参照してください。
</Warning>

## モード

| モード | リプレイ | 記録 | デフォルト |
| --- | --- | --- | --- |
| `'read-write'` | する | する | ローカル |
| `'read-only'` | する | しない | `cache` が未設定の場合の CI |
| `'off'` | しない | しない | 1 回の実行に対する `--no-cache` |

```ts title="e2e.config.ts fragment"
cache: 'off',
// or
cache: { mode: 'read-write', dir: '.e2e/cache' },
```

`--no-cache` は設定より優先されます。`read-only` モードでは、古いエントリーは `read-write` の実行が置き換えるまで残ります。カスタムの `cache.store` はファイルストアを置き換え、CI でも `read-only` がデフォルトになりません。`e2e explore` と `e2e mcp` のセッションはキャッシュを使いません。セッションが実行するテスト ([`open_session {test}`](/reference/mcp#running-a-test)) は、実行の最初の試行と同じようにキャッシュを使います。

## チェックアウト間でキャッシュを共有する

`E2E_CACHE_DIR`、または 1 回の実行なら `--cache-dir` で、プロジェクトのすべてのチェックアウトを 1 つのディレクトリに向けてください。どちらも `cache.dir` を置き換え、プロジェクトルートから解決され (`~` または先頭の `~/` はホームディレクトリです)、モードは変更しません。カスタムの `cache.store` を使っている場合、`--cache-dir` はエラーになり、`E2E_CACHE_DIR` は無視されます。並列実行でディレクトリを共有できます。各書き込みはファイルをアトミックに置き換えます。エントリーはプロジェクトごとにキーが付けられるため、すべてのチェックアウトに同じ `projectId` (または `package.json` の `name`) を指定してください。どちらもない場合、各チェックアウトのパスがそのアイデンティティになり、チェックアウト間で何もリプレイされません。

- チェックアウトはエントリーを共有します。どのチェックアウトで失敗した実行もエントリーを削除し、アプリのアイデンティティが同じでアプリのコードが異なるチェックアウトは互いのエントリーを上書きします (最後の書き込みが優先されます)。
- オーバーライドが設定されている間は、`cache.dir` 以下にコミットされたキャッシュは読み込まれません。
- プロジェクトごとに 1 つのディレクトリを使ってください。1 つのディレクトリに 2 つのプロジェクトがあると、`cache.strict` の下で誤った `REPLAY_STALE` で失敗することがあります。

```bash
E2E_CACHE_DIR=~/.cache/my-app/e2e npx e2e run
```

## リプレイキャッシュをコミットする

<span id="commit-your-traces" />

`e2e init` は `.e2e/cache/` を `.gitignore` に追加するため、各マシンはそれぞれ独自に記録し、CI は何もない状態から始まります。リプレイを共有するには、その行を削除してディレクトリをコミットしてください。`cache: 'read-write'` を設定しない限り、CI は `read-only` のままです。コミットされたエントリーはテストデータとして扱い、再記録したプルリクエストでレビューしてください。

ローカルの実行は、何かが変わらない限り、コミットされたディレクトリを変更しません。リプレイされたステップはエントリーを書き換えず、アクション、パス、アンカーが同じライブの記録は書き込まれません。そのため、少しずつ変化する UI のエントリーは、コントロールが見つからなくなったときにのみ修復されます。ファイルが変わるのは次の場合です。

- ステップが初めて記録されたとき、またはエージェントへの引き継ぎのあと
- ステップがリプレイ後に失敗した、エージェントが修復する必要のあった `end-mismatch` で終わった、記録するものがないまま合格した、または試行の終了までに確認されなかった場合で、これらはエントリーを削除します
- `e2e` のアップグレードでエントリーの照合方法が変わったとき。すべてのエントリーに新しいキーが付くため、次の実行で再記録されます

## 古い記録で失敗させる

デフォルトでは、コミットされた記録がリプレイできなくなっても何も失敗しません。エージェントがステップを引き継ぎ、誰かが再記録するまで、CI の実行のたびにモデル呼び出しのコストがかかります。`--strict-cache` (または `cache: { strict: true }`) を使うと、ステップは `REPLAY_STALE` で失敗し、モデル呼び出しを行いません。

<CodeGroup>
```bash npm
CI=1 npx e2e run --strict-cache
```

```bash pnpm
CI=1 pnpm exec e2e run --strict-cache
```

```bash bun
CI=1 bunx e2e run --strict-cache
```
</CodeGroup>

`REPLAY_STALE` は終了コード 2 で終了し、リトライされません。

| 厳格モードで失敗するもの | 引き続きライブで実行されるもの |
| --- | --- |
| `invalid-entry`、`wrong-context`、`target-not-found`、`target-ambiguous`、`viewport-changed`、`action-failed`、`action-uncertain`、`end-mismatch`: アプリまたはエントリーが変わった | 一度も記録されていないステップ (新規または編集された指示やパラメーター) |
| `no-entry` で、キャッシュディレクトリに同じステップの記録が別のキーで存在する場合 | `gap` または `truncated` の記録 |
| | ストアの読み取りが失敗するステップ |

別のキーの記録は、キーを変更した `e2e` のアップグレード、またはプロジェクト ID、アプリのアイデンティティ、エージェントのコンテキストの変更によって生じます。メッセージはそのファイルを示し、現在のバージョンで作られた記録の場合は何が変わったかも示します。何もリプレイしないファイルは削除してください。このチェックはカスタムの `cache.store` には適用されません。

厳格モードの実行は、`read-write` モードであってもエントリーの書き込みや削除を一切行わないため、新しいステップは厳格モードではない実行でのみ記録されます。設定の `cache.strict` よりも、CI での `--strict-cache` を推奨します。古いエントリーを修正するには、次のようにします。

1. フラグなしで、`read-write` モードでテストを実行します。設定で `cache.strict` を指定している場合はオフにしてください。
2. 変更されたエントリーをコミットします。カスタムの `cache.store` の場合は、代わりにその実行から新しいエントリーを受け取ります。

## キャッシュを調べる

<CodeGroup>
```bash npm
npx e2e cache ls      # one row per entry: test, target, instruction digest, age, actions
npx e2e cache stats   # entry count and size
npx e2e cache clear   # delete every entry
```

```bash pnpm
pnpm exec e2e cache ls      # one row per entry: test, target, instruction digest, age, actions
pnpm exec e2e cache stats   # entry count and size
pnpm exec e2e cache clear   # delete every entry
```

```bash bun
bunx e2e cache ls      # one row per entry: test, target, instruction digest, age, actions
bunx e2e cache stats   # entry count and size
bunx e2e cache clear   # delete every entry
```
</CodeGroup>

<Note>
AI 使用量の `cached` の割合は、プロバイダーのプロンプトキャッシュです。これはモデル呼び出しのコストを下げます。リプレイキャッシュは呼び出し自体をスキップします。
</Note>
