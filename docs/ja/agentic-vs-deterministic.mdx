---
title: エージェント型か決定論的か
description: エンドツーエンドテストで、エージェント型と決定論的なアクションやアサーションのどちらを使うかを選びます。
---

エージェント型テストでは、ユーザーの意図と期待する結果を自然言語で記述できます。
エージェントは実行するアクションを選び、画面が期待を満たしているかを判断できます。
テストは結果に集中でき、UI が変わるたびにセレクターを保守する必要はありません。

決定論的テストでは、アクションとチェックをコードで指定します。どちらのアプローチでも
ユーザーにとっての結果をテストでき、e2e では 1 つのテストの中で両者を組み合わせられます。

## エージェント型テストを使うべきとき

UI の変更のたびにテストのセレクターを更新しなければならない場合は、エージェント型テストを使います。
フォームへの入力と送信のように、多くの操作が必要でも平易な英語で簡単に記述できるフローにも適しています。

`agent.act` を使うと、割引コードの適用のようなユーザーの意図を記述できます。
エージェントは、どのコントロールを使い何をすべきかを判断します。
`agent.assert` は、合計に割引が適用されているなど、記述した結果が画面に表示されているかを確認します。

たとえば、`app` と `agent` のフィクスチャを使うテストの中では次のようになります。

```ts
await app.open('/checkout');
await agent.act('apply the discount code SUMMER');
await agent.assert('the checkout shows code SUMMER applied with a 10% discount');
```

割引のフィールド、それを適用するボタン、結果を表示する要素の名前を指定する必要はありません。

CSS クラスやテスト ID に依存したテストは、それらの識別子が変わると修正が必要になります。
ボタンを移動したりフォームを再設計したりしても、エージェントは画面上にあるものを使って
ユーザーの意図を実行できます。

エージェントはアプリに適応するため、エージェント型テストを使うと、決定論的なデータを投入しなくても
ステージングや本番環境の実データでモニタリングできます。その場合はテスト用のアカウントを使ってください。
モデルには画面上のものが見えます。[セキュリティ](/security) を参照してください。

複雑なジャーニーでは、一連のゴールを平易な英語で書きます。各ゴールの結果は 1 つに絞り、
次に進む前にそれを確認してください。ジャーニーをステップに分割する方法については
[ゴール](/core-concepts#goals) を参照してください。

## エージェント型アサーションを使うべきとき

エージェント型アサーションは、複数の言い回しやレイアウトが同じ要件を満たしうる場合に役立ちます。
たとえば、バリデーションメッセージは、特定の 1 文と一致しなくても何が問題かを説明できます。

```ts
await agent.assert('the error message explains that an email address is required');
```

視覚的なチェックには `vision: true` を追加して、モデルがスクリーンショットも見られるようにします。

```ts
await agent.assert('the chart trends upward', { vision: true });
```

`agent.assert` は現在の画面を確認し、記述が偽である場合や証拠が不十分な場合に失敗します。
UI が期待する状態になるまでにまだ時間がかかる場合は、`agent.waitFor` を使います。
両方のメソッドについては [アサーション](/core-concepts#assertions) を参照してください。

## 決定論的テストを使うべきとき

使うべきコントロールがすでにわかっている、短く安定したフローにはロケーターを使います。
この割引のテストのように、各フィールドとボタンをコードで指定します。

```ts
await app.open('/checkout');
await screen.getByLabel('Discount code').fill('SUMMER');
await screen.getByRole('button', 'Apply').tap();
await expect(screen.getByRole('status')).toHaveText('10% off');
```

これらのアクションとチェックはモデルを呼び出しません。テストがユーザーにわかるコントロールを
参照するよう、ロールとラベルを優先してください。決定論的テストが CSS クラスやテスト ID に
依存する必要はありません。

期待する結果を正確な値、数、状態として表現できる場合は、決定論的アサーションを使います。
これらはモデルの判断なしに結果を確認します。バリデーションメッセージに特定の文言が必要な場合は、
そのテキストを `expect` で確認してください。

## エージェント型と決定論的テストを組み合わせる

アクションとアサーションはそれぞれ独立して選べます。変化する UI の中はエージェントに進ませ、
その後 `expect` で正確な値を確認できます。

```ts
await agent.act('apply the discount code SUMMER');
await expect(screen.getByRole('status')).toHaveText('10% off');
```

また、ロケーターを使ってフォームに入力して送信し、その後 `agent.assert` を使って
バリデーションメッセージが問題を説明しているかを確認することもできます。

適応は、あなたが書いたゴールに従います。曖昧な指示では、意図しない結果が許容されることがあります。
特定の経路が重要な場合は、それをゴールの中で指定するか、それらのアクションにロケーターを使ってください。
`agent.act` の後に `expect` を置くと、誤った形で達成されたゴールを検出できます。

モデル駆動のアクションとアサーションは、レイテンシーとコストを増やし、間違えることもあります。
[リプレイキャッシュ](/cache) は、記録された `agent.act` のアクションをモデル呼び出しなしで
繰り返せます。アサーションはテストを実行するたびに再実行されます。記録が一致しなくなった場合、
厳格なキャッシュモードが有効でない限り、エージェントは変更された UI に適応できます。
この仕組みについては [セルフヒーリングテスト](/self-healing) を参照してください。
